# Lark bot: chatting with Persona in Lark

When the user DMs the bot of a custom Lark app, they are talking to Persona: messages go into the main chat in the **Persona** tab (or, via commands, another chat or
Claude Code / Codex on one of the computers), and the turn's answer is sent back to Lark as the bot; whenever Persona or an Agent needs the user to answer or approve something, a card is sent in Lark,
and one tap answers it; pushes and answers from the main chat elsewhere can also be copied to Lark. Each item has its own switch, all off by default (requested 2026-11-02: "do P1/2/3, all optional", issue #322).

It is the channel `feishu` (`docs/extensions/channels.md`): tracking the turn goes through the shared pipeline (`assistant/channels_runs.go`, rules in `server/internal/channel`, the same as WeChat);
this page covers the Lark side (progress card, answer card, reactions, question cards, commands).

**Who owns what** (since 2026-11-04, `docs/extensions/channels.md` ("Responsibilities"); since 2026-11-05 the transport also lives in the manager, `server/internal/extmgr`, `docs/extensions/extensions.md` ("Who owns what"); the transport parts below that say "hub" are done by the manager): the transport is only the app credentials and feature switches (`bots.feishu`), the Open Platform long connection, pairing, accepting only the owner (in DMs, and in the topics of the group chats the owner opted in), sending / replying to / editing messages and cards,
reactions, reading messages and downloading resources; the owner's messages and card taps are handed to the assistant (`feishu.message` and `feishu.card_action` on the bus). Which chat a message goes to, commands, tracking the turn, progress and answer cards,
question cards and button answers, pushes and sync belong to the assistant (`personad assistant`), and so does the chat state `bots.feishu.state`; whatever it needs to send or edit, it asks the hub to do via `app.call feishu.*`.
When the assistant isn't connected, the owner's message first waits up to 60 seconds for it (the hub just started, the assistant is restarting); only if it doesn't come does the bot reply "Couldn't send it: Can’t reach the assistant right now. Try again later"; card taps get the toast "Can’t reach the assistant right now. Try again later";
pairing, binding and the settings page here keep working (see `docs/extensions/channels.md` ("When the assistant is away")). When a card tap answers a question / approval, the hub hands the assistant a one-time "owner action" that can only answer that one card;
the assistant can't approve anything on its own (`docs/extensions/channels.md` ("Responsibilities", "No answering approvals on the user's behalf")). After re-pairing (including while the assistant was away), the chat starts over: it goes back to the main chat, and thread bindings and pending answers are cleared.

Code: `server/internal/feishubot` (long connection, REST, events and message content, cards), `server/internal/hub/bots*.go` (pairing, routing, transport: events on the long connection are handed to the assistant; `assistant_channels.go` is the `feishu.*` the hub gives the assistant),
`server/internal/assistant/feishu*.go` (targets, commands, sending into chats, cards, pushes, sync: Lark's side of the shared pipeline);
prompt `server/internal/prompts/bot/message.md`; the App page `apple/Persona/Views/Settings/FeishuBotView.swift` (**Settings › Connectors › Lark Bot**). On web Settings › Connectors, the lark-cli status appears in this Lark group.

## How it differs from Lark `/agent`

| | Lark bot (this page) | Lark `/agent` (`docs/extensions/lark-agent.md`) |
| --- | --- | --- |
| Trigger | DM the bot | **You** send `/agent …` in any chat |
| Identity | The bot itself (never taken as you speaking) | Replies in your name (ends with "> 🤖 AI 代答，仅供参考" (AI reply, for reference only); the prompt forbids making promises for you) |
| Where it goes | The main chat (or the chat / Agent switched to), continuing the earlier conversation | A new headless chat per request / thread; the hub first collects that chat's context |
| Depends on | A custom app on the Lark Open Platform (may need admin review) | The Lark gateway (no approval needed) |
| Interaction | Card buttons answer questions and approvals directly | None |

The two complement each other and have separate switches.

## Why the Open Platform long connection

- The hub doesn't need a public address: `POST /callback/ws/endpoint` returns a WebSocket URL, the hub connects out, and both events and card callbacks come over that connection (Open Platform's "receive events over a long connection").
  It runs on intranet machines, NAS boxes and home machines alike.
- The official Go SDK (`oapi-sdk-go/v3`) is 4.8 MB in total and also pulls in gogo/protobuf and gorilla/websocket; the protocol itself is tiny (one protobuf `Frame`),
  so `feishubot/frame.go` hand-writes the encoding, checked against bytes the SDK generates in `TestFrameMatchesTheSDK`. The WebSocket is the repo's existing coder/websocket.
- Protocol essentials (following the SDK's behavior): the client sends ping control frames every `ClientConfig.PingInterval` (2 minutes by default), and the pong may carry new config; a data frame's
  header has `type` (event / card), `message_id`, `sum` / `seq` (fragments of large messages, reassembled before processing); every data frame must be answered with the same frame, its payload replaced with
  `{"code":200,"data":<base64 JSON>}`; for card callbacks the data is the toast / new card to show, and if Lark gets no answer **within 3 seconds** it retries. Receiving nothing for two ping intervals means the connection is dead, and it reconnects.
- The same event may be redelivered: messages are processed only once per message_id (`seen` in `bots.feishu.state`, keeping the latest 300).
  Card presses are not deduplicated on the hub side, which hands every delivery to the assistant: each press that does something once guards itself there —
  an answer goes through its one-use owner action (a second answer to the same card finds it answered, `interactions.resolve`), and a press that starts work
  takes a slot per pressed card and button (`pressOnce`, `feishu_card_actions.go`: the `/start` card's **Start** for a minute, the list card's **Start new agent**
  for ten seconds), so a double tap, Lark's redelivery and the hub's resend of a call it gave up on all act once. A press whose work failed frees its slot and
  says why, so pressing again retries it rather than being answered with the same "Starting…".

## Pairing and permissions

- App credentials: enter the App ID / App Secret in the App (it tries `GET /open-apis/bot/v3/info` once first and saves only if that works); the Secret is AES-GCM encrypted with the manager's own `secret.key` and stored in settings
  `bots.feishu` (the same master key as launcher keys), and no endpoint ever returns the plaintext. If you'd rather not go through the App, write `bots.feishu` in the manager's `manager.json` (0600, `docs/operations/config.md` ("manager.json")); what's saved from the App takes precedence.
- **Only the one paired person**: the main chat can use all the data (Lark, mail, every computer, the phone's calendar and location), and anyone in a group can @ it, so a group is only listened to where the owner said so ("Topic group chats" below). In the bot's DM, anyone else who writes to it gets a single reply "This bot only works for its owner." (at most once per person per 10 minutes). Card buttons also only accept the owner's open_id, in the DM and in a group alike, and only on a card in the DM or in an opted-in group: the chat comes from the callback, else from the card's message (what the hub remembers of it, else the Open Platform), and a press whose chat cannot be told is refused.
- Sending: the assistant's `feishu.post` / `feishu.text` go into the owner's DM unless the call names a `chat_id`; the hub accepts the owner's DM chat id and the ids of the group chats the owner opted in (anything else is refused with an error, nothing is sent). `in_thread: true` on a reply puts it in the parent's thread (`reply_in_thread`); if the parent was withdrawn, a plain reply's answer goes into the call's chat as a plain message, while a call with `no_detour: true` fails with the error instead (for what belongs under that parent or nowhere: a to-do's line into its topic, and a card for a topic's run, which then goes to the owner's DM as one that the chat refused does). A reply lands in the chat of the message it answers whatever `chat_id` says, so `reply_to` is checked too, for `feishu.post`, `feishu.text` and `feishu.cot_create` (the only calls that take one): the hub looks up which chat the parent is in and refuses a parent that is not in the owner's DM or an opted-in group, and one whose chat it cannot tell. The chat comes from what the hub remembers (the owner's own messages in the DM and in an opted-in group, and the messages the bot itself sent there, the last 500; a stranger's message is never kept, so strangers cannot push them out), else from the Open Platform (`GET /open-apis/im/v1/messages/:id`, whose answer must be about that very message; the client reads again when the network blips or Feishu is busy; an answer for a chat the bot may use is remembered). A lookup that keeps failing refuses the reply, so it happens only for a parent that is not remembered (after a hub restart). A parent that is withdrawn or deleted cannot be replied to and goes by the rule above. An agent message (`feishu.cot_create`) is made in the owner's DM, so its parent has to be in the DM, not in a group. A thread reply and a plain reply to the same message with the same content have different idempotency keys, so one is not dropped as a repeat of the other. A call may also pass its own `uuid` (`feishu.post` and `feishu.text`; letters, digits, `:`, `_` and `-` only, anything else is ignored; cut to 50 characters for text, 46 for a card): the reply goes out under it in place of the parent-and-content key, so two lines with the same words are two messages. Without these fields nothing changes. The one exception is a text reply (`feishu.text`) under a message the owner's `@bot /ai …` was taken from in a group that is not opted in ("Asking from any group" below): that chat is not allowed, only the reply is.
- **Creating the app in one authorization** (#4347, `extmgr/bots_register.go`, `feishubot/register.go`): binding the channel (Settings › Channels › Lark) with no app yet starts the accounts site's
  device-code app registration (`POST https://accounts.feishu.cn/oauth/v1/app/registration`, Lark's accounts site for Lark tenants) for a personal-agent app named Persona, asking for the bot's tenant scopes
  and the card callback (the page's `addons`) and for the confirming person's `open_id`. The step is a QR code of the authorization page with a link to open it directly (on the phone that has Lark);
  the client asks again every `interval` seconds. Once confirmed, the answer carries the new app's App ID and Secret: they are saved and checked like typed ones, `AutoConfigure` runs as below, the confirming
  person becomes the owner, and the bot greets them by `open_id`, which gives the private chat's `chat_id`; the assistant is told `feishu.owner {paired, greeted}` and starts the chat without a second greeting.
  The registration under way (its device code sealed with `secret.key`) is kept in `bots.feishu.registration`, so a restart between polls loses nothing; a confirmed one whose finishing failed is finished on the next poll, never registered again.
  A tenant on the other cloud (`tenant_brand`) is polled there; an expired or declined authorization starts another one and says so; when the accounts site cannot be reached, or the deployment is private, the step is the credentials form.
  Typing the App ID and App Secret of an existing app stays available on the Lark bot's settings page, folded under Advanced.
  The web Lark bot page starts the same registration itself when there is no app (#5818): its first group is **Create the bot**, one
  **Scan to create with Lark** button that sends the channel's bind step (`POST /api/v1/channels/feishu/bind`) and draws the QR step
  Settings › Channels draws, so both places run one flow. The credentials form and the manual steps sit under a folded
  **Already have a Lark app?** (no app) or **Advanced: use another Lark app** (an app bound); with credentials from `manager.json` there is no
  create step. When the dialog also shows reading Lark as you (`larkcli`) and lark-cli follows the bot's app with none of its own,
  that section says to create the app above first instead of offering an authorization that cannot work; once the scan is
  confirmed, the authorization starts by itself and shows its own QR code, so setting up both is two scans on one page.
- Pairing (an app whose credentials were typed in): tap **Pair** in the App to get a 6-digit code (valid for 10 minutes) and send it to the bot in Lark; whoever sends it becomes the owner (its open_id and the DM's chat_id are recorded).
  When not paired, DMing it returns instructions on how to pair; 5 wrong guesses void the code, and you have to get a new one. Changing the App ID means pairing again (it's a different bot).
- Names: reading contacts needs `contact:user.base:readonly`; without that permission the owner is called by `assistant.owner` in the manager's `manager.json`, and others "someone".

## How a message flows

1. `im.message.receive_v1` → de-dup → stop if it's not the owner / not a DM (a group's message goes by the gate in "Topic group chats"; up to here it's the hub; the owner's message is handed to the assistant, which de-dups again by message_id and stores it). Anything starting with `/` is first treated as a command (below); unknown commands are passed through as is (they may be the Agent's own, e.g. `/compact`); to a Persona conversation, a bare one that looks like a slipped bot command (a letter dropped or two adjacent letters swapped, e.g. `/stpo`, `/stp`) is not sent: the bot replies "Did you mean /stop?". With words after it (`/news 今天有什么新闻`), real words (`/news`, `/now`) and Claude Code / Codex commands (`/stats`) it goes on, and nothing to an Agent is held back. To send such a command itself, double the slash (`//stpo` sends `/stpo`); a doubled slash is only taken off before a bot command or a slip of one, outside an Agent, so other text starting with `//` (`// TODO`, `//example.com`) goes as written (#5005).
2. Target: if it's a reply to a message the bot sent (or in its thread), it goes to the chat / Agent bound to that message (`threads`, kept for 30 days, up to 500 entries, so replying to a card from several days ago still goes back to the original place, #4779); otherwise it goes to the current target (`current`: `main` / a Persona chat / an Agent).
3. Content: text (rich text converted to Markdown, @ mentions turned back into names); images (up to 4) as image attachments; files, voice, video and extra images are downloaded and stored via the node's
   `file.upload.*` in that computer's temp directory, with the path written into the message (a file over 50 MB is skipped: the rest of the message still goes, and a line says which file was too large, #4824); quoted messages and merged-forward chat histories (read out one per line) go into `<persona-context>`; images and files in quoted messages are handed over by the same rules (up to 4 together with the message's own images; if they can't be read, only the quoted text is included, without blocking the send, #4728);
   messages to Persona also get a note "the answer will be sent back to Lark; lead with the conclusion, don't use notify_user" (prompt `bot/message.md`).
4. Sending: Persona chats go through `session.send` (the main chat follows the launcher in **Settings › Assistant** just like the App; the assistant sends via the hub's `session.send_once`), with `client_msg_id` `feishu-<message_id>`,
   sharing the `sent_messages` de-dup with the App: redelivered events aren't sent twice. If there's no main chat yet, a new one is started and set as the main chat. The message gets an "OnIt" reaction.
5. Tracking the answer (the shared pipeline's run, stored in `channels.state`, so waiting resumes after the assistant or hub restarts; old versions' data in `bots.feishu.state` is moved over on first read): the assistant follows the chat the way the App does when it opens it (`session.follow`; the hub forwards new items and text being written).
   - Progress: about 1 second after the message is sent, a **progress card** is posted as a reply under the owner's message, without waiting to see the chat working: while the message hasn't shown up in the chat yet it says "Getting ready…"; while the chat is busy with another turn (this one queued behind it) it says "Queued…"; once the message is found it says "working", with the summary "Working · 3m 12s so far", and steps are counted only from this message on (the previous turn's steps aren't listed).
     The card shows, in order: "Now: Run `go test ./...` (40s so far)" (the latest tool call without a result yet and how long it has run; when several are running it adds "and N more"; once all have results this line is dropped);
     the last 5 steps (earlier ones as "…N earlier steps"); when subtasks (Task / Agent) were used, a "Subtasks" section, one line each with description, type and "running" / "done", up to 6, more as "and N more";
     small gray text "N tool calls · read X files · changed Y files" (counting distinct files, zeros omitted, "1000+" from 1000 up); and finally the text being written. These are recorded as new items arrive (`chanLive`), not rescanned, with a cap on entries; the turn after a background task reports back starts from zero.
     With new steps it's edited at most once every 3 seconds, and even without new steps it's edited every 3 seconds, so the elapsed time keeps moving and it never looks stuck. The answer is written into this card, and the process goes into a collapsible panel "Called tools N times". Before a background task reports back (after one answer, while waiting on the background), no new card is sent; it's sent once that turn starts working.
     When editing, if the content is the same as last sent, nothing is sent; when Lark says edits are too frequent (230020, 99991400, HTTP 429), it pauses 5 seconds first, then 10 and 20 seconds on repeats, up to 30 seconds, and then sends the latest state; the answer isn't held back by that pause: its own last write into the card waits the card-update window out once when it is refused as too frequent (a finished run has no later update to write the card, so it would keep saying it is still working),
     if the card was recalled or deleted (230011, 230110), it forgets the card, the next refresh posts a new one, and the answer goes into the new card.
   - New turns no longer use **agent messages** (the Open Platform's `message_cot`, since 2026-11-06): they can't show elapsed time or "what it's doing now", and they're only created once thinking or a tool call appears, so nothing shows during a text-only stretch.
     A turn that already created an agent message before that (started before an upgrade or restart) keeps appending to it and finishes it (`RUN_FINISHED`), and the answer is sent as a separate card. The hub's `feishu.cot_create` / `cot_append` / `cot_complete` call the API, and events are in AG-UI format (`feishubot/cot.go`).
      When an already-open agent message errors (#2807): rate limits, a busy service or no response from Lark (the hub records error code -1) only mean this attempt wasn't sent, and the next one continues; a batch that may already have arrived isn't resent; if the final append fails, the answer is still sent and the agent message is closed with `cot_complete` (its own 15-second deadline, up to 3 tries) rather than left spinning; tool calls already shown but without results are stored in the run's `cot_calls`, so they're still closed after the assistant restarts.
   - When the turn ends (not working, no card waiting for you), it takes the answer **after this message** (every assistant text from the first on, in order, except a passing line of at most two sentences said right before a tool call: a report written before a tool call is part of it; `transcript.AnswerParts`) and writes it into the progress card
     (for old turns that still have an agent message: that gets closed, and the answer is sent as a separate card), and the reaction changes to "DONE". The card has no buttons.
     If the turn stopped without saying anything (model service error, interrupted): the card says "This turn stopped without a text answer: <reason>"; the only reasons recognized are "API 错误：…" (API error) and "已中断" (interrupted) at the end of the turn (compaction notices after them are skipped; goals, background tasks, Codex events and command output don't count as reasons), squeezed into one line of at most 300 characters; for Codex it takes the session's `turn_error` (`channel.Stopped`, #3340); without a reason it's still "(No text answer this turn)".
      If the end of the turn it reads isn't the assistant's text (the node reports "ended" slightly before the record finishes writing the last stretch), or the answer is empty / only a placeholder like "No response requested.": it doesn't answer yet and rereads within 10 seconds; if there's still nothing, it sends Persona chats one message "write out this turn's answer" (only once; not for Agents) and waits for that turn's answer; if there's still none, it sends "No answer came out of this turn. Why: …" and logs it (#4588).
     The card's last line says how it ended: "Done · took X · N tool calls"; cards that didn't finish normally say the outcome in the title rather than staying at "working / Getting ready":
     interrupted (`/stop`, the App, Esc on the computer) is "Stopped", a model API error is "Failed", not done after 4 hours (2 hours when waiting on the background) is "Timed out, see the app",
     a chat that was closed or deleted is "Conversation closed", and a computer going offline (including mid-task) is "Computer offline"; an ending with nothing to say also turns the progress card into this line, and a held run that has no card left (it gave the card back with its message) gets that line as a card of its own, so a timeout — or a background wait whose turn ends without another word — is never silent.
     That card of its own is posted for every ending except a message the owner recalled, which gets no card of its own (when the progress card itself cannot be written, the fallback below applies to every ending); it carries an idempotency key made from the run id, so a retry after the hub could not be reached cannot post the ending twice.
     **Answer as a new card** (`answer_new_card`, #5396): the progress card stays where the message came in, and in a busy chat (approvals, pushes, task reports posted meanwhile) an answer written into it ends up far above the newest message, with no Lark notification (Lark notifies on new messages, not on edits). With the switch on, a run that ends with an answer posts the answer's first card as a reply under the owner's message, under an idempotency key made from the run id and the progress card's message id (a held run answers each turn under a card of its own; a retry after the hub could not be reached lands once), and then rewrites the progress card into the folded process (`foldedProgressCard`: the process panel and "↓ Answered below"); the steps are left out of the answer card, which is otherwise the same (later pieces, the footer, "Open on web"). A quiet ending (no answer) still turns the progress card into its line. When the new card is refused, the answer is written into the progress card as with the switch off; when only the fold fails, it is logged and the progress card keeps its last state.
     The line says how the wait ended, done or not: a held run whose turn was interrupted, hit a model API error, or lost its computer ends as "Stopped", "Failed" or "Computer offline" rather than "Done" (#4228). When merged into the next message, the whole card becomes "Answering together with the next message".
     If editing the card fails with anything but a rate limit (the card was recalled, or is no longer a card), the answer — a quiet ending's line too — is sent as a card of its own; a rate limit is waited out once first (5 seconds), and only then is the answer sent as a card of its own — the progress card then keeps the last state it had, so the wait is what keeps it from saying "working" for good. An ending whose card and card of its own both failed because the hub could not be reached is not dropped: like any answer that did not go out, it stays with the run and is tried again.
   - The chat is busy when the message is sent: it queues behind the current turn. When that turn ends the message isn't in the transcript yet, and that turn's ending must not be taken as the answer, so it uses the message's `client_msg_id` (`feishu-<message_id>`; for old nodes without it, a stretch of the message's opening text, `probe`)
     to find its position in the transcript and takes only the answer after it; only if it still can't be found after 10 minutes does it fall back to the last words.
   - Another message to the same chat before it finished answering: the two get one combined answer (both messages switch to "DONE"): both go into the chat, the answer comes only when the last turn ends, and each message's own answer is joined in chat order (`docs/extensions/channels.md` ("Message flow")).
     The assistant processes the owner's messages one at a time in the order received (adding the reaction, downloading images, reading quotes, sending into the chat), and the next one waits until the previous was sent in: previously they ran in parallel, and a slow one (slow Lark API, images to download) could be overtaken by the next one into the chat, so the combined answer got attached to the earlier message.
     If the previous one is stuck (images downloading slowly, `/new` slow to start a new chat), it waits at most 20 seconds, then the next one stops waiting for it. Messages that weren't processed (duplicate deliveries, commands, not allowed to send) also let the next one proceed.
     The order is set from the long connection on: events on the long connection are handed to the manager in the order received (card buttons aren't queued), and the manager hands them to the assistant one at a time in order (when the assistant is away the previous one waits for it, and the next waits behind it).
     A message that arrives while a turn's answer is just about to be sent (`answering`) is no longer merged into that turn, or the same answer would be sent twice.
   - There are still background tasks (`run_in_background`, Monitor, sub-Agents): it answers once, saying "N background tasks are still running", then answers again when the turn in which they report back ends (waiting up to 2 more hours).
   - If it's not done after 4 hours, it stops waiting and says to check in the App.
   - The answer is laid out as cards by rules (no model call, `feishubot/answer.go`, #3148): a leading H1 becomes the card title; "请验收 / 无变动 / 有变动" (please review / no change / changed) in the title or at the start of a body line becomes a tag next to the title and sets the color (orange / gray / blue; blue when there's no status);
     H2s and short lines like "一、…" ("1. …" in Chinese numbering) start sections, with dividers between sections; Markdown tables become native tables (10 rows per page, up to 100 rows; a row with more cells than its header, a "|" it did not escape inside a code span among them, keeps those cells in the header's last column, joined with " | " and with empty ones skipped, rather than losing them (the joined cell is clipped and escaped like any other), #3852); "备注：" / "注：" (note:) lines are small gray text; web links in the answer become buttons at the bottom of the last card (up to 4). Code blocks are kept verbatim, with no headings or tables recognized inside. A nested list keeps its nesting: its items are re-indented to the four leading spaces per level that cards nest by, since a model indents a sub-item by its parent marker's width (two spaces under "- ", three under "1. ") and a card reads that as a sibling (#4180); a list item's indented continuation lines and anything in code are left as they are.
     Long answers are split into cards at 6000 characters, 80 elements or 5 tables, never breaking inside a code block; up to 5 cards, beyond that it says to see the rest in the App. If one in the middle can't be sent (rate-limit retries exhausted, rejected as both card and rich text), the rest are still sent, and finally a line is added under the owner's message: "N parts of this answer couldn't be sent to Lark (parts x); see the whole answer in the app." Already-sent ones aren't resent; the same goes for `notify_user` pushes, main-chat sync and scheduled-task answers (these are sent in the DM, #4766). If Lark rejects the card (the Markdown has something it doesn't accept), it's sent as rich text instead.
     When a stretch of text or a "备注：" line has lots of escaping (`<` takes 5 bytes in a card) and 6000 characters exceed 24000 bytes, it's cut smaller by bytes, so even a single stretch never pushes a card past 30 KB.
6. Turns started from Lark and answered in Lark no longer push a "done" notification to the phone (`botAnswered`), and `sync` doesn't send them again.

## Topic group chats

The bot's chat with the owner is the DM. A group chat is different: anyone in it can write to the bot, and the owner's Persona can reach all of the owner's data. So the bot listens to a group only where the owner has opted in, and then only to the owner, and only inside a topic (#5279: one topic per to-do, see `docs/assistant/todos.md` ("Replies in the thread")).

**Opting in.** The owner sends `/topics` (Chinese alias `/话题群`) in the group chat (only there: in the DM it is an ordinary message that goes to the assistant like any other); `/topics off` (or `/话题群 关`) takes the group out again. The hub checks the sender is the owner, and answers in the group with one line saying it is on / off / already on / was not on. From anyone else, or while the bot is not paired, the command is dropped without a word. It is the hub's own: it never goes to the assistant, and it takes effect before the next message is looked at (the message right after `/topics off` is not read, the one right after `/topics` is). The same list is the `topic_chats` setting: `PUT /api/v1/bots/feishu` takes `topic_chats: [{chat_id, name?}]` (replaces the list; absent leaves it, `[]` empties it; a paired bot is needed; at most 50, ids not empty, no spaces, no repeats; the list is checked before anything of the request is applied, so a list sent together with a new App ID, which unpairs the owner, is a 400 and changes nothing: set the list in a request of its own) and `GET` returns it as `topic_chats: [{chat_id, name?, added_at}]`. It is kept in `bots.feishu` with the owner, so unpairing (or changing the App ID) empties it. Adding and removing a chat are audited (`bot_topic_chat_added`, `bot_topic_chat_removed`).

**Home topic group** (#6146). One of the groups on the list is the *home*: where a request from a group that is not on the list opens its topic ("Asking from any group" below; with no home group the request is taken in the DM instead). `/topics home` (Chinese alias `/话题群 主群`) in a group makes it the home, and turns it on if it was not (the owner said so in so many words); only one group is home at a time. With none marked, the first group opted in is. Taking the home group out with `/topics off` takes the mark with it, and the first one left is home. `PUT /api/v1/bots/feishu` takes `home: true` on one entry of `topic_chats` (more than one is a 400; a list that says nothing about `home` leaves the mark where it is) and `GET` returns `home: true` on the group that is home now. `feishu.status` carries it as `home_chat`. Setting it is audited (`bot_topic_home`).

**The gate.** A message from a group chat (`chat_type` other than `p2p`) is handed to the assistant only when all five hold, or when it is the owner's `@bot /ai …` from a group that is not on the list ("Asking from any group" below); otherwise it is dropped without a word: no reply, no "owner only" note, no reaction, nothing said in the group.

1. The bot is paired.
2. The sender is the owner.
3. The chat is on the owner's list.
4. The message is in a topic (it has a `thread_id`).
5. It is not the opt-in command above.

A group message never changes where the owner's pushes go: the DM's chat id (`owner.chat_id`) is only ever set by a message in the DM. The message is handed over without an owner action (it can answer no card). The assistant does not rely on this gate: a `feishu.message` whose `chat_type` is not `p2p` goes to `threadMessage`, not to the DM's road (no commands, no card answers, no `botTargetFor`, never the current target). The to-do bound to the message's topic takes it as a `source = "thread"` decision and its Agent (else the conversation that opened it, else the main chat) gets it; the answer, progress card and notes go back into the same topic with `chat_id` and `in_thread`, and so do the question, plan, permission and terminal-dialog cards of the run (a card whose run was asked in a topic is a reply to that message in the topic). A conversation that has both a private run and a topic's gets the card in the owner's DM, where only the owner sees it, and the topic gets one short line saying the card went there. A card the topic refuses outright (the hub's refusal, because the group was taken off the list; Feishu's "the bot is not in the chat" 230002 or "the chat was dissolved" 232009) goes to the DM as well; any other failure (a timeout, a gateway error) may have gone out, so it is only logged and the card is not sent again. A topic with no open to-do gets one hint per 10 minutes, unless it asks for one: the message that starts a topic, or "/ai …" in a topic bound to nothing, opens a to-do for it and hands the words to the main chat (`docs/assistant/todos.md`, "Opening a to-do from a topic"). Details: `docs/assistant/todos.md` ("Replies in the thread").

### Asking from any group

(#6146) People who work with many groups do not want an AI conversation in each one. The owner writes `@bot /ai <what>` where the question comes up (optionally as a reply to someone's message, which is then the context); the work happens as a topic in the home topic group, and the outcome comes back as a reply to that message. Everything about the work stays in the topic; the original group sees an emoji on the message and, at the end, the outcome. It needs only `im:message.group_at_msg:readonly`. A topic group is not required: Lark is one channel of Persona, not its shape, so with no home topic group the work happens in the owner's private chat with the bot instead (see "No home topic group" below).

- **What the hub takes** from a group that is not on the list (`botAIElsewhere`, `extmgr/bots_topics.go`): the owner's message (a text or rich-text one, not a merged forward) that @-mentions the bot (told by its own open id) and whose words, the leading @ of the bot taken off, start with `/ai` as a word (`feishubot.AICommand`, also the full-width slash and any case; `/aim` is not it). Nothing else from such a group: someone else's `/ai`, the owner's ordinary message, an `/ai` without the @ all stay dropped without a word. What is taken is kept as a *source* (`ai_sources` in the bot's settings: chat and message id and how many replies it has had; the last 500, a source older than 90 days no longer counts, gone with the owner on unpairing), audited (`bot_ai_taken`, never the words), and handed over as `feishu.message` with `from: "elsewhere"` (no owner action), so the assistant can tell it from a topic's message. The group does not become one the bot reads, and a group message still never changes where the owner's pushes go.
- **What the bot may write there.** `botChatAllowed` is unchanged: that group is not a chat the bot may send into. One more rule of `feishu.text` (`aiSourceReply`): a text **reply to a source message**, in that message's chat, of at most 2000 characters, **at most two per source** (the one thing it has to say, and one more for a try that must be made again; a reply that fails still counts), and never turned into a message of the chat if the original is gone (`no_detour`). That is all: a send into the group, a reply under any other message in it, a card, a reply that names another chat, and a longer one are refused with `chat_denied` as ever. Two things use it: the failure note and the outcome. The emoji is `feishu.react` (and `feishu.unreact`): it goes only on a message of the owner's private chat, of a group on the list, or a source (which carries its chat), found as a reply's parent is (`checkReactTarget`); on a message of any other chat it is refused with `chat_denied`.
- **Opening** (assistant, `feishu_elsewhere.go`): `openFromElsewhere(src Source)` posts the topic's first message into the home group (a new message, so a new topic: "From another group chat: <what>", the replied-to text as a quoted line, clipped, only text, a merged forward not expanded, and a line saying `/noreply` stops the report back), reads its `thread_id` back, and from there does what a topic the owner started does (`docs/assistant/todos.md` ("Opening a to-do from a topic")): a to-do bound to the topic, handed to the main conversation, with the source recorded on it. The replied-to text is someone else's: it goes into the to-do's notes under a label that says so (and with nothing in it that closes a context block), and to the main conversation as a block of its own, escaped like any quoted text, titled as a message written by someone else, background only (`prompts/todo/thread_open.md`); the user's own words stay in the quotation above it. On success the original message gets an emoji (`OnIt`) and nothing is said in its group. Nothing is posted if there is no one to take the to-do (main conversation missing or off). A bare `/ai` gets a line asking for the words, under the message; any other failure is told under the message, with its reason.
- **No home topic group** (none on the list): the request is taken all the same, in the owner's private chat with the bot, the one place the bot always may write (`openInOwnerChat`). The first message is the same line, posted to the DM; the to-do is made as for a topic (supervised, handed to the main conversation, the run answering as a reply under that first message) but is bound to **no topic**, and its `source` carries that first message as its `anchor` (`docs/assistant/todos.md` ("Where it came from")). The original message gets the same emoji, and the group is told nothing. With a home group nothing differs from the above: it is never bypassed, and a home group that fails to give the message a topic is still a failure under the message, not a fall-back to the DM. The notice before the report goes into the DM as a reply under the first message, and `/noreply` is said by replying to that first message, to the notice, or to an answer under it (a `/noreply` that replies to none of them is an ordinary message to the conversation the chat is talking to). A to-do with no topic gets no lines in a topic, since it has none; its question and permission cards come as for any run in the DM.
- **Reporting back** and "don't report back": `docs/assistant/todos.md` ("Where it came from"). What goes out to the original group is one fixed-shape line only (the outcome's sentence, or "Done."), shown in the topic (or, with no topic, in the private chat) ten minutes before it is sent.
- **Later channels.** `openFromElsewhere` takes a `Source` (channel, chat and message of the request, the words, the quoted text) and does not care who received the request: the bot's gate is the first caller. A channel that sees the owner's own chats as the owner (an extension; the bot is usually not a member of those chats) can hand the same `Source` over the bus once a bus method for it exists, and tell the outcome back itself: a channel is added to `sourceChannels` and to `sendSourceReport` in `assistant/todo_source.go`, and until then a request from it is refused when it comes, so that no to-do is opened that cannot answer.

**Risk: a group on the list is a group the bot acts in.** Once a group is on the list, every topic the owner starts there opens a to-do and wakes the main chat, so a group used as a notebook gets a to-do per topic. And a group another bot already works in (an auto-starting bot, for instance) is answered twice, once by each bot. Put only groups meant for this bot on the list.

**What the bot says in a topic** (#5279, step 4). A to-do bound to a topic tells it about new decisions, its Agent finishing a turn or needing the user, and the to-do being accepted or closed: one short line with a link to the to-do, at most one a minute per to-do (several things of the same minute are one line; each line under a key of its own, so two that read the same both arrive). It goes out as `feishu.text` with `chat_id` and `in_thread: true`, a reply to the latest message the owner said in the topic, and only when the chat is one the bot may send into: `feishu.status` carries it as `chats` (the owner's DM and the opted-in groups, the same rule `feishu.post` / `feishu.text` are held to), so a `chat_id` an Agent put into a binding is never written to. The bot's own line is not a reply: it comes with a sender that is not a user and is dropped at the gate (condition 2 holds for users only). The DM's reports and pushes are not changed. Details: `docs/assistant/todos.md` ("Posting into the thread").

**Safety limits.**

- Only the owner counts. What anyone else writes in the group is never handed over, whatever it says; people in the group cannot drive the owner's Persona.
- Nothing others said is read in: a quoted message and a merged forward are not expanded for a topic message (the owner may quote someone else's text, which would carry it in).
- A card button pressed in a group counts only from the owner (the same check as in the DM) and only when the press names a chat that is the DM or on the list: a card left in a group that was switched off is dead (the toast says the chat is not turned on). The Stop button of a topic's progress card works the same way.
- A recall in the DM is passed to the assistant; in an opted-in group only a recall of a message the hub handed to the assistant is (the event does not say whose message it was).
- The bot sends into the DM and the opted-in groups only (see "Sending" above), and, in a group that is not opted in, one text reply under a message the owner's `/ai` was taken from ("Asking from any group").
- The group should still be one the owner trusts: anyone in it sees what the bot posts there (answers, progress, cards).

**Open Platform permissions.** Receiving a group's messages needs one of two permissions; the code does not tell them apart:

- `im:message.group_at_msg:readonly`: only messages that @ the bot arrive, so every message to Persona in the topic has to @ it. No special review is usually needed.
- `im:message.group_msg`: every message in the group arrives, no @ needed. It is a sensitive permission and usually needs the enterprise admin's review.

Subscribe to **Receive message v2.0** (`im.message.receive_v1`) as for the DM; the bot has to be in the group. A leading @ of the bot is stripped when reading `/topics`.

## Commands

`/help`, `/main`, `/new [first message]`, `/list`, `/agents [keyword]`, `/start [what it should do]` (a form to pick a machine and fill in a directory), `/stop` (Chinese aliases `/停止`, `/停`; interrupts the turn: sent in a message's thread / as a reply to it, it interrupts the chat or Agent bound to that message, otherwise the current target; a conversation whose last turn already ended gets "nothing is running" and no interrupt, while one this chat just sent a message into is stopped even when it does not read as working yet, #3793), `/status` (picks the target the same way from the reply / thread binding: who messages go to now, how many answers are pending), `/tasks` (aliases `/进展`, `/总览`; a snapshot of what waits for your decision and the open to-dos, or with `board` on, the standing board below). With `workbench` on: `/home` (aliases `/工作台`, `/主页`), `/today` (`/今日`, `/今天`) and `/inbox` (`/收件箱`); with it off they go on as text, as any command the bot does not know.

A newline, Tab or full-width space after the command name all count as separators, and a leading full-width slash `／` counts as `/`; content after `/new` is passed through as is, multiple lines included (#3897).

## Cards

- Cards use JSON 2.0 (`schema: "2.0"`): Markdown supports headings, tables and code blocks, so model answers display as written (1.0 doesn't support headings and tables). Needs Lark 7.20 or later; old clients show only the title and an upgrade notice.
  2.0 pitfalls: there's no `action` module, so lay buttons out horizontally with `column_set` (`flex_mode: flow` wraps automatically on narrow screens); `note` is gone, use `div` + `text_size: notation` + `text_color: grey`;
  button callbacks go in `behaviors: [{type: callback, value}]`; a submit button in a form needs `form_action_type: submit` and a `name` unique within the card; **one unknown extra field rejects the whole card**;
  a new card returned from a callback must also be 2.0.
- `<` in text outside code is turned into `&#60;` (cards swallow things like `<at>` and `<font>` as their own tags); data such as names and titles goes through `EscapeMarkdown`.
  The exception is autolinks the model writes, `<https://…>` and `<mailto:…>` (CommonMark): cards don't recognize them, and escaped they become unclickable text, so they're first rewritten as `[url](url)` (#4727). `(` `)` in the URL and `[` `]` after the hostname are percent-encoded, and `_` `*` `[` `]` in the link text become entities; other schemes (`javascript:` etc.), `\<` and anything in code stay as they are. Test: `go test ./internal/feishubot -run CardMarkdownAutolinks`.
- `persona-card` (chart cards, #886) in assistant answers can't be drawn by Lark, so they're written out as numbers before sending (`PersonaCards` in `feishubot/personacard.go`; it's the first step of `CardMarkdown`, so all text sent through `CardMarkdown` gets this, not just the health space; text a client draws as Markdown is converted before it is clipped as well, since `clipMarkdown` flattens a chart to its title on its own (`PersonaCards` first in the briefing card and in the task report card, #3818 / #4093); the bot's answer is converted as a whole before being cut into cards (`answerCards` in `assistant/feishu_answer.go`), otherwise a chart longer than one card would be cut off and unreadable, leaving an empty card):
  `stat` becomes one line (`Steps today: **8,432 steps** · +12% vs yesterday`); `line` / `bar` become the title plus a ▁…█ sparkline, with the numbers on the next line one by one (at most the latest 31) and the unit written once; `stacked_bar` and `ring` become a small two-column table (a `ring` whose `total` is more than its parts ends with a "剩余" row) with the total in the header, and beyond 31 rows the rest are combined into one "Other" row.
  Numbers are formatted the same as on every client (`wire.Number`), and text the model wrote always goes through `EscapeMarkdown`; cards that no client can draw keep only the title; a `persona-view` card (the assistant's cards are always on, #5509) is written as its text `fallback`, never its JSON or HTML; other code blocks and example cards inside code blocks are left alone. In chat list summaries, cards show only their title. Tests: `go test ./internal/feishubot -run PersonaCards`, `go test ./internal/assistant -run TestAnswerCardsWriteChartsAsNumbersBeforeCutting`.
- Link buttons only use http(s) (the docs only mention http(s) and AppLink; `persona://` may get the whole card rejected); "Open on web" opens the matching session page in the web version the hub hosts.
- The options on interactive cards match the App's cards:
  - Questions: a single question with at most 4 options and single choice is a row of buttons + a "Write your own answer" input; anything else is a form (one dropdown per question, a multi-select dropdown for multiple choice, plus an input), submitted at once.
  - Plans: the full text (up to 5000 characters), "Approve & run" (bypassPermissions) / "Auto-accept edits" (acceptEdits) / write feedback and "Send back".
  - Permissions: tool, reason, command or arguments; "Allow" / "Deny", plus "Always allow" for this session on Claude's card when there is a session. Another agent's card only gets the button that agent names itself (`always_label`, e.g. 本会话不再问这个命令): as in the App, a runtime can't keep Claude's session rule, so the button would only allow once. **Anything that must be filled in on the phone (passwords, authorization codes, `fields`) can't be approved in Lark**; only "Open on web" is offered.
  - An MCP server needs your authorization or a form (`elicitation`): the card says what it wants to do (`message`); link authorization gets an "Authorize" button (only http(s) links without username / password, opened as is; the card has a separate line "Opens: <site>", and after authorizing you go back to the App and confirm); forms only list the names of the fields to fill, which you fill in the App (values may be passwords, which Lark doesn't take), #4234.
  - Terminal dialogs: when the options can be read, one button per option; when not, Enter / Esc / 1 / 2 and an input; ones that need a password (`secret`) can't be typed in Lark.
- Wherever it's answered (Lark, the App, the watch, a notification button, the computer), the Lark card changes to "✓ Answered: …"; recalled / expired ones change to "Ended". Cards posted before an assistant restart are closed the same way (which message each card is in is kept in the chat state). Pressing a card that was already handled replies "Already handled"; the card changes to "Ended" only when the record says it ended for good (resolved / dismissed / expired / cancelled), and one not restored yet or not found stays as it is. The catch-up after the assistant reconnects does not close a card just because it is missing from the current list either: it asks for each card's outcome, and looks again after 90 seconds at the ones it is unsure about. Pressing a terminal or Codex card has to wait for the computer; after 2 seconds it first replies "Working on it…", then edits the card when done. A press whose answer comes back after that wait still says what became of it: one that failed posts a note under the card, which waits again for another press, and one that lost to another surface answering first closes the card as handled, as ever (#4123).

## Nudging a card nobody answered

A card the bot sent (a question, a plan, a permission, a terminal dialog or an MCP authorization) that has waited a while without an answer gets **one** short reply under it in Lark, where the user answers (#6084): "Still waiting for you: <what it asks>". Users who run many Agents get many cards; one answered within minutes needs nothing, the expensive ones slip past while the user is busy elsewhere. The phone's reminder 30 minutes after a seen-but-unanswered question (`docs/protocol/agent-states.md`, #5096) is a push, does not follow the card into Lark, and skips a card never opened, which is the slipped case.

- **When.** The assistant looks at the bot's open cards once a minute (`nudgeLoop` in `assistant/feishu_nudge.go`, next to the reply reminder's loop; rules only, no model, no tokens). A card is nudged once it has waited `nudge_after` since it was posted: 60 minutes unless set, **`0` turns nudges off**. The setting is the bot's, kept with its other settings in `bots.feishu` (the web app's and the iOS / Mac Lark bot pages have a picker for it, under "What it can do"; the Android page does not yet, so there it is set in the web app or through the API): `PUT /api/v1/bots/feishu` takes `nudge_after` (whole minutes, 0 to 8640, six days: the chat keeps a card's record seven days; a fraction, a string or a number out of range is a 400; absent leaves it), `GET` returns the value in force, and `feishu.status` carries it to the assistant. A card still not nudged a day after it was due (`nudge_after` plus 24 hours since it was posted) is let go. With no card kept, the sweep does nothing, not even asking the hub for the bot's status. Turning nudges on after they were off (`nudge_after` from 0 back to a number, seen by the sweep) does not catch up: the cards already due at that moment are let go, not nudged, so a backlog never arrives all at once; the moment nudges were first seen off is kept in the chat state, so a restart while they are off changes nothing. Shortening the wait (60 to 15) does nudge, at once, the cards that have waited between the two.
- **Once per card.** When the card was nudged is kept in the card's record in the chat state (`bots.feishu.state`, `nudged_at`), next to where the card is, so a restart does not nudge it again. The record is written before the nudge is sent, so a restart in between can lose a nudge but never doubles one. A send that fails for a reason that may pass is tried again in the next sweep under the same key (`uuid`, so one that did go out lands once), at most three sends in all and only within an hour of the first, because Feishu drops a repeated key only for about an hour; a refusal (the card or its chat is gone) is not tried again. A nudge given up, let go or refused is recorded apart from one sent (`nudge_skipped_at`): the board shows only a nudge that went out.
- **Not nudged.** A card that was answered anywhere (Lark, the App, the watch, the computer), dismissed, expired or withdrawn: its record is gone. One whose interaction the hub's queue no longer has pending, whose Agent is no longer in its computer's list, or that the queue cannot be asked about now (not restored after a restart yet) waits for a later sweep. The main conversation's `ask_user` card waits 2 hours (`askUserWait`), so the default 60 minutes reaches it; a Claude Code hook card still expires at 30 minutes, before the default nudge, and is asked again on the terminal.
- **Where.** A plain reply to the card in the owner's DM, which notifies by itself. In a topic group (`Topic group chats` above) the card's record keeps its group (`chat_id`; a card posted before this feature has none, so it is treated as a private chat card: a plain reply, no @), and the nudge goes in the topic (`chat_id`, `in_thread`) and @-mentions the owner at its start (`<at user_id="…"></at>` in the text message, Feishu's own syntax) so it reaches them. It is sent with `no_detour`: if the card was withdrawn, nothing is sent rather than a stray message.
- **What it says.** One line from the language files (`assistant-feishu_cards.nudge`, `nudge_permission`, `nudge_bare`; en, zh-Hans, ja): the first line of the question or the plan, cut to 100 characters. A permission card names the tool only, never the command, path or reason.
- **Quiet hours.** The hub's quiet hours (#5806, `hub/quiethours.go`) are set per device, so there is no one window. The assistant asks the hub (`notify.quiet`, `AppNotify`): quiet means **any device with quiet hours on is inside its window now**. The price: a device the user forgot, with a window on, holds nudges back during that window too. A nudge due then is not sent; the sweep of every minute sends it in the first minute after, once, if the card still waits (a card answered meanwhile is gone). If the hub cannot be asked, the nudge waits as well.
- **On the board.** With the waiting-for-you board on ("The waiting-for-you board" below), the row of a nudged card says "nudged" next to how long it has waited, and sending a nudge brings the board up to date like any other change.
- **Not built.** Urgent buzzing (Lark's urgent API) and the morning summary of deferred questions.

## Configuration and endpoints

```json
"bots": { "feishu": { "app_id": "cli_…", "app_secret": "…", "domain": "feishu" } }
```

The Lark app is one app used in two ways. The built-in bot uses its sealed App ID and secret for the long connection and bot messages. When `lark.cli` is configured without an explicit profile, the manager binds lark-cli's managed `persona` profile to that same App ID and keeps it synchronized when bot credentials change; lark-cli then provides the “read as me” user identity. An explicit `lark.cli.profile` remains an advanced compatibility override. The bot secret is passed to `lark-cli config init` on stdin and is never exposed in arguments, logs or status.

`domain`: `feishu` (default), `lark`, or the Open Platform address of a private deployment. Switches, features and pairing are configured in the App and stored in settings `bots.feishu` (read / written by the hub); chat state (current target, thread bindings, processed messages, and which message each still-open question / approval card is in: only ids and the conversation it belongs to, never the card's content, at most 100 cards for 7 days, #4358) is stored in `bots.feishu.state` (read / written by the assistant), and pending answers in `channels.state`.

These routes belong to the hub; `target` and `agents` in the response are queried from the assistant on demand (`feishu.view`). When the assistant isn't connected, these two fields are absent; everything else works as usual. `agents` is one row per Agent the owner has talked to in the chat — the threads bound to it folded together, the newest naming the row, newest first — not one row per thread: every card the bot posts about a conversation is bound to it so a reply finds it again, and the settings page shows the Agents, not the cards.

## What to do on the Open Platform

Nothing, when the app is created in one authorization ("Pairing and permissions"). For an app you create yourself:

1. Create an enterprise custom app and enable its **Bot** capability, and open the **Modify app info** permission (`application:application:patch`) once: with that, the rest below is done for you. When the App ID / App Secret are entered in the App, the manager configures the app through the Open Platform's server API (`feishubot/configure.go`): it opens the scopes and subscribes the events with the **long-connection** mode (`PATCH /application/v7/applications/:app_id/config`), then submits the publish, which creates the version when none is pending (`POST /application/v7/applications/:app_id/publish`). Best-effort and never blocks binding: a private deployment skips it, and a failure names the one switch left (the bot capability, the patch permission) with a link to the app's console page. The credentials step links out to the developer console; a rejected App ID / Secret is one sentence, not a code.
2. By hand (the app was not auto-configured, or a step is checked): permissions `im:message` (read / write direct messages), `im:message:send_as_bot`, `im:message.p2p_msg:readonly` (messages sent to the bot in a DM), `im:resource` (download images and files in messages); for `workbench`, `im:message.pins:write_only` and `im:message.pins:read` (pinning the home card; without them it stays unpinned and works otherwise); optional `contact:user.base:readonly` (names); for topic group chats one of `im:message.group_at_msg:readonly` (messages that @ the bot) and `im:message.group_msg` (all messages in the group, a sensitive permission, usually reviewed by the enterprise admin), "Topic group chats". The auto-configure opens `im:message:send_as_bot` and `contact:user.base:readonly` only: the rest are read scopes the platform lists for review, and group messaging stays the user's decision.
3. Events and callbacks: select **Receive events through a long connection** as the subscription method; subscribe to **Receive message v2.0** (`im.message.receive_v1`), optionally **User enters a chat with the bot** and **Message recalled** (`im.message.recalled_v1`: if the owner recalls a message before it is sent into the chat, it isn't sent, #4880; if already accepted and being answered, a turn answering only that message stops like /stop, changes its progress card to ‘Recalled, this turn stopped’, and sends no answer; if merged with other messages, only the recalled message is removed; already completed answers remain unchanged, #5248); subscribe to **Card interaction callback** (`card.action.trigger`). The auto-configure sets the mode and subscribes all four.
4. Publish a version (enterprises usually require admin review; a version already under review counts as done), then enter the App ID / App Secret in the App, enable it and pair.

## Task progress and review requests (#2768)

The owner only watches Lark, so the bot proactively sends updates on tasks (to-dos) dispatched from the main chat to the DM, without lark-cli or individual approvals on the phone (requested and authorized 2026-11-05). Sends only when something changes; no change, no message. Code: `server/internal/assistant/reports.go`, `acceptance.go`.

- **Goal level by default** (#3218, the owner, 2026-11-10: "I care whether the direction and the goal are met, not the execution"): with `report_steps` off (the default) a finished turn, an interruption, a closing by the judge and the stage moving on are execution steps and are not pushed; the stage is still kept for the apps. What goes out is a change of the goal: reached (the conclusion card below, or "Please verify" once deployed), waiting on the owner (the decision's own answerable card, with no report line around it) and stuck: the task did not start, or its turns were cut off 3 times in a row with no finished one between (told once; a finished turn starts the count again). A stuck task's card (🎯, red) has three lines per task: **🎯 Goal** (the title), **Now** ("stuck: did not start" / "stuck: cut off 3 times in a row"), **Evidence** (the error in a line and a link to the Agent's chat, else the task page); no stage bar, no Agent's words; up to 10 tasks, then a line counting the rest. The rest of this section is the card with `report_steps` on.
- **Coalescing**: changes within a minute (a turn finished, waiting for you, interrupted, failed to start, automatically marked done) are combined into one card; only the latest state of each task is kept. Check again before sending: don't report questions already answered or to-dos deleted; if a question card is already in the chat (`cards` / `all_cards`), don't repeat "waiting for you"; quiet tasks aren't reported when `sync` is on (the main chat's answer has already been synced), except "automatically marked done", which is still reported (the main chat doesn't mention that).
- **Card**: decisions needed go first (each followed by the usual question card so options can be tapped directly; cards already sent aren't duplicated), then a section per task: status, title, computer, stage bar
  Plan → Development → Review → Merged → Deployed → Verified (✅ completed, 🔵 current, ⚪ upcoming), the Agent's last words (first 300 characters), and buttons **Task page**, **PR**, **Agent chat** (web links; omitted if hub.json has no `public_url`). No bare IDs.
- **Stages** (`Todo.stage`, `Todo.pr_url`, stored in settings `assistant.todo_stages`, only advance): starting work is **Development**; a PR link in the reply means **Review**, also mentioning a merge means **Merged**; saying deployed / live means **Deployed** (doesn't count when preceded in the same clause by "还没" (not yet), "未" (not), "别" (don't), "无需" (no need), "等你确认后再" (after you confirm), "not yet", "will be", etc., or followed by "吗" (a Chinese question particle) or "yet"); saying tested successfully after deployment means **Verified**; tapping **Pass** on a review request also means **Verified**. The App's to-do detail draws the same stage bar from these two fields (#2776).
- **Deployed needs evidence** (#3205): a task reaches **Deployed** only when the running hub's commit contains its PR's merge commit; merged but not in the running hub, it stays **Merged** ("已合未上线", gate "等部署…"), with no review request, and moves on by itself once the deploy lands (`docs/assistant/todo-status-sop.md` "Deployed needs evidence").
- **Who verifies** (#3205): a deployed task is accepted by the supervising assistant by default (`by_assistant` on the ask, stage Verified, no card); only a big feature (a to-do with priority `high`) gets the review request below.
- **Review request**: as soon as a big feature reaches **Deployed**, send a three-line card: what changed (one sentence), where to look (a link straight to the page, only one present in a reply, the task page or Agent chat; never one invented by the model), how to check (what to tap, what to expect). A small model (purpose `inbox.judge`, prompts `prompts/assistant/acceptance*.md`) reads the task and replies to write these three lines; if the model isn't available, use the task title, task page and a generic check instruction.
  - Tap **Pass** or reply to the card with "通过" (pass; "没问题" (no problem), "OK", "LGTM" also count): mark the to-do **Verified**, and change the card to **Accepted**. When the hub cannot read the stored asks or save the acceptance, nothing is accepted and the stage does not move: the card button's toast and the web button (`POST /api/v1/todos/{id}/accept` answers 503) say the service is unavailable, never "already handled", and the same tap works once the store answers. A text reply says so only when the asks were read and the save failed: while the asks cannot be read the hub cannot tell the reply is about the card, so it is handled like any other message in the chat. A reply to a card of a round that is no longer the one waiting (an earlier round, or one handled meanwhile on another surface or by the card's own button) is answered "already handled", as that button is, and does not reach the Agent (#3836).
  - Any other reply: record it in the to-do's decision section (**Review feedback**) and send it to the original Agent to fix; deploying again after the fix triggers another review request.
  - Only the words of a reply go on (#5107). A reply that carries pictures or files is told they did not go to the Agent and to say in words what is wrong, or send the picture from the app: a picture alone gets just that line and the card still waits; a picture with words sends the words as above and adds the line to the receipt.
  - Each task gets one ask per round (stored in settings `assistant.acceptance`), kept whenever the work is deployed; the card is how it is shown in Lark, not what makes it. With the bot on and `reports` on, the ask has its card. With no card due (the bot off or not paired, or `reports` off) the ask is kept all the same, with `no_card: true` and no message id: the briefing's "To accept" section, the board and the snapshot list it, and the Accept button of the web `brief` item (`POST /api/v1/todos/{id}/accept`) verifies it like a tap on the card (stage Verified, the line in the to-do's topic, the report back to where the request came from). A card that failed to go out while the bot is on (the send failed or timed out, or the bot's status could not be read) is a different case: that is a card for later, not a card never due. The ask is kept without a message id and without `no_card`, listed meanwhile as a card-less one is, and every 10 minutes the sweep that sends the reminders tries its card again, under a key of that round's own (`uuid`), so a send that did land though its answer was lost is not posted twice. Feishu drops a repeated key only for about an hour, so the card is tried only within 45 minutes of the ask; after that, or when the sweep finds the bot off or `reports` off, the ask is marked `no_card` and stays card-less. The sweep follows the round rules below: it never posts an ask from before the to-do's latest reopen or one whose to-do ended, and drops it instead. A card-less ask gets no morning reminder card and is not posted after the bot is set up later; the next briefing lists it. Round rules are the same with or without a card: an ask made before the to-do's latest reopen is dead, and a to-do the owner closed or a review closed drops its ask. If not accepted the next day, mention it again in the morning brief ("waiting for user acceptance" in the snapshot, item 4 of the morning prompt), and send a **Not yet accepted** card at the morning-brief time (the time of scheduled task `morning` when enabled, 9:00 if disabled or deleted, in the user's time zone), once a day. With the morning briefing's `facts` on, the briefing card carries these instead and the reminders wait an hour; see "Morning and evening briefings" below.
- The switch is `reports`; when the bot is disabled or unpaired, nothing is sent and changes during that time are discarded (later cards describe the state at that later time). The "Please verify" ask is not one of those changes: it is kept without a card (see above).
- **The verdict on top**: the "Please verify" card's first line is its verdict, "✅ Done: deployed, check it below", the same line the briefing and the web `brief` item show for it (see "Conclusions").

## Conclusions (#1226)

The owner hands out many tasks and wants one thing of each: its conclusion. Code: `server/internal/assistant/conclusion.go`.

- **When**: the main conversation's review of a supervised task gives a result. `task_review accepted` sends a card that says **✅ Done** (`outcome: done`, the default) or **⛔ Cannot be done** (`outcome: cannot`: the work found the thing cannot be done; that is a result too). `task_review needs_user` sends **🤔 Needs your decision**, and so does a third rework, which goes to the owner (its reason then is "sent back 2 times and still not done; how should it go on?", not the rework meant for the Agent). Rework and cancel send nothing.
- **The card** (goal → now → evidence, #3218): **🎯 Goal** (the task's title), **Now**: the verdict and one sentence of why, and for a done or cannot-be-done one how far the work went out (from the done judge's delivery, else the stage: "live and checked", "live, not checked yet", "not live: stopped at a PR", "not live: merged, not deployed", "deployed, off by default", "nothing to ship"; nothing when not known), then **Evidence**: one link. In detail: the verdict and one sentence of why (`reason`; the first line of the review's note when it gave none) on one line, one link, a button. The link is the one the review gave (`link`, a web address); else the task's PR; else the first web address in the review's note and evidence; else the Agent's chat; else the task's page. "Needs your decision" adds the option the supervisor recommends (`recommend`).
- **Against what was asked** (#3822): under the goal, a done or cannot-be-done conclusion lists each criterion of the task's brief with how it ended (met, not met, not checked, dropped with the scope change), then what was done beyond the brief (`docs/assistant/unified-entry.md`, "Briefs"). Nothing for a task whose brief has no result, and nothing on a decision.
- **Answering**: **Got it**, or a reply "OK" (the same words as **Pass**), marks it seen; unlike **Pass** on deployed work it does not move the stage to Verified (the review closed the task already). On a decision, **Take the recommendation** or "OK" records the recommendation in the to-do's decisions and sends it to the task's Agent; any other reply is the owner's choice, recorded and sent the same way. Either way the task no longer waits for the owner (`needs_user` is cleared), so the Agent's next stop comes back to the supervisor as any stop does. A recommendation that could not reach the Agent is not taken and not recorded: a reply is told that nothing was changed, and why, the Lark button with an error toast, and the web button with an error (`POST /api/v1/todos/{id}/accept` answers 502); the button works again. Any other reply to a done or cannot-be-done card reopens the to-do and goes to its Agent, as feedback on "Please verify" does. A decision with nothing recommended has no button, and "OK" to it goes on as an answer.
- **One push**: the task's closing is not also a line of the task report. Deployed work keeps its "Please verify" card (with the verdict on top) and gets no second card when the review accepts it. A decision is its own card even then. A later conclusion of the same task replaces the one before, whose cards then answer "already handled"; rework or cancel ends a decision still waiting.
- **The supervisor's acceptance is the check** (#3240): the owner only decides, and looks at what truly needs their own eyes. A supervisor's (the main conversation's or a leader's) `task_review accepted`, made after checking the evidence, passes a "Please verify" still waiting (one from before deployed work was accepted by the assistant, #3205) for the owner: the to-do is **Verified** as if they had pressed **Pass**, the card's buttons give way to "the supervisor checked the evidence: marked verified" (`by_supervisor` on the ask). A done or cannot-be-done conclusion it sends is likewise already checked: it tells, it has no **Got it**, and the briefing does not list it. When the hub starts and every 10 minutes a sweep passes the asks left waiting on tasks their supervisor accepted. The owner is still asked when the review sets `user_check` (a UI change someone has to see: a "Please verify" card is posted and waits for **Pass**, also when the deployed work was accepted by the assistant before), for a big feature (to-do priority `high`, #3205), or when the task has no supervisor. A task the done judge closed after its spot check (`by: judge`, #3356) counts as checked the same way: its conclusion is told, not left for **Got it**, unless it is a big feature.
- **Kept like "Please verify"**: the conclusion is the to-do's ask in `assistant.acceptance` (`conclusion`, `outcome`, `reason`, `recommend`), with a card or without (`no_card`), retried the same way. The briefing's "To verify" section, its Lark card, the web `brief` item, the board and the snapshot list it with the same verdict line. It is not posted again the next morning, and it does not expire: the briefing lists a done or cannot-be-done conclusion the owner is to acknowledge (a big feature's) until they press **Got it** (or reply "OK"). A decision stops being listed once the to-do is closed or no longer waits for the owner.
- **A decision that can wait** (#4930): a `needs_user` review marked `can_wait` gets no card and no push when it is raised; the next briefing lists it, and its card goes out later only if it had to be pushed because no briefing reached the owner with it (`docs/assistant/todos.md`, "Decisions that can wait").
- **Not covered**: tasks nobody supervises (closed by the hub's judge) end with the task report's closed line only with `report_steps` on; by default their closing is not pushed (it is no goal-level result: nobody checked it); Android draws no `brief` item yet.

## The waiting-for-you board (#6052)

With `board` on, `/tasks` (and `/进展`, `/总览`) keeps one standing card in the owner's private chat that lists everything waiting for them, and edits that card in place instead of sending a snapshot each time. Code: `server/internal/assistant/feishu_board.go`. With `board` off nothing changes: `/tasks` sends its snapshot every time and the board is never made or edited.

- **One card, edited.** The first `/tasks` sends the board as a message of its own and remembers its message id and the time it was sent (`board` in the chat's state, `bots.feishu.state`). Every later `/tasks` edits that message and replies with one short line, "Updated, it is the card above", as a reply to the board (Feishu shows the quoted board in the reply, and tapping it jumps there; Feishu has no link to a message). A new board is sent only when the old one can no longer be edited: it is older than 14 days (Feishu's edit period, counted from when it was sent; no edit is tried), or an edit fails with an answer that will not change: deleted or withdrawn (230110 / 230011), past the edit period (230031, "Update sent message card" in Feishu's docs), not a card (a card Feishu refused went out as rich text, and its id is a text message's), or any other Feishu refusal. Only a passing failure keeps the board as it is: no answer at all (the network, a timeout, the connection to the hub), a rate limit (230020), a server error (5xx) or a token that had to be renewed; then `/tasks` answers with the snapshot as it does with the switch off. The new board goes out under a key made of the old one, so a send that timed out and is tried again is still one message, and it is remembered and is the board from then on. Writes are one at a time, so two `/tasks`, or `/tasks` and the timer, make one board. A new pairing starts the chat's state afresh, and the board with it.
- **Kept current.** Once there is a board, it is edited about 3 seconds after any of these (changes that come within those seconds are one edit; nothing is scheduled while the chat has no board): a card opens or ends (`interaction.announced` / `interaction.ended`: answered anywhere, dismissed, expired, its Agent gone), a to-do enters or leaves "Please verify" (its card goes out, it is passed, it is closed, reopened or deleted), and once when the assistant has connected to the hub and read the cards that are pending (a restart of either); before that read, nothing is written, because the list is empty only for being unread. With the switch turned off, or the bot unpaired, nothing is edited, and the to-dos changing do not ask for the bot's status more than once a minute. A bot paired again is a new chat: the old owner's board is forgotten, not edited.
- **The rows.** Each row is a short number, one sentence, how long it has waited ("2 min", "1 h 20 min", "3 d"), who asked (Persona, or the Agent by its title), and a link to the conversation or the to-do on the web app (left out when hub.json has no `public_url`). The sentence is the card's question, clipped (a plan: "Approve the plan"; a to-do waiting to be verified: "Please verify: <title>"). A permission card says only "Needs your approval", never the command, the path or the tool, and a terminal dialog only "Needs you": the board sits in a chat that may be seen in a screenshot. Order: the cards that hold up an Agent first, the longest waiting first, then the to-dos waiting for you to verify them, the longest waiting first. A card that has ended is not listed even while its entry is still being taken away.
- **Waiting times do not tick.** How long a row has waited is written when the board is, so it does not move between two updates: go by the "Updated" note at the bottom. The board goes only to the private chat; a card raised in a topic of a group shows on it as a row with a link to the web app, and the topic keeps the card itself.
- **Nothing waiting.** The board says "Nothing is waiting for you right now" and stays; a note under the rows says when it was last written.
- **One card.** At most 30 rows, and as many as fit the card's size limit; the rest, the last in the order above, are counted ("and N more, see the web app").
- **Switch.** `board` in the bot's features, next to `cards`, `reports` and `pushes`. The web settings page and the channel page (Android, and the channel list in the Apple apps) draw it from the lists they have: the channel page's list is the manager's (`GET /api/v1/channels`), the web page's is its own. The iOS / Mac Lark bot page lists its switches itself and shows it under "What it can do" when the hub's answer has it (a hub from before leaves it out, and the page shows no switch); it sends it with the other switches, and when the hub did not send it, it sends nothing of it.

## The workbench (#1961)

For people whose front end is Lark rather than the app. With the `workbench` switch on, the standing board below is drawn as a home page and kept where the owner finds it. Code: `server/internal/assistant/feishu_workbench.go` (the cards, the commands, the Inbox actions), `feishu_workbench_pin.go` (pinning, the button on every card), `feishu_companions.go` (companion bots).

- **The home card.** Where messages go now; what waits for the owner, as the board lists it (the first three, each holding an Agent up with an **Answer** button that withdraws its card and posts it again at the bottom of the chat); the agents at work (the first three, each with **Chat here**); the Inbox (what needs the owner, what is only to know, the first two items); the next meeting; how many computers are online; buttons for the main chat, a new chat, `/agents`, `/start`, Today, Tasks, the Inbox and Refresh; and a link to each companion bot. The `main` and `agents` switches still decide which of those buttons are there.
- **One, pinned.** `/home`, the **Workbench** button of any card, or `POST /api/v1/assistant/feishu/workbench` posts a fresh home card at the bottom of the chat, pins it (`feishu.pin` with `exclusive`: the bot's other pins in the chat come off, the owner's own stay) and withdraws the one before (`feishu.recall`); one too old for Lark to withdraw is redrawn as a line that says the workbench moved. The card is the board from then on (`botState.Board`), so it is edited in place as the board is, and a home card that can no longer be edited is replaced by a new one, pinned in its place.
- **Kept current.** Besides the board's own triggers (a card opening or ending, a to-do entering or leaving "Please verify"), the pinned card is looked at every minute while the switch is on, and edited only when what it shows changed (the "updated at" note does not count). With `board` off as well, `/tasks` stays the snapshot it always was; with both on, `/tasks` edits the home card and points to it.
- **A way back from every card.** Every card the bot posts or redraws gets a **Workbench** button (not one that has workbench buttons already, and not one near the card size limit). The button follows the switch as last read (each feature read updates it), so it stops with the switch. When the last row already contains only `open_url` navigation (a mirrored answer's **Open on web**), Workbench joins that `flow` row instead of making a second navigation row; approval, form and other callback action rows stay independent. Narrow clients wrap the same row without changing either action (#5317).
- **`/today`.** The main conversation's Today (the one the app shows: waiting, meetings, done overnight, what did not go through, Lark chats that @ the owner), the questions and approvals waiting, the Inbox items that need the owner, and a "right now" line.
- **`/inbox`.** The open Inbox without its noise, what needs the owner first (at most six, the rest counted), each with **Done**, **AI draft** (when a reply can be sent to its source) and **Mute sender** (when it has someone to mute). Done and Mute redraw the card in place. AI draft posts a draft card under it (the model takes longer than Lark's 3-second callback): the draft to edit, a line of what to change, **Send as me** and **Redraft**. Sending is the app's reply (`replyInboxFrom`, the draft card's message as the send's id, so a double press sends once and a press after the item was filed changes nothing); the draft card turns green with what was sent, and the Inbox card is redrawn.
- **`/start`.** A permission field before "what to do", offering `proto.PermissionModes`; none keeps the launcher's own mode (the agent's `session.start` gets no `permission_mode`).
- **Switched off.** None of it: the commands go on as text, no card gets the button, `/start` has no permission field, nothing is pinned, the companions are not linked and the notices go to the chat. The home card already in the chat stays as it was.

### Companion bots

An extension can run other Lark bots for the owner (an Inbox bot, a notifications bot) next to this one. The hub knows nothing of them: the extension registers them with the assistant, which links them from the home card and, while one polls, hands it the notices. All four routes are for full credentials only (an extension with `hub_api`); none has an extension scope yet.

- **Registering.** `PUT /api/v1/assistant/feishu/companions {bots: [{kind, name, icon, app_id}]}` replaces the list (at most six; `kind` is `inbox`, `notify` or `other`; `name` at most 20 characters; `app_id` a `cli_` app id); `{bots: []}` removes them. They are kept in the chat's state, so a new pairing starts without them: an extension registers again when it starts and from time to time. Each is a link button on the home card (`https://applink.feishu.cn/client/bot/open?appId=…`, which opens the chat in the Lark apps; the web client may not follow it). An `inbox` companion's button, with the count of what needs the owner, replaces the home card's `/inbox` button.
- **Notices.** While the workbench is on, a `notify` companion is registered and it polled in the last 90 seconds, these go to it instead of the chat: `notify_user` pushes (`push`), a scheduled task's own conversation's answers (`task`) and the task progress cards (`report`). The main conversation's turns, the agents' finished cards, questions, approvals, plans, a decision's own answerable card, "Please verify" and conclusions stay in the chat: they answer for the owner or are answered by a reply there. The companion long-polls `GET /api/v1/assistant/feishu/notices?boot=&after=&wait=` (`wait` at most 50 seconds) → `{boot, notices: [{seq, kind, card, text, at}]}`, `card` the bot's Card 2.0 JSON and `text` its fallback; `boot` changes when the assistant restarts (a poll with another one starts from the beginning). Notices are kept in memory, the last 200. A companion that stops polling gives them back to the chat after 90 seconds.
- **Presses.** A notice's button pressed in the companion's chat (the companion checks it is the owner's) is relayed to `POST /api/v1/assistant/feishu/notices/action` with the card callback's event; only what needs no owner's action is taken (`accept`, a workbench button), and anything else answers with a toast to answer it in the bot's chat, where the cards carry the owner's action.

## Morning and evening briefings (`facts`)

With a scheduled task's `facts` setting on, its run has a part Persona fixes and computes, and the model only writes a sentence or two on top. It is on for the default morning and evening routines of a new hub; on a hub set up before it is turned on only for a routine that still holds an earlier default prompt, which is replaced by the current one (`upgradeDefaultRoutines`). A routine whose prompt was edited keeps `facts` off and behaves as before. The setting is the task's `facts` field (`PUT /api/v1/assistant/tasks/{id}` sets it only when the body has it, so an app that does not know it leaves it as it is). Code: `server/internal/assistant/briefing.go`, `briefing_card.go`.

- **Computed once, when the run starts.** The card, the push and the facts the model is given (they head the message that starts the run) all come from that one computation, so their numbers agree. Right after a restart the cards waiting for an answer are not read yet: the run waits up to 20 seconds for them, and if they still are not there the briefing says so instead of saying nothing waits. The routine's own earlier failed attempt (this run is its retry) is not listed. The card is made only for the turn the run started and only when it ended normally; a message the owner sends into the routine's conversation later, or a turn that stopped on an error, is mirrored as any other answer.
- **Waiting for you.** The standing board's rows that hold an Agent up, as `boardRows` gives them: how long, who asked, a link, and "nudged" for a card the bot nudged under.
- **Last 12 hours.** What did not go through is listed before what finished, so a long list of finished to-dos does not push it out. To-dos closed in the 12 hours before the run (those still waiting to be verified are listed only as such), and what did not go through: to-dos whose Agent did not start, and scheduled runs that failed or were skipped (`todayFailures`, the same data as the Today card).
- **To verify.** The board's "Please verify" rows and conclusions waiting for the owner, each with its verdict line (word for word as its own card), what changed (deployed work) or the recommended option (a decision), and a button: **Accept** for deployed work, **Got it** for a conclusion, **Take the recommendation** for a decision (none when nothing is recommended). A decision its supervisor marked `can_wait` got no push and no card when it was raised and is first put to the owner here; a card that has no room for its row leaves it held (`docs/assistant/todos.md`, "Decisions that can wait").
- **Can wait.** The questions Agents left for a briefing (see "Questions that can wait" below), the oldest first, at most 10 and the rest counted, each with what was asked, who asked, how long ago, a link to the Agent's chat and a **Handled** button. After "To verify" and before "In progress"; left out when the queue is empty.
- **In progress.** The open to-dos whose Agents are working, the longest open first, each with its stage bar (plan → develop → review → merge → deploy → verify) and a link; at most 8, the rest counted. It comes last and is left out when nothing is running.
- **Inbox follow-ups, for the model only.** Up to five matters waiting on the other side (state key `waiting`) for more than 24 hours (`handling.since`), and up to five coming due today: `follow.check_at` in the owner's today, or the state key `follow_up_ask` / `check_due` whatever the date; each with its title, who or what it waits on and next step. The model includes them even when a card carries the other facts. These rows are not added to the card, the apps' `brief` item or the push counts. Computing them never advances a check, rewrites a follow or changes an item's state.
- **Recommended setup.** The first briefing of a week that reaches the owner (its run ends normally) carries one more section when the numbers name something: which mechanism that is off (the assistant answering agents' questions, standing authorizations, starting directly, the triage's actions, leader conversations, spot-check reviews, independent review) would have removed how many of the last 7 days' asks or background rounds, its cost in one sentence, and where it is turned on; and, when the background supervisor's reviews held on a provider that has a lower tier, one line saying so (#5805). It is computed like the rest and drawn on the Lark card and on the web app's briefing card, each mechanism is named at most once in 30 days, and nothing is turned on (`docs/assistant/assistant.md` ("Recommended setup")). There is no weekly routine; this is where the weekly block goes.
- **In the apps.** Whether or not the Lark bot is on, a `brief` item with the same rows is written into the routine's own conversation when a run is sent (`docs/protocol/protocol.md` ("Tasks and the chat feed")). The web app and the iPhone and iPad app (#2320, `docs/apple/ios.md` ("Briefing card")) draw it with an **Accept** button per task to verify (`POST /api/v1/todos/{id}/accept`, which holds to the same round check as the Lark button) and a **Handled** button per question that can wait (`POST /api/v1/later/{id}/handled`); Android does not know the kind yet and skips it. A waiting card's row and a question's row name the chat they came from (`machine_id` / `session_id`), which the apps open. The tasks to verify come from the "Please verify" asks, which are kept whether or not a Lark card went out, so the section is the same without the bot. When the Lark card is not going out (bot off, or `pushes` off) the model is told so and lists the rows itself, in the same order, from the same numbers, which keeps Android whole until it draws the item.
- **Accept on the card.** The button carries the time the "Please verify" ask of that round was made (`asked_at`; the ask of a to-do without a card has one too). It verifies the to-do only while that is still the round waiting, so the button of an earlier card does not verify a later round (#4853); it answers "already handled" instead.
- **No second reminder that day.** Once the briefing card is out, the to-dos it listed with an Accept button are not asked again by the morning reminder (`RemindedAt` is set). When the morning routine has `facts` on, is due that day and its card can go out (the Lark bot is on with `pushes`), that reminder waits until an hour after the routine's time (never past midnight); if the briefing has not gone out by then, the reminders go one by one as before. To-dos the card did not fit ("and N more") are reminded as before.
- **The push** says the counts instead of the first words of the model's answer: "waiting for you 3 · not through 1 · done 2 · to verify 2 · can wait 2". Only the turn a scheduled run started says them; a turn that failed, was cut off or asks a question, and a health conversation, are pushed as before.

## Questions that can wait (`urgent: false`)

An Agent working on a supervised to-do can say a question does not hold it up: `report_to_supervisor` with `kind: "question"` and `urgent: false` (#6287). Its other ways to ask stop it until the owner answers (its own question tool, a permission, a plan) or start a turn of the main conversation (`report_to_supervisor`, urgent). This one waits for the next morning or evening briefing. Code: `server/internal/assistant/later.go`, `agent_control.go`.

- **What happens.** No supervision signal (so no extra turn of the main conversation), no card and no push. The question is written into the supervisor's conversation as a `report` item marked `later` (the web app draws it quietly, with the mark), and an entry goes into the queue kept in settings `assistant.later`: id, to-do, machine and session, the text (clipped to 2000 characters as any report), `asked_at`. The queue survives a hub restart. At most 100 entries; beyond that, and whenever the queue can't be read or written, the question is sent as an urgent one. The same question of the same Agent that is in the queue already is not put in again (the answer says so). The report rate limit (10 in 10 minutes per session) counts these too.
- **Only when a briefing will list it.** If no daily routine with `facts` on is enabled (the default morning one, or the evening one), `urgent: false` is ignored and the report is sent as an urgent question; the tool's answer says which happened. `urgent` on any other kind has no effect and the answer says so. Missing or `true` changes nothing.
- **Leaving the queue.** Only three ways: the owner marks it handled (the **Handled** button of the `brief` item in the web app or on iPhone and iPad, Lark **Handled** button on the briefing card), its to-do ends (closed or deleted), or 7 days pass. Handled on an Agent's question only takes it out of the queue: its supervised to-do stays open and its Agent is not told. Persona does not guess from the chat that a question was answered. A question that left without an answer is not asked again. Entries that are over are dropped when the queue is next looked at (a briefing, a press of Handled, a new question); a Handled press on one that is over answers "already handled".
- **Not on the board, no nudge.** The standing board (#6052) does not list these, and the card nudge (#6084) does not apply: nothing is held up by them. They are in no push either, except as a count in the briefing's push text.
- **What a row says.** The question (the first 160 characters), who asked (the Agent by its title; one that is gone, or has none, by its to-do), how long ago, and a link to the Agent's chat. The evidence the Agent sent is only in the `report` line in the supervisor's conversation.
- **The assistant's own questions too.** An `ask_user` of the assistant's that expires unanswered becomes a to-do (`docs/assistant/todos.md`, "Questions nobody answered", #1617) and goes into the same queue, the asking conversation as who asked; it leaves the queue the same ways (its to-do is closed once the owner decides). Handled on its row ends the question too (#1854): the to-do is closed first, as closing it in the to-do list does, so the asking conversation is told once that it was dropped; if the to-do can't be closed, the press fails and the row stays.
- **Supervisors' decisions wait the same way, in their own place.** A `needs_user` decision a supervisor marked `can_wait` is not in this queue: it stays the to-do's ask and the briefing lists it under "To verify", where it is answered. It counts on the same routines and, unlike a question here, is held only when one of them is due in time, and is pushed after all when no briefing reached the owner with it (`docs/assistant/todos.md`, "Decisions that can wait").
- **In the briefing.** Every briefing run with `facts` on lists the whole queue, so a question stays in the next briefings until it is handled, ends or expires. The model is told how many there are and not to list them again. Without the Lark bot the section is only in the `brief` item, which the web app and the iPhone and iPad app draw.
