# Lessons: Paseo engine (`integrations/paseo`)

Read before changing the bridge (`integrations/paseo`), its node runner (`node/paseobridge.go`), or testing real Paseo. Design: docs/integrations/paseo.md.

- **Connect only to the address in home's `paseo.pid`, never default-port fallback** (2026-11-04). Paseo writes PID file immediately with listen:null; fills address after listening. Earlier fallback `PASEO_LISTEN` / `127.0.0.1:6767` connected a temporary-daemon prototype to the live local Paseo and sent agent.create. Missing provider made it fail, leaving only failed `creations/` record.
  - Bridge / node detection now trust PID-file address only, like Paseo CLI.
  - Before temporary-daemon requests, verify `daemonTarget(home)` port equals assigned port.
- **Claude Code `ExitPlanMode` permission passed to Paseo lacks plan body** (tested 2.1.294). Input {}, no metadata.planText. Plan in corresponding timeline tool call `detail.type: "plan"` and transcript tool_use.input.plan. Bridge finds via metadata.toolUseId.
- **Pending requests in Agent snapshots are trimmed**: `sanitizePendingPermissions` drops empty input. `agent_permission_request` event more complete, but either arrives first; never assume input present.
- **Read-only Bash does not request Claude permission**, e.g. echo / ls. E2E approval card needs writing command, e.g. touch.
- **New Paseo 0.14 Claude Agent `runtimeInfo.sessionId` null**, Claude ID appears only after first turn starts. Persona-created sessions use `paseo-<agent id>` stored `persona.session` label; waiting for Claude ID would change identity mid-run.
- **Provider models await warmup**: `get_providers_snapshot` immediately loading; `providers_snapshot_update` after ~1 second. First hello launchers may lack models; bridge rechecks while providers loading.
- **Send reply waits until turn actually starts**, Paseo max 60 seconds, node runtime timeout 30. Loading closed Agent may take longer; bridge waits max 25 then treats as handed to Paseo. Creation same.
- **Subscription event can arrive in same read as reply**: `fetch_agents` reply immediately followed by directory update. Register synchronously while handling reply, not after await, or lose events. Reply also `subscriptionId`, so route `requestId` replies before `subscriptionId` events.
- **Reading closed-Agent timeline loads it** from persistence. Skip closed Agents when fetching list last-text; read only when phone opens chat.
- **Paseo's `config.mcpServers` entries need `type: "stdio"`** (0.13.2 schema), which Claude-style `mcp.json` entries omit. The bridge adds it and sets each server's `PERSONA_SESSION_ID` to the Agent's `persona.session` label (#3655); the provider's own session id would break the task link.
- **A provider that takes no MCP servers fails `agent.create` when `config.mcpServers` is set** (0.13.2 `requireExternalMcpSupport`: `Provider '<name>' does not support MCP servers`, an `error` on the response, before any Agent is registered). Paseo keeps a record of each creation request under `creations/`, and the failed one stays; the bridge's one retry without `mcpServers` simply uses a new Paseo agent ID, and only for that message. The Persona session ID must not change with it: the start may already have returned its row (a refusal later than the 25 s wait), so label and `PERSONA_SESSION_ID` stay the first request's. The fake daemon (`test/fake-paseo.js`) refuses MCP servers for `noMcpProviders` (slowly with `refuseDelay`) and checks the stdio shape Paseo's schema needs.
- **A Paseo workspace is not a tab** (#4493). A slot is one tab, and the apps draw the sessions that share a `slot_id` as that tab's panes: one row for all of them, a pane strip in the chat, a stopped one shown as replaced by another. A workspace's agents are separate conversations, any number of them: on one real machine a workspace had 78, of which 72 were created by other agents, and all 78 were one row. Send the workspace's title as `slot_name` and no `slot_id`.
- **An agent another agent created is quiet in Paseo and loud as a plain session** (#4494, Paseo 0.14). Paseo labels it `paseo.parent-agent-id`, shows it under its creator in the same workspace, archives it with its creator, and notifies nobody when it stops (`broadcastAgentAttention` returns early for it). It still sets `requiresAttention` on it, which only opening the agent in Paseo clears. Listed as an ordinary session, each one was a "done" push and a lasting Unread.
  - The workspace status follows `resolveWorkspaceRootAgent`, not the label alone: one created from another workspace is that workspace's own agent and its attention counts; one whose creator is gone, and a ring of creators, show nowhere.
  - A list that keeps only the agents whose direct creator is one of the user's own drops an agent two levels down, even while it waits for a permission. The node refuses a card for a session it was not told of, so that request never reached the phone. Follow the whole line of creators, and test with a fake node that refuses cards for unlisted sessions (`startFakeNode(t, { strict: true })`).
  - A creator Paseo closed (`closed`: it let the process go) while its agents run is not "offline" for a list of what runs: their reports wake it.
- **Paseo 0.14 runs Claude Code's command line itself** (#4521). Every transcript of its agents says `entrypoint: sdk-cli` from the first line to the last, as a script's `claude -p` run does, not `sdk-ts` as a host on the Agent SDK writes. Nothing in the transcript tells the two apart; only Paseo's agent records do. A filter written from what one host writes (#3931: "interactive hosts run through the Agent SDKs") hid the conversations of every archived Paseo agent. When a rule keys on what a program writes into a transcript, check what the other hosts write.
- **Paseo's removal of an agent from its list does not say why.** `agent_update {kind: "remove"}` is the same for an archive, a delete and an agent that only stopped matching the list (its provider switched off). `fetch_agent_request` tells them apart: an archived agent's record comes back with `archivedAt`, a deleted one is `agent: null`. Ask only about an agent that was listed: a removal also comes for every change of an agent the list never had (Paseo's internal agents, which name the others: a dozen removals for each agent started with a prompt), and an archive is told twice. Archiving an agent archives the agents it created in its workspace too (`cascadeArchiveChildren`); a delete does not cascade.
- **Paseo tells a delete only to the client that asked for it** (#4629, Paseo 0.14). `handleDeleteAgentRequest` sends `agent_deleted` and the list's `remove` to its own session. Every other client sees one last upsert with `status: "closed"` when the agent was loaded (the delete closes it first, and removes its record a moment later), and nothing at all when it was not. A list kept from updates alone keeps a deleted agent until it reconnects: ask for the agent after one closes, and compare with the directory now and then. A fake daemon that announces a delete to every list hides this; the end-to-end check deletes through a second client.
- **`fetch_agents_request` with `filter.includeArchived` lists archived agents among the live ones**, in the order asked for; an archive sets `updatedAt` to `archivedAt`. So "archived lately" is read newest first until a page ends before the window, not by a fixed number of pages.
- **An id the transcript does not carry is lost when the session is listed as its transcript** (#4771). A session Persona starts in Paseo is `paseo-<agent id>`, chosen before Claude Code has a session id. Named to the node as an archived agent's transcript (#4521), it came back under the Claude session id: a second id for one conversation, and the to-do link, pin, archive mark and read state kept under the first one were left behind. The node lists a named transcript under the transcript's id, and nothing in the transcript says otherwise. A session with an id of its own stays the runtime's row (`offline`, with `transcript`) while it is archived.
- **What Paseo 0.14 does with an archived agent.** `send_agent_message_request` takes it back from the archive first, then loads and runs it (`sendPromptToAgent`, `unarchive` on by default), its labels untouched. `import_agent_request` for a Claude session an archived agent has restores that agent rather than making another, found by `persistence.provider` and session, and writes the request's labels over its own: a takeover that sends the transcript's id as `persona.session` renames the session. `set_agent_mode_request` and `set_agent_thinking_request` refuse it (`ensureUnarchivedAgentLoaded`); `fetch_agent_timeline_request` loads it without restoring it; `update_agent_request` renames its stored record and tells no list (the directory lists only agents Paseo has).
- **Paseo tells the list of an archive before it answers the archive request** (`archiveAgentForClose` emits the stored record, then `agent_archived`). By the time the bridge has the answer, the list's `remove` has taken the agent's copy away: anything wanted from it (its placement) is read before the request is sent.
- **Retaining an archived Codex row also needs the archive ledger** (#5129). Extending `archivedUnderOwnId` alone leaves `noteArchived` dropping agents without a Claude transcript. Keep Persona-labelled Codex agents with a known thread, deduplicate their threads separately from Claude transcripts, and never put their IDs in `unlisted_transcripts`. Otherwise two archived Codex agents collapse into one because both have an absent transcript. Exercise archive, reconnect and restore through the bridge, with an unlabelled Paseo-originated agent as the negative control.
- **Paseo's workspaces are followed like its agents, and its answer to a creation is thinner than its update** (#6295, Paseo 0.14). `fetch_workspaces_request {subscribe: {}, page}` lists them and sends `workspace_update` (`upsert` / `remove`); a workspace's status moves with every turn of its agents, so tell the node only when the rows it lists change. `workspace.create.request` answers with a descriptor that has no `project` yet (no placement until Paseo's next update of it): keep the subscription's richer upsert when it came first, and find a just-made worktree by its `workspaceKind` and folder, not by its placement.
- **Create a worktree workspace without an agent** (#6295). With `agent` in the same request Paseo renames a new branch after the first prompt, asynchronously, so the branch the node checked and reported is not the one that stays. And `action: "checkout"` with a branch another worktree has checked out does not fail: Paseo makes another branch of it, so refuse such a branch before asking (`git worktree list --porcelain`), as for Orca.
- **A stale workspace id must be refused, not dropped** (#6295). Paseo files a worktree folder handed to it alone under a project record of its own: a start that drops a workspace id Paseo no longer has puts the agent in a new workspace somewhere else. A workspace Paseo still has, agents in it or not, is a valid target.
- **A Paseo workspace id where a terminal host's used to be** (#6295). Session rows now carry Paseo's `workspace_id` (`wks_…`), and "Open terminal here" and the preview's Start sent it to herdr. The node maps a runtime's workspace to the terminal engine's space that holds the folder, else a new one there (`newShell`, `preview.start`; the first space by id was an unrelated one), and the web and iOS offer Start only for sessions with a terminal.
- **Paseo renames the folder it is asked for, and steps around anything there** (#6295 review, Paseo 0.14 `createWorktree`, `slugify`). The
  requested name is slugified (lowercase, `[^a-z0-9]+` to `-`, at most 50 characters, cut at the last hyphen past the 25th), and when anything
  exists at `<root>/<slug>`, an empty folder too, it makes `<slug>-1`, `-2`… instead. A node check on the typed name or on "empty is fine" passes
  and the worktree lands elsewhere: check the slug's folder (`runtimeFolderName`, its test cases are Paseo's own answers) and refuse anything
  there. Long agent names lose their `-10` to the 50-character cut and land on the base folder: shorten the name, not the number.
- **One deadline for a create that asks twice** (#6295 review). prepare (30 s) and create (up to 140 s) each inside the hub's 150 s still add up
  past it, and the user then sees the hub's timeout while Paseo goes on. Bound the whole operation once (145 s) and say when it ran out.
- **Paseo's archive removes the folder whatever runs in it** (#6297 review; Paseo 0.14 `archiveByScope`). It archives the
  workspace's agents, running ones too, kills its terminals and force-removes the worktree, with a herdr Agent `cd`'d into it as
  well; when the disk removal fails it only logs it (`removedDirectory: false`) and still succeeds. So the node checks, at the
  preview and again at the confirmation, that no session of the workspace is at work and no Agent of any engine runs in the
  folder, and judges the outcome by the list and the disk, never the answer.
- **Where Paseo puts a repository's worktrees** (#6295, Paseo 0.14 `deriveWorktreeProjectHash`): `<worktrees root>/<hash>/<slug>`, the hash the first 8 base-36 characters of a SHA-256 of the repository's real path, the root `worktrees.root` in its `config.json` or `<home>/worktrees`. Prefer the folder of a worktree Paseo already made of the repository; the derived one is only what the dialog shows first, and the answer names where the worktree really is.
- **Archiving a worktree workspace in Paseo deletes its folder, forced** (#6297, Paseo 0.14 `archiveByScope`, `deletePaseoWorktree`). `archive_workspace_request` archives the workspace's agents and record, then, for a worktree Paseo made and no other workspace uses, removes it with `git worktree remove --force` and a recursive delete: uncommitted work goes, the branch stays. A main checkout, a folder or a worktree made elsewhere is only archived, its folder left. So the node shows the changes and has the user confirm them before it asks, and refuses anything Paseo did not make. Paseo answers `archivedAt` even when the disk removal failed (it only logs it): check the folder before calling it deleted.
- **A project rename reaches the workspaces, not the agents** (#6297). `project.rename.request` sets the project's `customName` and sends its workspaces' descriptors again, with the new `projectName`; agents keep the placement of their last update. The bridge names a space by vote over agents' and workspaces' placements, so the old name would win until each agent changes: update the placements the bridge keeps when Paseo accepts. `workspace.title.set.request` is the same for a workspace's `workspaceName`. An empty name clears the custom one (Paseo's derived name comes back), so never send one.
- **Android names a space by its session's workspace** (#6297). Its Rename space sends `workspace_id`, which for a Paseo session is now the workspace's (`wks_…`), not the project's: the node takes a runtime workspace id to the space it is in, and the hub finds the old name (for pins, mutes and to-do links) from the runtime session in that workspace.
- **Paseo forks an agent's Claude session when it goes on after an API error** (#6709, Paseo 0.14, Claude Code 2.1.294). A turn the model never answered (a gateway's 499, for instance) is dropped before the next message: Paseo rewinds it with the Agent SDK's `forkSession`, at the last answered turn, into a new transcript beside the old one. The agent's `persistence.sessionId` moves to the fork, and every record the fork copied ends with `forkedFrom: {sessionId, messageUuid}` (the last key of the line, after the message, so a prefix of the line does not show it). On one machine, an agent that hit the error four times left five transcripts in one project folder.
  - An id keyed on the current Claude session moves with each retry. The open chat answered 409 ("no such session"). Each failed turn's "needs you" card stayed under an id nothing listed: "Fixed, go on" could not reach it and put it up again under a new id, and only the card's 24 hours ended it. Paseo's own rewind is no different from Persona's, which #6293 already guarded with the label. The bridge now keeps the id on any move it sees, and follows `forkedFrom` for moves it missed.
  - A fork's records keep their original timestamps, so the first record of every transcript in the line is when the conversation began. That is how the bridge tells an agent's own line (begun after the agent was created) from a conversation handed over from another agent: Paseo plugins that move a conversation to another provider fork the previous agent's session into a new agent. Never follow such a line into another agent's session.
  - The manager now withdraws a card whose session stays missing from its online computer's list, and one whose answer the computer refuses as `not_found`. A card can only end that way while the session is gone for good. An engine that is merely away (its bridge leaves the node after 30 seconds) also takes its sessions off the list, which is why the manager waits 10 minutes first.
- **ACP providers approve through a switch, and Grok names its tools in its input** (#7758, Paseo 0.14, Grok CLI 1.0). A provider Paseo runs over ACP (`extends: "acp"`, such as Grok's `grok agent stdio`, and Copilot or Cursor) lists no permission modes, or only its own; what decides whether it asks is Paseo's Auto Accept feature (`features[].id === "auto_accept"`, set at creation with `config.featureValues` and later with `set_agent_feature_request`). OpenCode has the same switch. A mode sent to such an agent does nothing, so Allow all has to go through the switch, and the switch being off proves nothing: Grok's own always-approve setting answers its prompts before they reach Paseo. A closed agent's snapshot lists no features at all; Paseo loads the agent before it sets one.
  - Grok's ACP raw input carries its own tool's name as `variant` (`ListDir`, `Monitor`, `TaskOutput`, `KillTask`, `UseTool` for an MCP call). Paseo passes such a call on as an `unknown` detail named `other` or after the ACP title (``List `/w` ``), its output Grok's own object (`{type, Content: {content}}`, `{type, Result: {...}}`, `{type: "MCP", output: {OkayOutput}}`). Read the name from `variant`, never from the item's name. Grok's tool search arrives as `plain_text` titled `Search tools: "<query>"`, with no input at all.
