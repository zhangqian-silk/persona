# To-dos (Todos)

Record something to do, hand it to one or several Agents, and see in To-dos which Agents are working on it, what each is doing and how far the overall task has progressed; Agents can also be grouped by to-do on the Agents page.

## Why this is needed

One task often needs several Agents (different computers, workspaces and tabs). An Agents list arranged by project, state or computer does not show which ones are working on the same task, its overall progress, where it is blocked or who it is waiting for. To-dos collect scattered Agents under one goal for progress tracking and coordination.

## Who owns what (since 2026-11-04)

To-dos belong to the assistant (`todos.go`, `todo_decisions.go`, `todo_sessions.go`, `tasks_close.go` in `server/internal/assistant`; formerly in hub, see `docs/assistant/assistant.md`, "Boundary with hub"):

- **Assistant**: storage (the four tables below, still in the hub's Postgres, no migration, read/written only by the assistant process), every to-do API in "API overview" below, automatic project linking and following spawned sessions, reconciliation of herdr markers, snapshots of Agent titles/start errors, decision records, automatic completion and closing Agents for completed tasks.
  When hub receives a computer's session list it emits `sessions.changed`; when the user handles a card it emits `interaction.resolved`. These behaviors come from those two events.
- **Hub**: only forwards to-do APIs (`assistantwire.Routes`, carrying caller role; read-only roles still get 403), and uses the assistant's snapshot report for App session lists, question cards and pushes (`todos`: which unfinished to-do each Agent works on and which Agents are quiet, `hub/assistant_todos.go`; quiet reports only cover Agents of unfinished quiet tasks or those completed less than 7 days ago (`quietKeep`), keeping the report small; Agents from older tasks still push normally if they work again);
  `POST /api/v1/sessions` and `POST /api/v1/sessions/{mid}/{sid}/messages` with `todo_id` first ask the assistant (`assistant.todo_handoff`): does the to-do exist, is it done (if handoff is disallowed, it supplies 404/409 and the message, echoed by hub), prepend decisions to the Agent's message and project context for new Agents, all in one call. After handoff, ask assistant to link it (`assistant.todo_link`; assistant determines both linked title and to-do title); workspace renames through hub notify assistant (`todos.space_renamed`). Protocol in `docs/protocol/protocol.md`, "Bus".
- **When assistant is disconnected** (hub just started, assistant process restarting): to-do APIs return `503 assistant_offline`, "The assistant is temporarily unavailable. Try again later"; create/send with `todo_id` also return 503 (to-do existence unknown). Session-list to-do/quiet markers keep hub's last report (absent in the first second or two after hub starts before assistant reports). Hub emits no events during this period, so automatic linking, marker reconciliation and decision records wait for the next session list or answer after reconnection; workspaces renamed through hub are not migrated.

Completed ownership is display-only (#5929): `TodoReport.completed` names the most recently completed, non-dismissed
to-do for each session without an active link. Session lists expose it as `completed_todo: {id,title}`, separate from
the existing active `todo`. The Web chat menu labels it Completed and opens the to-do; it offers no fresh-link prompt.
Active task routing, supervision, counts and the existing quiet grace period still read only their original active
links/quiet report. Unknown optional fields are ignored by older clients; native menus are not changed by this fix.

## Permission of a planned task

A writable task that `task_plan` leaves without a `permission` gets one on the hub before the plan is saved, so the
plan card shows the mode the Agent runs in (#1897, #3026), in this order: the manager's default permission mode
(Settings › Assistant, `default_permission_mode`), then `permissions.defaultMode` in Claude Code's settings on the
computer the task lands on (Settings › Claude Code › Default permission mode, read with `claude.settings`), then
`default` (Ask every step). The last two cover the common case: someone who set Claude Code to start in Auto gets
Auto for the Agents the assistant starts, as for the ones started from the Agents page with no mode picked. A plan
saved before this, or a task that reaches the start with no mode, is settled the same way on the computer it starts
on. A computer that is offline, an older node, or a mode Persona does not know (such as `dontAsk`) gives `default`.
The card names Auto (`auto` is one of `task_plan`'s modes, and Edit offers it on every client); a Codex launcher still
takes only `plan` from it (`assistant/tasks_permission.go`).

## Read-only planned tasks

`task_plan` treats `readonly: true` as task metadata and a first-prompt constraint. Claude-family launchers save and start with
`permission: bypassPermissions`, whether the task is read-only or writable. A read-only task's first message adds
`本任务只读：不改项目文件、不提交、不对外写入` after its own prompt, without changing the saved prompt or duplicating the
constraint on retries. Codex read-only tasks keep `permission: plan` and the hard read-only sandbox. Planning, card edits,
legacy plans, retries, and the final dispatch all resolve the launcher before applying this rule; a permission change is
saved with the resolved launcher and model.

Ordinary plan-mode starts keep their existing behavior. For Codex read-only tasks, the node must honor `plan` or refuse
the start. Terminal starts and supported terminal resumes use `--sandbox read-only
--ask-for-approval never`: no approval can escalate past the sandbox. The node retains that constraint for later
resumes, including a message that reopens the session. The terminal policy uses `never` because Codex 0.167 no
longer accepts `untrusted` on its CLI; the separate thread API policy is unchanged.

A Codex launcher with its own `-s` / `--sandbox`, `-a` / `--ask-for-approval`, `--full-auto`, dangerous bypass
(including `--yolo`), or `--approve-for-me` is refused with `readonly_unsupported` and `delivered: none` instead
of guessing which permission wins. Managed launcher arguments are checked too. A launcher argument separator
that would turn the added flags into prompt text is also refused. Non-plan launches retain their original arguments.
An already running Codex cannot receive new CLI flags, so it cannot be adopted by a read-only start.
External runtime starts fail closed unless the runtime declares `caps.readonly` (`docs/integrations/runtimes.md`):
without it a runtime may ignore the mode or fall back to a different provider at dispatch. The Paseo bridge declares it
(#3238): a plan start runs on a Paseo provider that runs Claude Code, in Paseo's `plan` mode; a non-Claude provider, no
such provider, an agent Paseo reports in another mode (archived at once), or a takeover are refused.
Update both the assistant and nodes for this behavior. This is the runtime's plan restriction on task work, not a
promise that the runtime writes no session metadata or plan files, and it does not prevent a later explicit mode
change by the user.

Health-space plans and mixed plans still wait for Start. Clients show the Read-only requested label on a waiting plan and
collapse a started plan to "Started N tasks". The saved task's `permission` is the actual launch mode:
`bypassPermissions` for Claude and `plan` for Codex read-only tasks.

## Data model

Server state is stored in the hub's Postgres database (read/written by the assistant, above):

### 1. todos table
- `id` (text, PK): opaque string identifier (e.g. `todo_3f2a1b9c`).
- `title` (text, NOT NULL): to-do title.
- `notes` (text, NOT NULL, DEFAULT ''): detailed description and requirements, sent as context when handed to an Agent.
- `done_at` (timestamptz): completion time; `NULL` while unfinished.
- `created_at` (timestamptz, NOT NULL): creation time.
- `updated_at` (timestamptz, NOT NULL): last modification time.
- `origin` (text, NOT NULL, DEFAULT ''): assistant chat that created the task (session id); empty for manual creation ([unified-entry.md](unified-entry.md)).
- `plan_id` (text, NOT NULL, DEFAULT ''): plan that created it (`task_plans.id`).
- `done_by` (text, NOT NULL, DEFAULT ''): who marked it done: empty = user tapped (or launch failed, see `start_error`), `auto` = assistant automatically completed it after judging it finished ("Automatic completion"), `review` = supervisor completed it after acceptance (#3124), `cancelled` = supervisor cancelled it (#1851). The API continues to send `done_by = review` for cancellations so existing clients retain their review labels and reasons; supervised cancellations also keep `supervision.state = cancelled`.
- `done_reason` (text, NOT NULL, DEFAULT ''): judgment model's reason for automatic completion (e.g. "PR merged and TestFlight released"), cleared when user marks done or reopens.
- `reopened_at` (timestamptz): last time user reopened a completed to-do; assistant only judges automatic completion again after a new turn of work follows it.
- `thread` (jsonb, NULL): the chat thread the to-do is bound to, `{"channel", "chat_id", "thread_id", "title"}` (#5279, "Chat thread" below); `NULL` while it has none. A `CHECK` requires all three keys, and a unique index `todos_thread` over `(thread->>'channel', thread->>'chat_id', thread->>'thread_id') WHERE thread IS NOT NULL` lets a thread belong to one to-do only. One value, read and written as a unit, hence a jsonb column like the ledger's `reviews` rather than four more columns on every to-do read; the binding goes with the row when the to-do is deleted.
- `source` (jsonb, NULL): where the to-do was asked for when that is another chat, `{"channel", "chat_id", "message_id", "anchor"?, "no_report"?, "reported_at"?, "report_text"?, "report_due_at"?, "attempts"?}` (#6146, "Where it came from" below); `NULL` for any other to-do. Migration `0429` (manager side; first numbered 0428, which #6188 also took, so `db.go` renumbers it); a `CHECK` requires the three ids. Not unique (several to-dos may come from one message); one value read and written as a unit, hence jsonb like `thread`. Deleting the to-do deletes it.
- `due_at` (timestamptz) / `due_date` (date): when it is due, a moment or a whole day in the user's time zone; at most one (`CHECK todos_due_one`). `remind_at` (timestamptz): when the phone is pushed about it; `reminded_at` (timestamptz): when that was claimed, cleared whenever `remind_at` changes. `priority` (text, NOT NULL, DEFAULT ''): `''` normal, `high`, `low` (`CHECK`). Migration `0442` (manager side, #1683, "Due date, reminder, priority" below).
- `inbox_item` (text, NOT NULL, DEFAULT ''): the Inbox row it was made from (#6480, `docs/assistant/inbox.md` "Merge rows and Add to to-dos"), `''` for any other to-do. Migration `0512` (manager side). The to-do's page opens the row from it; the row links back through its chain.
- `project` (text, NOT NULL, DEFAULT ''): the slug of the knowledge-base project the to-do belongs to, `''` for none. Migration `0461` (manager side, #2581, "Project" below). Not a foreign key: projects live in the knowledge base's files.
- `kind` (text, NOT NULL, DEFAULT ''): `''` for a to-do or a task, `concern` for one of the owner's concerns (#3561, "Concerns" below). Set when it is made, never changed. Migration `0487` (manager side). `done_by` gains `reported` for a concern closed by its report.
- (Not in the table) `stage`, `stage_kind`, `pr_url`, `delivery`: stage strip, task kind, change link and delivery-card location, stored in settings `assistant.todo_stages`, merged when reading to-dos ("Delivery").
  `stage_kind` is `code` or `general` (#3380): read-only tasks are general (plan permission alone is not: code tasks start in plan mode to get a plan approved). Otherwise, only nonempty `done_when` with research, investigation, report, plan, triage, cleanup, summary, analysis or doc-review wording and no code wording is general; missing or ambiguous criteria default to code. Code wording includes PR, MR, merge, deploy, release, fix, bug, implement, code, test, commit, build, feature and refactor, with Chinese equivalents. A linked GitHub PR or an HTTPS merge request on any host overrides general. Older clients ignore the new field; the web omits the strip for general tasks and retains its existing task status.
  Mid-task replies (session lists, full followed items and supervisor progress reports) and final handoffs update the same forward-only progress. List snippets ending in an ellipsis and followed items marked with `FullSize` are skipped, without fetching transcripts from the session-list handler. GitHub `/pull/N` and any host's `/merge_requests/N` or `/-/merge_requests/N` links count; bare `MR !N` does not. Web links use `PR #N` or `MR !N` respectively.
  A pending `IxPlan` approval temporarily shows `plan` before review; answering it restores the stored stage, without recording a backwards progress change. Agent-link changes recompute pending plans for both the old and new task. Other permissions and questions never imply plan approval.

### 2. todo_spaces table
Records project workspaces (herdr workspaces) linked as a whole to a to-do:
- `todo_id` (text, NOT NULL, FK → `todos(id)` ON DELETE CASCADE): linked to-do ID.
- `machine_id` (text, NOT NULL): machine ID.
- `space` (text, NOT NULL): project name (session `space_name`, or `space_id` if absent).
- `linked_at` (timestamptz, NOT NULL): link time.
- Constraints:
  - Primary key: `(todo_id, machine_id, space)`.
  - Unique index: `UNIQUE (machine_id, space)`, ensuring a project follows only one to-do at a time.

### 3. todo_agents table
Records associations between to-dos and Agent sessions:
- `todo_id` (text, NOT NULL, FK → `todos(id)` ON DELETE CASCADE): linked to-do ID.
- `machine_id` (text, NOT NULL): machine ID.
- `session_id` (text, NOT NULL): session ID.
- `linked_at` (timestamptz, NOT NULL): link time.
- `released_at` (timestamptz): time active association was released; `NULL` while active.
- `title` (text, NOT NULL, DEFAULT ''): session-title snapshot (still displayable beyond the session-list time window).
- `cwd` (text, NOT NULL, DEFAULT ''): session working-directory snapshot.
- `agent` (text, NOT NULL, DEFAULT ''): launcher/Agent-type snapshot (`claude` / `codex`, etc.).
- `start_error` (text, NOT NULL, DEFAULT ''): asynchronous creation failure reason (viewable/removable in To-dos).
- `source` (text, NOT NULL, DEFAULT 'manual'): association source:
  - `manual`: manually linked or handed to an existing Agent;
  - `space`: linked with the entire workspace project;
  - `spawned`: spawned by a parent Agent linked to the to-do.
  - `leader`: the Agent of a task handed out with `task_plan` role `leader` (#3656, [unified-entry.md](unified-entry.md), "Task leaders");
  - `worker`: an Agent a task leader handed out with its own `task_plan`; `via` is the leader's to-do id (not a session): the worker's `supervision.supervisor` is that task's leader Agent session;
  - `review`: an independent reviewer's session (kept released, hidden from the lists).
- `via` (text, NOT NULL, DEFAULT ''): association path:
  - For source `space`, project key `<machine_id>/<space>`;
  - For source `spawned`, parent Agent identifier `<machine_id>/<session_id>`;
  - For source `worker`, the leader's to-do id.
- `dismissed_at` (timestamptz): manual removal timestamp. Removal sets both `released_at` and `dismissed_at`. APIs exclude removed records, and subsequent session updates do not automatically relink them.
- Constraints:
  - Primary key: `(todo_id, machine_id, session_id)`.
  - Partial unique index: `UNIQUE (machine_id, session_id) WHERE released_at IS NULL`, ensuring an Agent actively works for only one to-do at a time.

### 4. todo_decisions table
Decisions the user has made for this task ("Decision records"):
- `id` (text, PK): opaque identifier starting with `dec_`.
- `todo_id` (text, NOT NULL, FK → `todos(id)` ON DELETE CASCADE).
- `question` / `choice` / `reason` (text): question, selected choice, reason (reason may be empty).
- `source` (text, NOT NULL, DEFAULT 'manual'): `manual`, recorded manually in the to-do; `card`, recorded automatically when user answers an Agent question card; `outcome`, conclusions, decisions and lessons extracted from the Agent's last reply when the task finishes ("Record conclusions on completion" below); `agent`, noted by an Agent on the to-do while it works (`todo_decision_add`, below); `thread`, said by the user in the chat thread the to-do is bound to ("Chat thread" below); `reported`, what the main conversation told the owner of a concern's outcome (written only together with the concern's close, "Concerns" below).
- `source_machine` / `source_session` / `source_message` (text): provenance; for `card`, the asking Agent and card (interaction id), empty for manual records.
- `supersedes_id` (text, FK → `todo_decisions(id)` ON DELETE SET NULL): earlier decision this one supersedes.
- `created_at` (timestamptz, NOT NULL).
- Constraint: partial unique index `(todo_id, source_message, question) WHERE source_message <> ''`, recording each question on the same card only once.

### 5. todo_supervision table
Ledger for tasks supervised by the main chat (#3124, `docs/assistant/unified-entry.md`, "Supervision"), one row each; unsupervised to-dos have no row:
- `todo_id` (text, PK, FK → `todos(id)` ON DELETE CASCADE).
- `supervisor` (text, NOT NULL): supervisor, the chat that created it. With Agent tasks on (#3617, `docs/assistant/unified-entry.md` "Agent tasks") a to-do another chat or the user opened can have one too: the main chat or a leader, with `done_when` empty unless given. The background supervisor (#4927) is never stored here: a task it follows up keeps the main chat as `supervisor` (`docs/assistant/unified-entry.md` "Background supervisor").
- `done_when` (jsonb, NOT NULL, DEFAULT '[]'): acceptance criteria (string array); `expect_minutes` (integer, NOT NULL, DEFAULT 0): expected minutes.
- `state` (text, NOT NULL, DEFAULT ''): `''` in progress, `pending_review`, `rework`, `needs_user`, `accepted`, `cancelled`; `round` (integer): rework round.
- `reviews` (jsonb, NOT NULL, DEFAULT '[]'): each review (`verdict`, per-item `checks`, `note`), at most 20 kept; `updated_at` (timestamptz).

### 6. task_briefs and task_brief_todos tables
A task's brief (#3822, `docs/assistant/unified-entry.md`, "Briefs"): what was asked when the work was handed out.
- `task_briefs`: `id` (text, PK), `brief` (jsonb, written once: the owner's message, who started it, goal, `done_when`,
  `expect_minutes`, `out_of_bounds`), `state` (jsonb: the log of scope changes and overdue marks, the result),
  `created_at`, `updated_at`. Nothing rewrites `brief`; `done_when` in effect is the brief's as its logged scope changes
  left it, and a supervised task's `todo_supervision.done_when` carries the same list.
- `task_brief_todos`: `todo_id` (text, PK, FK → `todos(id)` ON DELETE CASCADE), `brief_id` (FK → `task_briefs(id)`),
  `continues` (the to-do it took the work over from), `reason`, `linked_at`. A brief's rows in `linked_at` order are its
  lineage.

`GET /api/v1/todos` carries both on a to-do that has a brief: `brief` (the record, its `log`, `criteria` and
`expect_minutes_now` in effect, `clock_at`, `due_at`, `overdue_at`, `result`) and `lineage`. A task from before briefs
gets a reconstructed one lazily.

### 7. todo_imports table
To-dos imported from another app (#4009, "Imported from Reminders" below). Migration `0499` (manager side).
- `source` (text, `CHECK` `'reminders'`) and `external_id` (text, nonempty): the item in that app; together the PK.
- `todo_id` (text, NULL, FK → `todos(id)` ON DELETE SET NULL, unique while set): the to-do it became; `NULL` once that
  to-do was deleted in Persona, which keeps the item from being imported again.
- `fingerprint` (text): short hashes of the title, notes and due date last taken from the item, one per field.
- `created_at`, `updated_at` (timestamptz).

Link/release semantics:
- When an Agent is linked to a new to-do and is active on another, the same transaction marks the original association `released` (records `released_at`); the old to-do shows it as "Previously involved".
- If an Agent previously involved in this to-do is manually linked back, clear `released_at`/`dismissed_at`, and refresh `linked_at` and snapshot information.
- When the user removes an Agent from a to-do, set that row's `released_at`/`dismissed_at` (soft removal, excluded from API results).

| POST | `/api/v1/todos/{id}/decisions` (`"source": "reported"`) | Report a concern's outcome by hand `{"choice", "source": "reported"}` (`choice`: what the owner was told; the question is the concern's title) → `{"todo": Todo, "closed"}`: writes the `reported` decision and closes the concern in one write; already closed: the report is kept and `closed` is false; not a concern or empty `choice` 400; an extension 400; missing 404; read-only role 403 ("Concerns") |
| PATCH | `/api/v1/todos/{id}/decisions/{did}` | Mark supersession after the fact `{"supersedes_id"}` (empty string undoes) → `{"decision": Decision}`; same rules; missing 404; read-only role 403 |
| POST | `/api/v1/sessions` | Create session, optional `todo_id`: after successful creation, automatically link within the same request; missing to-do 404, completed 409, read-only role 403 |
| POST | `/api/v1/sessions/{mid}/{sid}/messages` | Send message, optional `todo_id`: automatically link after success; missing to-do 404, completed 409, read-only role 403 |

### Session decoration fields
In session lists (`GET /api/v1/sessions` and WebSocket `sessions` pushes), hub injects to-do fields using the assistant snapshot's report (`todos.links`):
```jsonc
"todo": {
  "id": "todo_weather",
  "title": "Release weather App 1.3"
}
```
Only present when the session is currently associated (`released_at` and `dismissed_at` both `NULL`) and the to-do is unfinished. On release, transfer or completion, the field automatically clears; clients need no frontend join.
The internal `spawn_from` field carried in session reports is stripped before hub pushes to clients.

### Live WebSocket pushes
- `{"type":"todos"}`: broadcast on to-do creation, edit, deletion, whole-project link/unlink, Agent association changes, a change of its chat thread, or when its `ask` comes up, is taken or ends ("Waiting for the owner"); clients refetch `GET /api/v1/todos`. The hub sends one per write, so they come in bursts: the App (`TodoStore`) and the web (`todosPushed` in `web/src/lib/store.ts`) keep one such read out at a time, and a push that lands while it is out asks for a single read after it.
- Session-change push: when to-do/association changes affect sessions, assistant reports a new snapshot; hub compares which computer's sessions changed and re-pushes that computer's `sessions` event.

### Status codes and roles
- Missing title or malformed parameters: 400 Bad Request.
- Missing to-do: 404 Not Found. Old hubs without to-do APIs return 404; clients hide the entry point without an error popup.
- Linking to a completed to-do: 409 Conflict. Binding a chat thread another to-do holds: 409 Conflict.
- Assistant disconnected: 503 `assistant_offline` (to-do APIs and create/send with `todo_id`).
- Read-only role (e.g. paired Apple Watch, `role: "answer"`): every to-do write API (POST / PATCH / DELETE / PUT), plus create/send with `todo_id`, returns 403 Forbidden.

## Whole-project linking and automatic linking

### Whole-project linking
A herdr workspace can be linked as a whole to an unfinished to-do:
- On linking, batch-link every currently online Agent in the project (state not offline), `source = "space"`, `via = "<machine_id>/<space>"`.
- If the project is already linked elsewhere, unlink it first (remove the old to-do's space-linked Agents belonging to this project), then transfer to the new to-do.
- If an Agent in the to-do was dismissed, whole-project linking clears that dismissed state too.
- Unlinking deletes the workspace association and physically deletes Agent rows under this to-do with `source = "space"` and this project's `via` (manual/spawned Agents remain).
- Workspace writes (link, move, unlink, rename and task deletion) commit and publish their ownership changes in the same order. Session lookup happens outside that write boundary; a superseded request cannot later attach Agents to its former owner. Pending automatic Agent writes recheck current workspace ownership before persistence.

### Automatic linking with a project
When assistant receives a computer's session list (`sessions.changed`), it checks online Agents in whole-linked projects:
1. Agent currently has no other active to-do association (automatic rules do not take Agents away from other to-dos);
2. Target to-do has never had any record of this Agent (active, previously involved or manually removed all count as previously present, so no automatic relinking);
When both hold, automatically link to the to-do (`source = "space"`).
Automatic linking first updates assistant memory and reports to hub immediately (hub pushes that computer's session list again); database writes happen in background and roll back if they fail.
Previously hub linked it itself and included the association in that same session-list push; now it waits for the next push after assistant reports back (one bus round trip).
Automatic linking stops when a to-do is completed and resumes when reopened.

For renames through hub (shared with pin/mute's rename API), hub tells assistant (`todos.space_renamed`), migrating the space name in `todo_spaces` and corresponding `via` in `todo_agents` together. Assistant writes database first, then memory and broadcasts `{"type":"todos"}`. If the new name is already linked to another to-do (unique-index conflict), this project's old to-do link is invalidated and cleaned up, with a log entry. No migration if assistant is disconnected (same as "Known limitations", item 1).

## Following spawned Agents

For a supervised Agent's explicit handoff to a separate session, prefer `task_spawn` (or
`personad tool task_spawn` from its terminal). The manager records the child on the caller's existing to-do with the
same supervisor before returning; the Agent never reads a hub credential or chooses a to-do ID. See
[Separate sessions within a supervised task](unified-entry.md#separate-sessions-within-a-supervised-task-5751).
Native Codex sidecar ancestry and UI folding alone do not create a to-do link. A standalone runtime
`create_thread` without parent metadata is not a supported supervised handoff.

Child Agents spawned by a linked Agent automatically join the same to-do, tracking their parent hierarchy:
1. **Parent marker**: an active Agent on an unfinished to-do has a `persona_todo_ref` marker on its herdr pane, value `<todo_id>@<machine_id>/<session_id>`.
2. **Dispatcher passes the marker**: after launching a child, the dispatcher reads its own pane marker and writes the value to the child's pane as `persona_from`.
3. **node reports, assistant associates**: when discovering sessions, node copies `persona_from` into `spawn_from` and reports to hub; hub passes the session list unchanged to assistant (`sessions.changed`). Assistant parses to-do ID/parent Agent; if unfinished, child has no active association and no history in that to-do, automatically link it (`source = "spawned"`, `via = "<parent_machine>/<parent_session>"`). Following does not depend on parent being online or on the same computer.
4. **Grandchildren follow**: after the child joins, node also sets `persona_todo_ref` on its pane; further generations follow the same mechanism.
5. **Consume the marker**: after child gets an active association, node's periodic reconciliation automatically clears its pane's `persona_from`, preventing mistaken relinking later.

### Dispatcher contract and example command
After launching a child Agent (on the same or another machine), the dispatch script should copy the marker as follows:
```sh
REF=$(herdr pane get "$HERDR_PANE_ID" | jq -r '.result.pane.tokens.persona_todo_ref // .result.pane.tokens.persona_from // empty')
[ -n "$REF" ] && herdr pane report-metadata "$CHILD_PANE" --source persona --token "persona_from=$REF"
```
Note: for a child on another machine, read the parent pane marker locally, then send the command that writes `$CHILD_PANE` to the target machine's herdr.

### botmux following
botmux sessions have no herdr pane or `persona_from`. node reads each session's Lark group (`raw.chatId`) and thread-root message (`raw.rootMessageId`) from `botmux observe --include-raw`, then reads `orchestrate-dispatch.json` in the botmux data directory (`SESSION_DATA_DIR`, otherwise the directory referenced by `~/.botmux/.data-dir`, otherwise `~/.botmux/data`): keyed by dispatched thread-root messages, with `orchSessionId` identifying the dispatching session (`botmux dispatch --session-id`). These three values report to hub with the session (`chat`, `topic`, `dispatched`) and are stripped before pushing to clients. After the first two rules, assistant tries two more, only for Agents with no active to-do and no previous record in the target to-do:
1. **Follow dispatch**: if the session's thread was dispatched with `botmux dispatch` by a session (on any computer; offline counts if still in its computer's list, i.e. offline no longer than `offlineWindow`) linked to an unfinished to-do, join that same to-do (`source = "spawned"`, `via = "<machine>/<session>"`).
2. **Follow the group**: among unfinished to-dos linked by other online botmux Agents in the same Lark group, if the largest count is at least twice the runner-up (automatic when only one to-do exists), join it (`source = "chat"`, `via` is group id; client shows **Same Group**). Ties or insufficient margin do not link; wrong links can be changed manually. Agents linked by this rule do not vote (otherwise one Agent could spread a to-do across the entire group), nor do Agents on computers with no list report for 10 minutes.

## herdr markers and reconciliation

Under herdr, to-do associations map to pane markers (shown in the sidebar):
- **Written markers**: for Agents linked to unfinished to-dos, node maintains two metadata tokens on their pane:
  - `persona_todo`: to-do title;
  - `persona_todo_ref`: `<todo_id>@<machine_id>/<session_id>`.
- **Clearing markers**: when a to-do completes, is deleted or an Agent is unlinked, node clears its `persona_todo` and `persona_todo_ref`.
- **Source/namespace protection**: all writes/cleanup use `--source persona`. Reconciliation only touches `persona_todo`, `persona_todo_ref` and `persona_from`, never user or other plugin metadata.
- **Periodic reconciliation**: assistant sends expected markers by session ID (node RPC `todo.sync_session_tokens`, via `device.call`): immediately for computers whose associations changed, no resend otherwise; on a new node/hub connection (`connected` in `sessions.changed` changes: node may have restarted, do not touch markers until received), resend all with the first session list on that connection, like hub's former immediate resend after node reconnect. node resolves live panes dynamically only from currently living sessions and host-reported current Agent sessions, compares herdr's markers with expectations, fills missing and removes surplus markers. If two sessions map to one pane, only the live one counts. node reconciles every 30 seconds; after herdr restart, pane-ID change or hot handoff, markers restore on the correct new pane without old exited sessions contaminating it.

## State calculation rules

Clients calculate to-do runtime state live from linked active Agents; it is not persisted. Use the first matching state in this priority order:

| Priority | State | Condition |
| :--- | :--- | :--- |
| 0 | Didn't Start | Agent for a task created from chat failed to launch; assistant ends the to-do (`done_at` + `start_error`, #1077); client shows failure/removal, not active. A supervised task whose new tab is kept by its computer (`shell_waiting`, `agent_start_stalled`) is first remedied, still "starting" to clients ("Remedying a start" below) |
| 1 | Done | User marked done, or assistant judged a dispatched task complete (`done_at != null`; client shows **Auto-completed** for `done_by = "auto"`) |
| 2 | Needs You | A linked active Agent is `needs_you` (waiting for question, plan approval or authorization) |
| 2.5 | Interrupted | A linked active Agent is stopped (`unread` / `idle`) with `turn_error`: model-service failure interrupted the turn (disconnect, overload, rate limit, expired login…), unfinished (#1516); red, **Continue** on the card sends "继续" ("continue"). A subscription usage limit is not this (the next row) |
| 2.6 | Usage limit | A linked active Agent is stopped with `turn_error_kind` `usage_limit`, and the reset is not known or not more than 10 minutes past. Not red and not Interrupted: "Usage limit · resumes <time>" when the CLI or the hub will continue it, "Usage limit · resets <time>" when nothing will. An older hub that does not send the kind stays Interrupted |
| 3 | Unread | A linked active Agent is `unread` (task finished, not viewed yet) |
| 4 | Active | A linked active Agent is `working` (working or starting) and not waiting (next row) |
| 4.5 | Waiting | A linked active Agent ended its turn but something brings it back (#3274): only background commands, subagents, Monitors or workflows it started still run (`background_working`), or the hub waits out another agent, a deploy / CI / a time, or a moment's model failure for it and wakes it (`work.phase` `blocked`, `work.on` `agent` / `external` / `transient`). A wait only the agent's own process ends (background work, a /loop) is dropped once the node lists the agent as cut off (`interrupted`): its process is gone, so the task reads Follow up and, when nothing else brings it back, Nobody is working on this (#5124). Shown 等待中 with what it waits for (`work.line` / `work.wait`); under way like Active in the dock, the board, Today and the brief. The hub's `taskState` sends `waiting` on task cards. On a hub with bounded lists the web reads a task's agents from the list's rows (the Agents window, and `taskRows`: the list's deltas and one exact lookup for an open task's agent outside it), not only from opened chats |
| 5 | Follow up | All linked active Agents are stalled (`idle` seen, `offline` not running, or launch failed) with nothing to bring them back |
| 6 | Not started | No linked active Agents |

- **Nobody is working on this** is not a row of this table: the hub works it out, since it needs to know whether the Agents' computers are connected and whether a wake is pending, and sends it as `orphaned` on the to-do ("Nobody is working on this"). A client that shows it puts it ahead of Interrupted and Follow up; one that does not shows the row above as before.
- To-do list ordering: unfinished first (same state by `created_at` descending), completed collapsed at bottom.
- Completion means the task is over: its Agents' sessions no longer say they currently work for it; **Reopen** to continue. A chat-dispatched task the hub completed also reopens when one of its Agents starts a turn again: an auto-completed one on any new turn (sent more with `agent_send`, or by the user; see "Stop Agents of completed tasks", #5892); one accepted by its supervisor on any new turn too when its plan started the Agent (`task_plan`). An accepted task with no plan (its Agent adopted with `agent_supervise` or `agent_send` with a task, an Agent that became a task by itself, one linked by hand, or `agent_start`'s) reopens only when its own conversation sent that Agent more after the acceptance (`agent_send` from the task's conversation or supervisor, or the owner's message on its card): such an Agent is often kept on for other work, and its other turns (its own timers, other conversations, messages from other sessions, the owner typing in its session) leave the task closed (#6726). Cancelled tasks stay closed when their Agent works again; only an explicit **Reopen** resumes their task tracking and supervision (#1851).
- **A hub restart during startup** (#3251, `assistant/tasks_recover.go`): a task start keeps the assistant busy from before its goroutine is launched until linking, failure bookkeeping or entering a retained-tab remedy has finished. The built-in manager therefore waits for it before switching binaries, subject to its existing 30-minute maximum (`docs/assistant/managers.md`). After a forced restart or crash, before its background loops begin, the assistant reads saved to-dos and plans. A started plan updated within `taskStartTimeout` (5 minutes) before this service was created, with an open task that has no agent, start error or recorded start remedy, is marked failed with an explicit restart reason. This includes read-only / plan-mode tasks and reused topic to-dos, whose plan relationship is saved in `ReuseTodo` instead of the to-do’s `PlanID`. The plan keeps the error, the conversation gets a failed receipt, and the supervisor receives an urgent failed-start signal (other tasks use the ordinary failure notification). Completed or cancelled tasks, any task with an agent, recorded remedies, older plans and starts admitted by the new service are left alone. The window uses the plan's saved update time, so approving an old draft or retrying a failed start can still qualify; historical dangling work is not replayed on deployment.
  The hub never resends these starts automatically: a node, especially a runtime bridge, may finish the previous request after its connection drops, and the saved plan has neither a start idempotency key nor a session / pane identity to adopt safely. The reason asks the supervisor or user to wait for the computer to reconnect and inspect its sessions before retrying. An offline computer does not delay recording the failure. No kept tab is invented for `beginRemedy`; existing remedies retain their normal expiry handling. Recovery requires the plan’s saved `TodoID`: it does not guess a task association if the process stopped before that link was saved.
- **Remedying a start** (#2570, `assistant/start_remedy.go`): when the new tab's shell stopped on a startup question (`shell_waiting`) or Claude's own screen stopped before its input box (`agent_start_stalled`), the computer keeps the tab for 10 minutes (`node/shellsettle.go`). For a supervised task the hub records this on the plan task (`start`: `state` remedying / started / failed, `attempt`, `by`, `machine`, `pane`, `until`, `code`, `reason`) instead of failing the to-do, and the supervision message carries the question, the tab's last lines and the retries left. The main conversation may read the tab (`task_start_screen`), type into it (`task_start_keys`: any text up to 32 characters and keys, with a reason; the node takes them only into that kept tab while no agent runs there) and start again in it (`task_retry`, which also reopens a start that failed for good, in a new tab); at most 3 retries per task, and the hub never retries by itself. Each step is a `start_remedy` feed item. A retry that starts sends the supervisor a `started` signal. The start fails for good (`done_at` + `start_error`, the failed receipt, the bot's report) when the supervision turn that saw it ends with no retry running (the turn of the conversation that message went to, not another supervising conversation's, #4927), when the kept tab expires (checked on the supervisor's tick, so a restart catches up), or when a retry fails without a kept tab. If that turn never told the user (no `notify_user`, task review card or visible finish), the hub writes "Didn't start: <task>. <reason>" into the conversation and pushes it.
- User marks done while Agent is still launching (can take minutes on a busy machine; `done_at` written first): not **Didn't Start**, to-do stays done with no `start_error`; Agents that do launch join this completed to-do and are stopped by "Stop Agents of completed tasks" under existing rules (only after idle long enough) (#2954).

## To-do titles

To-dos created by `task_plan` and `agent_start` (#2775), and by `agent_send` with `task` and `agent_supervise` (#3020), formerly used the prompt's first line as title, often starting with instructions to the Agent ("ultrathink ultracode 主人 11-05 19:47 的反馈，已授权直接开工：…", meaning feedback from the owner, authorized to start; "秘书派活（主人授权过…）", meaning assistant dispatch, owner already authorized), obscuring the task itself. Now two steps (`assistant/todo_titles.go`):

1. **On creation**, synchronously supply a cleaned title: remove leading keywords such as ultrathink / ultracode / think hard, provenance/timestamps such as "主人 11-05 19:47 的反馈" (owner's feedback), parenthetical notes such as "秘书派活（…）" (assistant dispatch) / "【…】", and "已授权直接开工" (authorized to start); truncate to 20 Chinese characters (20 Japanese, 40 characters for other languages). No model call, no delay to task launch.
2. **In background**, the small-task model (**To-do Title** `todo.title` in model configuration, inheriting the knowledge-organization category, through `models.complete` like chat titles `assistant.title`) reads the prompt and produces a short title explaining the task, replacing step 1. Keep step 1 if model unavailable, errors or empty result. Before replacement, verify title is still step 1's (conditional `UPDATE … WHERE title = old title` in database); never overwrite an intervening user edit. Prompts: `prompts/todo/title.md`, `title_input.md`.

Assistant-supplied titles in `task_plan`, `agent_send`'s `task.title` and `agent_supervise`'s `title`: if within the limit and without those prefixes, use as-is without a model; only first-line, overlong or prefixed titles use the two steps. Without a title, `agent_send` names the task from its text when the task still has a `done_when` or `expect_minutes` (with neither it is a plain reply and makes no to-do, #3386); `agent_supervise`, which has no instruction, keeps the session's title (else its label).

**Batch retitle existing to-dos**: `POST /api/v1/todos/retitle` selects only task-created to-dos (nonempty `origin`) whose title is still the prompt's first line truncated at dispatch: over the limit and a prefix of `notes` (truncated, with or without "…"). Short titles merely resembling prompts ("【紧急】修登录", "[Urgent] fix login"; "11/05 反馈：修登录", "11/05 feedback: fix login") count as user-created and stay untouched (to-dos do not record who named them; this is the most conservative possible judgment). Use model for each (4 concurrent), or step 1 cleanup without a model; again verify title unchanged before writing.

```sh
curl -X POST '<hub address>/api/v1/todos/retitle?dry_run=1' -H 'Authorization: Bearer <token>'   # Preview changes first
curl -X POST '<hub address>/api/v1/todos/retitle' -H 'Authorization: Bearer <token>'             # Then apply
```

## Automatic completion

Tasks dispatched from assistant chats (to-dos created by `task_plan`, nonempty `origin`) are automatically marked done by assistant, without individual user taps (except tasks supervised by main chat: completion judgment moves to "Pending review", and supervisor must accept with `task_review`, `done_by = review`, see `docs/assistant/unified-entry.md`, "Supervision"). Manually created to-dos (empty `origin`) never auto-complete; only user marking done counts.

With Agent tasks on (#3617, off by default; `docs/assistant/unified-entry.md` "Agent tasks"), an Agent started from an app's New Agent or by `agent_start` from any chat is on a quiet, supervised to-do with a nonempty `origin`, so it is judged here like the main chat's own tasks: an app's Agent gets its to-do at the first turn end that did work, and that stop is the first one judged. A manually created to-do an Agent is linked to gets a supervisor then, but still never auto-completes.

**When judged**: all task Agents stop (none working, waiting for user or carrying pending cards), at the same point assistant sends the done receipt to chat (`taskTurnEnded` in `assistant/tasks_follow.go`; one receipt and one judgment per stretch of work). The receipt's `done` is the end of that stretch, not of the task: the apps draw it "<task> stopped, not done yet" while the to-do is open and as done once it is, and the "Today" card lists as finished only to-dos that are done (#6153).

**By session and turn** (#5718, `server/internal/assistant/task_turns.go`): the receipt, the judgment and the supervision signal belong to the turn the runtime closed, not to whichever event told of it. The runtime's end of a turn in the transcript names it: the turn id of Codex's `task_complete`, else the id of the item that ends it (Claude Code's `turn_duration`, the interrupted notice of a user's stop). Each open task has one row in the `assistant.task_turns` setting: the session and turn taken up last, the stretch of work it closed, the judgment written for it and whether its signal was told.

- **Idempotency key**: (to-do id, machine id, session id, turn key). The receipt's feed id is a hash of it, so the receipt is written once whichever path writes it and whichever manager process (the `assistant_feed` primary key). A turn taken up again gets no second judgment: the one on the row is put back without a model call when a start was heard since (a stale `working` row after the end takes the check and the review wait off), or made now when a manager stopped between the receipt and the judgment. Its signal is told once: the row keeps the signal's kind and key and when a supervision message carried it, and a manager started again tells what was not told and does not repeat what was.
- **No working needed**: for a supervised task the supervision sweep (every 30 seconds, below) reads the last turn of the task's last Agent when all its Agents look stopped (`done`, `idle`, or `unknown`) and that row moved since it last looked. A closed turn the row does not have is taken up through the end's own checks: only when none of them refuses or puts off the end, and the transcript, read once more, still shows the turn closed, is the start nobody heard taken (what a `working` list would have done), then the receipt, the judgment and the signal as usual. An end that is not taken therefore leaves the task's stage, check and review wait as they were. An `unknown` status counts as stopped only for the row whose transcript showed the turn closed; a row is the same row while its status and its transcript's size (`rev`) are (its time counts only where it has no `rev`: a node's later list can carry a later time for a transcript that did not change). So a node that never lists a runtime as working, a manager that was down or disconnected when the turn ended, and lists that arrive out of order all end in the same one receipt, one judgment and one message.
- **Bound**: a turn that ended unheard gets its receipt within one sweep tick (30 seconds) plus two transcript reads (the sweep's and the end's own, 20 seconds at most each) of the node listing the end; with more than four such tasks at once, four looks go at a time and the rest follow on the next ticks. The judgment follows within its own limit (90 seconds, with one retry 3 seconds after a failure); one that does not land (the task's work changed while it was judged) is asked again on the next tick, then one and two minutes later, and when the third does not land either the supervisor is told `unjudged` at once. The supervision message then goes out on the usual schedule (15 seconds to gather, at most one message per 2 minutes for a stop, per 10 minutes for a review; queued behind a running main chat turn).
- **A look that cannot finish** (the node does not answer the read, an Agent works or waits again, another look is at the same end, the judgment does not land) is tried again on the next tick, then 1, 2, 4 and 8 minutes later and every 10 minutes after that, while the row stays as it is and its node's connection is the same one. A row that moved, or a node that connected again, is looked at on the next tick whatever came before. Some states are not looked at at all, because looking cannot help:
  - **A usage limit that is waited out** (the CLI or the manager goes on after the reset): nothing is read and no start is taken until the wait is over; the turn that did not go on after all is taken up then.
  - **A computer that is not connected**: its rows are the manager's copy of its last list; nothing is asked until it is back.
  - **An end the task refuses as it stands** (a cancelled task that is still open, an Agent let go, a meeting's turn): recorded as seen after one read, not read again while the row stays, and not taken up if the task changes later.
  - **A turn stopped between its tools and its answer**: no receipt, as on the edge; left until its transcript is written to.
- **What it costs**: no call to a node unless an open supervised task's Agents all look stopped and the last one's row moved; then one `session.items` read of one turn, and a second one when the turn is taken up. Stopped sessions that belong to no open supervised task cost nothing, and after a manager start each open supervised task is read at most once.
- **Not recovered**: a turn of a task nobody supervises (it keeps the working → stopped edge), and a turn of a closed task (a turn found in a transcript does not reopen it). A turn that ended before the ledger was first kept, before its Agent was linked or before the to-do was reopened is recorded as seen and nothing is made of it. A turn whose transcript never gets an end record (an older runtime, a runtime that died before writing it) has no key: it is handled from the edge alone, as before.
- **A turn handled before it had a name**: the node can say an Agent stopped before the runtime has written the turn's end record (Claude Code writes it after its Stop hook; Codex in a pane is listed from the screen, not from the rollout), and the read at the end can fail. Such a turn is kept with the item that opens it (its prompt) and whether its receipt went out. Found later with its end record, it is that turn (the same opening item; where none was read, it began before the row was taken): it gets its name, and no second receipt, judgment or message.
- **Size and writers**: the setting holds one row per open task that had a turn; rows of closed tasks are taken off on each tick. A row is small (under 1 KiB usually, about 11 KiB at most: the judge's reason is 40 characters, a task has at most 6 criteria of 200 characters with 300 characters of evidence each, an error is cut at 300), and nothing caps the number of open tasks. The document is read once by a manager process and rewritten whole on a change, as the to-do stages are: a manager is one process at a time (a planned stop or switch waits for it to exit; its own service holds a lock). Where two overlap for a moment (a hub that was killed leaves its child running until it sees its input closed), an update of one can be lost to the other. The receipt is still written once (its id); the turn can be judged a second time, and its message is then held back by the 30-minute deduplication when the Agent's last words are the same.
- **Locks**: the ledger's mutex is held across its database reads and writes, so it is never taken while the task lock (`s.tasks.mu`, used all over the manager: starting tasks, routing messages, cards, stages) is held, nor the other way round. The one thing both sides need, the mark that a turn's end is being handled right now, is in memory under a small lock of its own that is held across nothing. A ledger write that does not come back (a full pool, a Postgres restart) therefore keeps the ledger's own callers waiting, up to that write's deadline, and nothing else (`turnsState` in `server/internal/assistant/task_turns.go`; `task_turns_lock_test.go`).
- **A dropped link at the wrong moment**: the stretch's receipt is reserved before the task's Agents are asked a second time whether they stopped. When that second look fails (the node does not answer, or one works again), the reservation is given back and the turn end is looked at once more 30 seconds later, so a link that dropped for a moment no longer leaves the stretch without a receipt and a judgment.

Normal receipts are written before judgment for both supervised and unsupervised tasks. At receipt time, the latest open to-do with a supervision ledger adds `review: {"state":"awaiting","criteria":N}` (the number of `done_when` entries, including zero), unless its effective supervision state is `needs_user`. This names Persona's next follow-up: `superviseJudged` signals review for finished work or idle for unfinished work; `needs_user` means the task is already waiting on the user. An accepted task that was reopened, or a cancelled task the user explicitly reopened, has an ongoing effective state and qualifies again. The receipt does not wait for the model or change the order of supervision signals. Failed / interrupted receipts carry no review. The web keeps the neutral stopped title for an open task and adds "Waiting for Persona's review", with a positive criterion count; completing the to-do hides this historical hint. Older receipts and clients remain compatible (#4893).

**How judged**: stopped is not finished; "not all changes done…" or "waiting for review" must not close. Assistant's judgment model (through hub model configuration, `app.call models.json`; **AI Twin Judge** `inbox.judge`, i.e. `inbox.judge_ai` in the manager's `manager.json`, inheriting `ai` if unset) sees three things: task title, dispatch requirements (to-do `notes`), each active Agent's latest turn (read via `session.items`: user's message and last complete reply; fallback truncated `last_text` in session list if unreadable). Later new requirements from user override original ones (already handled in earlier turns); if later messages merely confirm/answer a question ("OK", "👌", "Use A"), original dispatch requirements still apply (#1116). Model chooses one of five:

| Verdict | Meaning | Auto-complete |
| --- | --- | --- |
| `done` | Requested work finished, reply gives results, user need do nothing more, no waiting for others | Yes |
| `not_done` | Partial, failed, blocked, or only reporting progress/plan | No |
| `waiting` | Awaiting an external result (review, CI, someone else's reply, release queue), or no model is configured for the completion judge and the hub writes its own localized reason | No |
| `needs_user` | User must decide, supply information, approve, act manually or accept | No |
| `unsure` | Cannot tell | No |

- Caveats do not prevent completion: platforms without screenshots, unmeasured environments and reminders to user are not unfinished work. Routine waits after delivery (TestFlight external-group Beta review, CI rerun) do not count as waiting either; addressing App Store / Mac App Store review feedback then awaiting review outcome does count as `waiting`.
- Prefer leaving open: unavailable model, timeout, invalid JSON or verdict other than `done` leave the to-do open and log; receipt still sends. A verdict is kept as the to-do's `check` (below).
- No judgment for a turn interrupted by model service (#1516): if an Agent stops on an API error (`turn_error`: Claude Code's last message such as "API Error: …", Codex reported by node from this turn's error, #2185), receipt has `state: "interrupted"` (summary "Model-service error interrupted the task", original error in `error`); no judgment-model call or closing to-do. `done-check` directly returns `not_done` when the last reply is such an error.
- No judgment for a turn with no output either (#2349): latest stopped Agent's turn (node `session.items`, `turns: 1`) contains no assistant text, tool calls or images and no `turn_error` (model service returns 200 with empty content; Claude Code adds an invisible "no visible output" notice, retries, then ends silently). Receipt is `interrupted` (error "这一轮没有任何输出：…", "This turn had no output: …"), notification uses interrupted, no judgment or to-do close. Unreadable items (node unreachable/no items) or user pressing Esc ("已中断" notice, "Interrupted") do not count.
- Cheap signals: final reply has a GitHub PR link and mentions merging (merged / 已合并 / 合入, the latter two meaning merged), or mentions TestFlight plus a build number. Assistant includes these as hints only, never enough alone for completion.
- Prompts: `server/internal/prompts/assistant/task_done.md`, `task_done_input.md` (`docs/assistant/prompts.md`).

**The check on the to-do** (#3180): every automatic judgment, supervised tasks included (before `superviseJudged`), writes `check: {"verdict", "reason", "at", "work_since"}` on the to-do, so an open task can say why it is not done: `verdict` as judged (a made-up one becomes `unsure`; with Delivery on, `undelivered` too), `reason` the judge's line, `at` when it was judged, `work_since` the start of the stretch of work it judged. It is written only while the judgment is still current (`taskCompletionCurrent`, and no new turn since under `completionMu`), so one overtaken by new work writes nothing; a reopen and an Agent's new turn clear it. Having no configured model writes a hub-generated `waiting` check with the same localized explanation shown in model settings; a model error still writes nothing.
- **Language**: the judge writes `reason` in the user's language (`{{if .Language}}` in `task_done.md`) without internal ids. The hub's own reasons (no reply read, a cut-off turn, a side-conversation reply with no evidence for this task) and the `done_reason` fallback for an empty reason come from the hub's i18n (`assistant-tasks.*`).
- **Storage**: next to `delivery` in the `assistant.todo_stages` setting (`task_check.go`, `reports.go`), no migration. It is additive: no field changes meaning, `task_cards` is unchanged, and clients that don't know it show the to-do as before.
- **Clients**: web `ProgressTaskRow` and Android `trayProgress` say "Stopped, not done yet · <reason>" for a task neither working nor done whose current check is not `done` / `unsure` (`docs/assistant/unified-entry.md` "Progress tray"). iOS doesn't draw it yet (#2879).

**Visible and reversible**: auto-completion writes `done_at`, `done_by = "auto"`, `done_reason`. iOS / Mac / web list/detail show **Auto-completed** beside Done; detail shows reason. **Reopen**, like manual completion, returns to unfinished, clears `done_by`/`done_reason`, records `reopened_at`. Before it clears them, a reopen is recorded as a `todo_reopened` work event, so the work stats can count the judge's closes reopened within 24 hours (`docs/assistant/agent-work.md`, "Evaluation").

**After reopening**: same stretch of work cannot auto-close again; only when an Agent begins a new turn after `reopened_at` (user sends again, Agent resumes) is completion judged again. After assistant restart the turn's start time is unknown; reopened to-dos are not judged then (prefer leaving open). Database write rechecks (`done_at IS NULL`, `reopened_at` before work start); user completion/reopen during judgment wins.

**After completion**: same path as user marking done: sessions lose to-do field, node reconciliation clears `persona_todo` / `persona_todo_ref`, whole-project linking/spawn following stop, Inbox AI twin no longer associates messages with it; assistant live snapshot marks task "Done (automatically closed after hub judged complete)", omitted after 24 hours.

**Diagnosis**: `POST /api/v1/todos/{id}/done-check` judges the same inputs, returns verdict only without database writes, `check` included (read-only role 403):

```jsonc
{"verdict": "waiting", "reason": "Waiting for App review", "would_close": false, "skip": "", "replies": 1, "signals": {"merged_pr": false, "build": false}}
```

Nonempty `skip` means automatic flow would not judge this to-do (`not_a_task` manual, `done` completed, `reopened` no new work after reopen), but API still returns model verdict for inspection.

**Re-check applies** (#4867): with the body `{"apply": true}`, which the web's Re-check sends, the check writes what it finds, as the end of a turn would.
This catches up after a turn end the hub missed, such as a restart mid-turn, and after a verdict that was only shown.
It runs only when the automatic flow would judge the to-do (no `skip`) and its agents are not working.

1. It reads the agents' last replies and moves the stage and delivery from them through the deploy check ("Deployed needs evidence" in `docs/assistant/todo-status-sop.md`). Deployed work is asked to be verified.
2. It judges, keeps the verdict as the to-do's `check`, and moves the task on: a supervised task found done waits for its supervisor's review, and the supervisor is told; an unsupervised one is closed.

The answer adds `applied` (whether it wrote) and `stage`. Without `apply` nothing changes.
With **Delivery** enabled (next section), response also has `delivery`; `verdict` may be hub's own `undelivered`.

### Judged against the brief (#3822)

The judge's input names the task's brief (`docs/assistant/unified-entry.md`, "Briefs") when it has one: the owner's
message that led to the work, verbatim with its day, and the criteria as logged scope changes left them, with the
dropped ones listed as no longer required. A take-over's notes are a hand-over prompt; the request and the criteria
are what the work is judged against. When the judge closes a task itself (spot-check reviews), the brief's `result`
records each criterion as it did for the supervisor's review.

## Delivery

(#3306, lessons in `docs/lessons/delivery.md`) A code-change task is "done" only when live and tested, not when a PR is opened or merged. Judging only whether an Agent says finished leaves many tasks at "PR opened", "merged but off by default" or "not deployed" while showing Done.
Assistant setting `done_needs_delivery` is **off by default** (off retains the old verdict-only behavior). Enable either way:
tell assistant "Turn on 'only done when live and tested'" (`assistant.done_needs_delivery` in `persona_settings`, confirmation card on phone), or `PUT /api/v1/assistant` with `{"done_needs_delivery": true}`;
effective from the next judgment and next dispatched task. When on:

- **State criteria at dispatch**: for non-read-only tasks created by `task_plan`, hub appends delivery criteria to the Agent's first message (dispatch prompt, `prompts/assistant/task_delivery.md`): done = live and tested, with measurements;
  if rules permit self-merge/deploy/enable, finish the whole path; if current user approval is required (merging a repo not owned by user, production deploy, enabling an off-by-default feature, outbound messaging), stop one step before approval and state what needs approval;
  first try to resolve CI/other-person/environment blocks yourself; if impossible, state where and who can unblock. Fixed last line: `交付：<已上线并实测 | 停在 PR | 已合未上线 | 默认关待启用 | 不涉及上线>；卡点：…；谁来解：…` ("Delivery: <live and tested | at PR | merged, not live | off by default, awaiting enablement | no deployment involved>; blocker: …; who can resolve: …"). Read-only tasks omit it. While the triage's `closeout` switch is on the prompt also asks for a closeout, and the line is then the one just before that block instead of the last (`docs/assistant/agent-work.md`, "Closeout"); the line is read wherever it stands in the reply.
- **Judge one more thing**: the "Automatic completion" model also returns `delivery` (`live` / `pr` / `merged` / `off` / `none`), `gate` (blocking gate), `unblock` (`user` / `agent` / `other`), taking the Agent's line as authoritative unless contradicted by the body.
  If model omits it, use Agent's line; if neither exists, `none`. If `live` (or not judged) but reply mentions a PR without deployment or TestFlight build-number wording, treat as `pr` / `merged`, unless the Agent's line says live.
- **`live` needs evidence** (#3205): a `live` the judge (or the Agent's line) gives is checked against the running hub; the hub's commit not containing the PR's merge commit (or the check failing) makes it `merged` with the gate "等部署…" / "等确认部署…" (`docs/assistant/todo-status-sop.md` "Deployed needs evidence").
- **Only `live` and `none` auto-complete**: if `verdict` is `done` but delivery incomplete, change to `undelivered` and keep to-do open.
  Main-chat-supervised tasks (#3124, already not closed by hub) do not enter pending review; supervision message says "Finished but not live yet: …(at PR, blocked on '…')", for main chat to follow up or ask user approval.
- **A supervisor's `accepted` is held the same way** (#6428, `assistant/supervise_review_delivery.go`): `task_review` with `accepted` on a task whose PR (the review's `link` when it names a GitHub PR, else the to-do's) is not live is refused and nothing is written: the PR not merged, merged but not in the running hub, not named by its deployed-commits file, or the check failing. Where the running hub cannot be checked against (another repository, a hub that does not say its commit) the PR only has to be merged. The refusal tells the supervisor to rework, `agent_send`, park with `waiting_on: external_event`, or cancel; `outcome: cannot` and tasks with no PR are not held.
- **To-do shows the blocker**: judgment results except `not_done` are recorded in to-do `delivery` (`{"state", "gate", "unblock", "at"}`, settings `assistant.todo_stages` alongside stage strip, no new table); delivery replaces unconfirmed reply-keyword guesses (PR → review, merged → merge, off by default/live → deploy), but never rolls stored progress back or caps a deployment confirmed by the deploy gate. Explicit verification is recorded only after an acceptance is saved; a supervisor's `accepted` alone does not verify a high-priority task still awaiting its owner. All stage writes are forward-only except an explicit review withdrawing verification (`unverified`) from `verify`; rework, `cannot` and a requested user check do not count as verification.
  Web to-do rows add "At PR · Blocked on '…' · Needs your approval" while open and `state` is `pr` / `merged` / `off`; Android to-do rows (when the Agent is neither working nor waiting for you) and details show the same line (`Todo.hold` in `core:domain`); iOS / Mac do not render it yet (optional field, old clients unaffected).
- **Batch user approvals**: assistant live snapshot lists delivery blockers after each task; open tasks with `unblock = user` get a separate "Waiting for user approval to go live" group (oldest ten).
  Assistant CLAUDE.md tells it to present these together in one message; after user approves in one reply, use `agent_send` to notify the corresponding Agents separately, rather than asking anew for every item.

## Spot-check reviews

(#3128, `assistant/supervise_sample.go`.) Every finished supervised task waits for the main conversation's `task_review`; with many tasks that makes the main conversation the bottleneck. The assistant setting `review_sample_percent` (0–100) lets the done judge close the tasks it can verify and sends only a share of them to the main conversation.

- **Default 100**: nothing changes. The judge is not asked for anything more and every finished task waits for `task_review`.
- **Turning it on**: tell the assistant (`assistant.review_sample_percent` in `persona_settings`, confirmation card on the phone), or `PUT /api/v1/assistant` with `{"review_sample_percent": 20}`; `GET /api/v1/assistant` reports the share in effect. It applies from the next judgment.
- **The judge's check**: below 100, the "Automatic completion" model of a supervised task with `done_when` also returns `checks` (per criterion, in order: `checkable`, `met`, `evidence`) and `delivery` (as in "Delivery", whether or not `done_needs_delivery` is on; it is not written to the to-do unless that setting is on). The hub matches the checks to the ledger's criteria by position. A task **passes** when every criterion is checkable (a command's output, CI, a link, a live reading — not a matter of taste or something only the user can confirm), met, with evidence, and the delivery is `live`. A task without `done_when` never passes.
- **Passed and not sampled**: the judge closes it as `task_review accepted` would: the ledger records an accepted review `by: "judge"` with the checks, the to-do closes (`done_reason` starts with 判官核对通过), the outcome goes to the project timeline, and the owner gets the usual conclusion card. The main conversation gets no supervision message for it.
- **Passed and sampled**: whether a task is sampled is a hash of the to-do id and the stretch of work, so the same work always gets the same answer; about `review_sample_percent` percent are. A sampled one waits for `task_review` as before, its supervision message starting with 抽查 so the main conversation knows the judge's check already passed.
- **Failed the check**: waits for `task_review` as before.
- **Never closed by the judge**: a rework round (the supervisor was promised the next review, and asked for more than `done_when` says), a task that was reopened or was ever accepted or cancelled before, and a task the supervisor reviewed while the judge was deciding. `live` counts only when the judge itself says so, never on the Agent's delivery line alone; checks that do not come one per criterion with each criterion copied in its place count as not met.
- When the independent review (`supervise_autoreview.go`) starts for a task, it runs first and its result waits for `task_review`; the judge's check does not close it.

## Stop Agents of completed tasks

Completing a to-do stops Persona's automatic follow-ups for its linked Agents, including when a turn ends after
completion: no transient-error retry, usage-limit continuation, scheduled wake or new triage card. Triage may still
record the turn's work state. The check runs before scheduling and again before sending, including after a manager
restart. It applies to manually linked to-dos too, regardless of whether the Agent can be closed. Released or dismissed
links do not count, and an Agent linked to an open to-do can still receive follow-ups. Deleting a to-do leaves its Agents
unaffected. Direct chat messages and `agent_send` still work; a user-completed to-do stays done until explicitly reopened,
while a hub-completed task reopens on new work as described below.

After a task dispatched from assistant chat (nonempty `origin`) completes—manually or automatically—its Agent stops running (with Agent tasks on, `docs/assistant/unified-entry.md` "Agent tasks", that includes the Agents started from an app or another chat, whose to-dos have an `origin` too):
assistant checks every minute (`assistant/tasks_close.go`, reading hub's App-facing session list through `sessions.list`); once task completion and Agent inactivity both reach 3 minutes (`taskCloseIdle`, measured from the later of completion time and last activity), it asks node to stop it (`session.stop` with `retire`, `node/retire.go`):
the Agent process quits (Ctrl+C twice, up to three rounds, until the engine no longer shows the Agent in its pane) and **its terminal stays**: the tab keeps the shell the Agent ran in, ending with Claude's "Resume this session with: …". Persona never closes an Agent's terminal on its own (#4754, `docs/integrations/engines.md` "Agents run in a terminal"); an Agent that does not quit is reported (`not_stopped`) and left running, never closed to make it go.

**What stays**: to-do Agent record (machine, session id, directory) remains, not released; node's launch information (launcher, directory, model, hub `node_sessions`), transcripts and the terminal remain.
Results still read from transcripts (receipts, `agent_read`, chat page); Unread Agents may also stop.

**How to reuse**: a stopped Agent is read-only (#4754, `docs/integrations/engines.md` "Agents run in a terminal"): a message to it—`agent_send`, the task's card (`route`), the chat page—is refused (`agent_stopped`), nothing typed. The user brings it back with **Resume** on its terminal page, in the shell it left when that is still there (else a new tab), with its original launcher, directory and workspace:

| Agent | Resume method |
| --- | --- |
| Claude Code | `<launcher> --resume <id>`, with original permission mode, thinking effort and model |
| Codex | Launcher arguments (with original model substituted) `resume <id>`, through `personad codex-start` |
| Compatible Codex forks | `<launcher> resume <id>` |

When every Agent of a task has stopped, the user's message on the task's card (`route`) or the task's **Retry** starts a new Agent for it instead (`assistant/tasks_successor.go`): on the computer, in the directory and with the launcher of its latest Agent, linked to the to-do, its first message the user's after who worked on the task before and that Agent's last reply; the `routed` feed line carries `new_agent`. Persona's own follow-ups (a supervisor's rework, relayed answers to decisions, acceptance or conclusions) start nothing and are refused (`route_agents_stopped`).

When a resumed Agent starts a turn, its completed to-do (a chat-dispatched task it still belongs to that the hub closed: `done_by` `auto` or an accepted `review`; user-completed and cancelled tasks stay completed) reopens, as **Reopen** does (`reopened_at` recorded): the task shows as in progress, the turn's end gets its interrupted or done receipt and notice as usual, and completion is judged again (#5892). If the to-do is completed again, the Agent stops again after 3 minutes idle.

A cancellation stays final whether the Agent receives a user message, an `agent_send`, or continues after a background job, before or after its idle stop. It produces no new task receipt, completion judgment, supervision signal or automatic triage follow-up while the to-do stays closed. This also applies to older cancellations stored as `done_by = review` with a `cancelled` supervision ledger. The user can still explicitly **Reopen** the task. Cancelling a task stops its Agents right away, working or not (`session.stop` without `retire`, `assistant/supervise_leader.go`), keeps their terminals and archives them; a session with no terminal (another tool's, an engine that runs Agents itself) is closed as before.

**Do not stop**: working, waiting for user (questions, plans, permissions, any dialog, pending cards), unknown engine state; queued messages, background shells, running sub-Agents, `/loop`, listening ports (development servers); linked to another unfinished to-do; assistant chats; sessions managed by other tools (external Codex app-server, runtime, daemon, pi) or by an engine that runs Agents without a terminal (Paseo, Cindy); not started by Persona (the user's own Agents are theirs to stop); Agents other than Claude Code, Codex and compatible Codex forks.
node rejects these (`not_retirable`), assistant records them and does not ask again for 10 minutes if Agent unchanged (`taskCloseRetry`, then retries because node may have upgraded). Old nodes not recognizing `session.stop` are likewise treated as refusals, so nothing is closed while the hub is updated first; after the node upgrade, stopping resumes within at most 10 minutes. A node since #4754 answers an older hub's `session.retire` the same way: it stops the Agent and keeps its terminal.
Agents linked to no task (user-created, `agent_start`, inspection sessions such as herdr-leader) are not managed by the finished-task rule; the idle rule below covers the ones Persona started.

**Idle Agents stop too** (`assistant/tasks_idle.go`, #2784): in the same minute loop, an Agent Persona started (including a stopped one a message resumed, `agent_send` or the chat) that has been still for `idle_close_hours` (assistant setting, default 12, `0` turns it off, `GET`/`PUT /api/v1/assistant`) is stopped like a finished task's, by the same checks and the same `session.stop`, and keeps its terminal. The idle time counts from the later of its last activity and when the hub first saw it running, so a freshly resumed Agent is not stopped at once (and after a hub restart the clock restarts). Besides the "Do not stop" list above, it is left running when its work state is blocked (on the user, another Agent, CI or a deploy) or has a wake due, and when it belongs to an open task, unless that task itself has had no update for three times the idle time (stalled or never accepted). Transcripts, launch state and the terminal stay; it is read-only from then on, and the user's Resume brings it back.

**`/exit` from the assistant**: `agent_send` with only `/exit` or `/quit` stops a running Agent as `session.stop` does (its tab stays, holding the shell) instead of typing it in; to an Agent that is not running it does nothing, so a stopped Agent is not resumed in a new tab only to quit there.

**Terminals stay** (`node/personatab.go`): every tab Persona opens for an Agent carries the herdr pane token `persona_tab` (the session id when known). When its Agent exits, on its own (`/exit` typed by hand, an API error it gives up on, a launcher that quits) or stopped as above, the tab keeps its shell. Nothing closes it automatically: the ten-minute sweep of tabs left with a bare shell (#851) is gone (#4754). The user closes a terminal like any tab (on the computer, or a space's or tab's menu in the web's terminal list); the user's **Close** and **Archive and close** on a session still close its tab, and so does a finished review's reviewer, an internal helper (`assistant/supervise_autoreview.go`). Guards: `assistant/terminal_guard_test.go` pins the functions that ask a node to close, `node/terminal_guard_test.go` the functions that close a pane.

## Closed sessions archive themselves

#3618 (`assistant/agent_archive_auto.go`). A stopped or closed Agent stays in the lists as not running, so after a few weeks most of the list is finished tasks' sessions that no longer run and the Agents that matter are hard to find. Every five minutes, in the loop that stops Agents, the manager archives a session when all of these hold:

- it is **closed**: its Agent runs in no host (its terminal may still hold the shell it ran in, #4754): no `pane_id`, no `host`, and it is neither working nor starting. The status does not decide it. A closed session reads `offline`, but just as often `interrupted` with state `unknown`: a node that restarts marks the sessions it had running in a pane as interrupted so the apps offer **Continue**, the mark stays until a message resumes the session, and the unified state has no value for it. Some keep the `idle` or `unknown` their host last reported. A session another tool lists (`source_kind`) counts as closed only when that tool says `offline`;
- it has been **idle for `archive_closed_days`** (assistant setting, default 3, `0` turns the pass off, 0–3650, `GET` / `PUT /api/v1/assistant`), counted from the latest of its last step, the moment its latest to-do was done, and the last time its archive state changed (so a session the user restored is not taken straight back);
- it is **on no to-do, or every to-do it is on is done**.

It uses the archive the apps use ("Agent session archives" in `docs/protocol/protocol.md`): the session moves under Archived, nothing is deleted, the tool that owns it is asked to archive it too where it can, and new activity (the user's Resume) restores it for good. At most 20 sessions are archived per pass, so a long backlog clears over a few passes.

Never archived by this pass: a session still in a host (a pane or an engine host), including one whose state the host cannot tell (`unknown`); one working, starting, or with background commands, subagents, workflows, a `/loop` or a server running; one with a card waiting for the user or queued input; one the manager is to wake or continue, or that waits on something the manager follows (`work.phase` `blocked`, or `work.wake_at` set); one linked to an open to-do; an assistant conversation; a review's reviewer; a subagent's row; a session another tool owns (`source_kind` set: archiving it would also move it in that tool); with no to-do, one whose last reply asks the user something nobody answered (`awaits_reply`). Computers that are not connected are skipped, and nothing runs until the to-dos are loaded, since they say which sessions open tasks count on. Each candidate is looked at again just before its archive is written.

## Nobody is working on this

#3618 (`assistant/tasks_orphan.go`). An open task can lose its Agent without anyone noticing: the Agent ended on a model error nothing retries and its tab was closed, the user closed the tab, or the computer went offline. The task then still reads as in progress. Once a minute the manager looks at every open to-do that has Agents; the to-do is **orphaned** when every active Agent on it is gone and nothing pending brings one back.

An Agent is gone when its computer is not connected, the computer no longer lists the session, or the session is closed in the sense of "Closed sessions archive themselves" (no pane and no host, not working or starting, whatever its status reads: `offline`, `interrupted`, `idle` or `unknown`). It is not gone, whatever its status, when it is an assistant conversation, is starting, has a card waiting or queued input, has a wake or continuation pending or waits on something the manager follows (`work.phase` `blocked`, or `work.wake_at` set), or waits out a subscription usage limit.

`GET /api/v1/todos` then carries `orphaned: {"reason", "since"}` on the to-do, and the apps are told to read the to-dos again (`{"type":"todos"}`) when it appears, changes reason or goes. `since` is when the manager first saw it so (it restarts with the manager). `reason` is the first that applies to any of its Agents:

| `reason` | Meaning |
| --- | --- |
| `error` | An Agent is closed and its last turn ended on a model error (`turn_error`) that nothing is set to retry |
| `offline` | An Agent's computer is not connected. Reported only after the computer has been away for 10 minutes, so a dropped link or a node restart flags nothing |
| `closed` | The Agents are not running: stopped by the finished-task or idle rule ("Stop Agents of completed tasks"; their terminals stay) or closed by the user, and nothing is set to wake them |

Not orphaned: a done to-do; one with no Agent yet (not started, or its start failed: "Remedying a start"); a supervised task waiting for its review or for the user's decision, which waits on them and not on an Agent. A to-do whose computer is connected but could not be asked this minute keeps what was found before.

The assistant's snapshot says it on the task's line, and a supervised task's supervisor gets the `orphaned` signal once (`docs/assistant/unified-entry.md`, "Supervision": the supervisor loop's signals). Clients that do not know the field show the to-do as before; showing it on the task card and row is each client's own work: the web (`docs/web/web.md`), Android (`docs/android/android.md`, "Closeout, decisions and tasks nobody works on") and the iOS app (`OrphanedLine`, `docs/apple/ios.md` "Closeout, orphaned tasks and answerable decisions (#3612, #3618, #3804)") do.

## Decision records

A standing authorization answer records an Agent decision naming the grant, original user words and source. It is
committed in the same transaction as the hook's resolved question or plan, before the answer is delivered. It is not
presented as a fresh user click. The grant itself is managed through the main conversation's `persona_settings` key
and the list/delete API in [Unified entry](unified-entry.md#standing-authorizations); established task decisions keep
their provenance even after that grant is revoked.

The owner's own decisions (`source` `card`, and the `manual` ones made by choosing a decision's option) are also what
a suggested rule is counted from: after the same go-ahead three times in 14 days, the next decision offers to make it a
standing authorization
([Unified entry](unified-entry.md#a-rule-after-the-same-answer-three-times-4929)).


The costliest long-task mistake is an Agent forgetting a decision already made: asking again or silently overturning it (#1618). Decisions scattered across Agent chats disappear when switching Agents or compacting, so collect them by to-do:

- **One decision** = question + choice + reason + time + provenance (asking Agent, answering card).
- **Automatic**: when user answers Claude Code's choice question in App (`question` card, `AskUserQuestion`) and the Agent is linked to an unfinished to-do, record each answered question (`source = "card"`; hub emits `interaction.resolved`, assistant records; nothing recorded if assistant disconnected). Do not record authorization, plan approvals, terminal dialogs or ignored cards; duplicate reports of a card record once.
- **Manual**: **Decisions › Record one** in to-do details.
- **From the Agent** (#5279): an Agent on an open to-do has two MCP tools of its own (`mcp/todo/`, `agentToolNames` in `assistant/agent_control.go`). `todo_decisions` gives the effective decisions with who made each (`by`: `user`, or `agent` for `agent` / `outcome`), to reread after compaction; `todo_decision_add {question, choice, reason?, supersedes_id?}` notes a call the Agent made (`source = "agent"`, its machine and session as provenance), at most 10 in 10 minutes per Agent; it may replace an Agent's decision, never the user's (it is told to ask them). The to-do is always the one the calling Agent works on (node passes its pane's session, as for `report_to_supervisor`); an Agent cannot read or write another to-do's decisions, and outside an open to-do both say there is none. Handoff context marks these as the Agent's, not the user's.
- **Supersession**: a new decision can **Replace** an earlier one (`supersedes_id`), keeping the old one struck through; only unsuperseded decisions are effective. PATCH can mark/undo later corrections. Only earlier decisions in the same to-do can be replaced, preventing cycles.
- **Hand to Agent**: when `POST /api/v1/sessions` `prompt` or `POST …/messages` `text` carries `todo_id` (all clients' handoff does), hub asks assistant (`assistant.todo_handoff`); assistant prepends effective decisions as `<persona-context kind="context" title="待办 · <title> · 已定的决策">` ("To-do · <title> · Established decisions", prompt `server/internal/prompts/todo/decisions.md`), no client change needed; send unchanged without decisions. On read failure (database error), still send and only log.
- Recording/superseding updates to-do `updated_at` and broadcasts `{"type":"todos"}` so clients refetch decisions.
- iOS / Mac (`apple/Persona/Views/Todos/TodoDecisionsSection.swift`, model `TodoDecisionsModel`, wire `apple/Shared/TodoDecisions.swift`): the same Decisions section in to-do details, under the notes: **Add** records one, **Revise** records one that replaces it, the row's ⋯ marks it as replacing an earlier one or undoes that, **Full History** shows the replaced ones struck through. Read again whenever the to-do's `updated_at` changes; hidden on a hub without the route (route-level 404).
- **How many show** (#6447, web `DecisionsSection` with `shownDecisions` in `web/src/lib/todos.ts`; iOS `TodoDecisionsLogic.shown`): the first five, oldest first, with **Show all N** under them and **Show the first 5** to go back; the header's fold-all button (the Agents title row's) folds the list away and **Expand all** shows it whole. The header's count is the decisions in effect, whatever is shown, and folding asks nothing of the hub. Nothing is stored: each to-do opens at the first five, and recording or revising one shows the whole list so it is in view.

- Android (`android/feature/agents/src/main/kotlin/persona/feature/agents/TodoDecisions.kt`, wire `TasksApi.todoDecisions` / `addTodoDecision`, source `TodoDecisionsSource` that `TasksStore` implements; #1853): the same Decisions section in to-do details, under the notes: **Add** records one, **Revise** records one that replaces it (its question filled in, the earlier choice kept struck through), **Full history** shows the replaced ones struck through, and each row says when and where it came from. Typed words are asked about before the form is dropped. Read again whenever the to-do's `updated_at` changes; hidden on a hub without the route (route-level 404). So a question nobody answered can be answered on Android too ("Questions nobody answered"). Not on Android yet: marking an existing decision as replacing an earlier one, or undoing that (the iOS row's ⋯, `PATCH …/decisions/{did}`).

## Concerns

Something the owner raises in the main conversation and wants an answer to is a **concern** (#3561, `docs/design/proposals/owner-at-a-glance.md` G5 and H2): a to-do with `kind = concern`, so it is a record with a status that nothing forgets (`server/internal/assistant/concerns.go`). It reuses the to-dos and their decisions, no store of its own.

- **Recorded** by the main conversation, `todo_create {title, notes?, kind: "concern"}` (only the main conversation may; `origin` is the main conversation, no agent needed, nothing to confirm), or by hand, `POST /api/v1/todos {"title", "kind": "concern"}`. It needs the hub's database (without it a concern could never be reported, so it is not recorded).
- **Closes only after its report**: the main conversation tells the owner the outcome in its reply and, in the same reply, calls `concern_report {id, report}` with the words it told them. That writes a decision of source `reported` (`question` the concern's title, `choice` the report) and closes the concern (`done_by = reported`, `done_reason` the report) in one transaction (`db.ReportConcern`): there is never a close without its report, nor a report on a concern left open. By hand: `POST /api/v1/todos/{id}/decisions {"choice", "source": "reported"}`.
- **Never closes on its own**: the hub's judge ("Automatic completion"), a review or cancellation, a failed start, `todo_complete` and `PATCH {"done": true}` (an app, an extension) all leave it open (the PATCH answers 409, the tool says to report instead). The store refuses each of them for `kind = concern`, and memory refuses a row that would close one without `done_by = reported`. Reopened (`PATCH {"done": false}`, `todo_reopen`), it needs another report; deleting it stays the owner's choice.
- **Extensions**: `todo.changed` carries `kind: "concern"` (created, reopened, closed by its report), and each report is a `todo.decision` with `source: "reported"`, so a work-log extension can keep the concern in its record and show its answer.
- `todo_list {kind: "concern"}` lists the open concerns; `todo_list` / `todo_get` mark them `concern`.
- Clients: `kind` is on the to-do's JSON (left out for others), `done_by` `reported` on a closed one; clients that do not know them show it as a to-do. The SOP rule (an open concern sits in Working while a task of it runs, else in Other open, labelled Concern and not folded) is on the hub (`todo_triage.go`: never shelvable, so a leader's stuck report and the counts see it right) and the web (`web/src/lib/todo-triage.ts`, `web/src/views/Todos.tsx`): the shared fixtures cover it, an open concern keeps a row of its own, and every concern row has the existing neutral tag. iOS and Android follow in their own PRs (#3582), and are not claimed here. The secretary's prompt (P1, #3609) has the main conversation record a concern whenever the owner raises one, and report it only after telling the owner the outcome.

## Questions nobody answered

(#1617, `assistant/ask_todo.go`.) When a card of the assistant's own `ask_user` **expires** unanswered (2 hours, `askUserWait`), the question becomes a to-do, so it waits where the owner looks and a late answer still reaches the conversation that asked. Only an expiry does this: a dismissed card, one withdrawn because the user wrote in the chat (`replied_in_chat`), an answered one and a conversation that stopped waiting behave as before. Agents' question cards keep their own paths.

- **How an expiry is told apart**: the manager's interaction queue ends the card (`await`, history status `expired`) and hands the question a dismiss; `askOnPhone` reads the history and marks that dismiss `reason: "expired"` (`proto.DismissedExpired`; a history that says nothing, or whose end was not written, counts when the card's time is up), which only the manager sets (the apps' answers have their `reason` dropped, `fleet_routes.go`). A hub that keeps the cards itself sends a bare dismiss; it counts as an expiry once the card's `expires_at` has passed.
- **The to-do**: id `todo_ask_<the card's id without ix_>`, so the same card never makes two (a second hand-over, a restarted assistant, two assistants on one store: the id is the primary key). If its record (below) can't be written, no to-do is made and the tool says the user did not answer, as before. Title: the first question. Notes, in the owner's language: when and in which conversation it was asked, each question's options with their descriptions as written (a "(Recommended)" in a label stays), and how to answer. No Agent and no `origin` (#1852, #1909): it is not a task of the asking conversation, which is kept in its record (below) instead, since an `origin` is what makes a to-do a task for the hub and every app. So no app lists it in that conversation's task dock or task board (where it would read "Starting the agent" and offer a **Message** that can't go anywhere), and `task_plan` can't reuse it as a `todo_id`. Handed to an Agent (**Hand to Agent**), it is like a to-do of the owner's own: the Agent works on it, but its turns post no receipt, no done judgment closes it, nothing reopens it or retires the Agent as a finished task's; only the owner's decision, closing or deleting ends the question. Question to-dos made before had the asking conversation as their `origin`; migration `0453_ask_todo_no_origin.sql` clears it, and the snapshot's task list skips question to-dos by id all the same. The live snapshot lists it on a line of its own ("asked with ask_user, nobody answered, waiting for the user's call": don't ask again, don't go ahead), not among the tasks; the next briefings list it under "Can wait" (`laterQueue`, the same queue Agents' non-urgent questions use) until it is closed or deleted, or for 7 days as that queue keeps anything. **Handled** on that row (the web app's `brief` item, the Lark briefing card) closes the to-do as `PATCH done: true` does ("Closed without a decision" below; #1854), so the snapshot stops holding the question back; a to-do that can't be read or closed makes the press fail (503, an error toast) and the row stays. The apps show it as an open to-do; there is no new client UI.
- **The record**: what the message needs (the card, the asking machine and conversation, the questions, when) and whether it was told are kept in the assistant's settings (`assistant.ask_todos`), not on the to-do (no new column); records older than 30 days go (such a to-do is an ordinary one from then on). The record list is one setting, written whole: two assistants on one store dedupe the to-do by its id, but the last to write the list wins.
- **The answer goes back**: the first decision the owner records on the open to-do by hand (`POST /api/v1/todos/{id}/decisions`, the apps' decision form; `source = "manual"`) is claimed (written before it is sent, so it goes once; a claim not followed by the send within 5 minutes, say the assistant restarted in between, no longer holds, so the next decision goes) and sent to the asking conversation as one new message (`prompts/assistant/ask_answer.md`: "you asked … at MM-DD HH:MM; the user decided …"), through the queue `conversation_send` uses (now, or after its turn; kept across a restart; in the background, so the request that wrote the decision does not wait on the node); a conversation that is gone gives way to the main conversation of now. The to-do then closes. With several questions asked, the first decision goes and closes it; the message lists every question and says to ask again what the decision did not cover. A reply in the Lark topic the to-do is bound to is its decision too ("Replies in the thread"): the same message goes to the asking conversation (from the record, as the to-do has no `origin`) as the bot's own send (so the answer comes back into the topic), never to an Agent, and the to-do closes; if no send goes through, the claim is given back. A second decision (the to-do is closed by then) sends nothing.
- **Closed without a decision**: closing it (`PATCH done: true`, or **Handled** on its "Can wait" row) or deleting it tells the asking conversation once that the question was dropped (the same prompt, its "dropped" form). Reopening and closing it again says nothing more; a decision recorded after a reopen still goes back once.
- **The Lark card** of the expired question closes saying "Moved to to-dos" instead of "Ended".
- **Restart**: an `ask_user` waiting while the manager restarts is still cancelled (it lives in memory, #26): it makes no to-do.
- **Asked without waiting** (`wait: false`, #4928; `docs/assistant/assistant.md`, "Asking without holding the turn"): its card's expiry makes the same to-do with the same record, deadline handling and briefing row. Since no tool call is waiting to hear it, the asking conversation is told in a message that the question is now this to-do (or that its recommended options were taken by default); the owner's later decision, or closing the to-do, then reaches the conversation as above. Such a card survives a manager restart, and one whose time ran out while no manager ran becomes the to-do when the next one starts. One exception: when the owner wrote in the asking conversation while the card was up, its expiry makes no to-do and takes no default, since what they wrote may have been the answer; the conversation is told and asks again if it still needs one.

## Waiting for the owner

(#2056, `assistant/todo_ask.go`.) A to-do whose result waits for the owner carries that ask on itself, so the apps can show it in the to-do list and take it with one tap, not only the briefing and the Lark card.

- **`ask` on `GET /api/v1/todos`**: `{"outcome"?, "verdict", "recommend"?, "asked_at"}` (a decision carries more, "Decisions the owner can answer" below), the same rows and words as a `brief` item's `accept[]` (`docs/protocol/protocol.md`, "Tasks and the chat feed"), read from the same acceptance book: a deployed to-do's "Please verify" (no `outcome`), or a supervised task's conclusion (#1226: `outcome` `done`, `cannot` or `decide`). `verdict` is the verdict line as its Lark card says it, in the request's language (the reason is as the review wrote it); `recommend` only on a decision (`decide`) that recommends an option; `asked_at` the round, which `POST /api/v1/todos/{id}/accept` takes. A to-do with nothing waiting has no `ask`: never asked, verified, taken, acknowledged, asked before its latest reopen, or a decision the review moved on from (rework, cancelled) or whose task closed. A client that does not know the field ignores it.
- **Taking it**: `POST /api/v1/todos/{id}/accept {"asked_at"}` stays the one way, as the briefing's Accept button: a decision's recommendation goes to the task's Agent and is recorded in its decisions (the same path as the Lark card's "Take the recommendation"), a conclusion that only tells is acknowledged, a deployed to-do is verified. An `asked_at` from an earlier round is 409 "already handled" and takes nothing; 502 when the recommendation could not reach the Agent (nothing taken).
- **Direct completion of a decision** (#3038): the owner may end an open `needs_user` task without taking its recommendation. Use the existing `PATCH /api/v1/todos/{id}` with `{"done":true}` → `{"todo": Todo}` (200, `todo.done_at` set, `done_by` / `done_reason` cleared); carry its `manager` in `X-Persona-Manager` as for any to-do write. This is a completion-state edit, not a round-specific acceptance: no `asked_at` is required and no new endpoint is added. The decision disappears from `GET /api/v1/todos[].ask`, the briefing's pending `accept[]` and the board; historical feed cards remain history. A later Accept on that decision returns 409 and sends nothing. Completion itself never sends a recommendation or message to an Agent and never resumes a closed Agent. It keeps existing outcome recording and idle cleanup ("Stop Agents of completed tasks"): eligible task Agents stop, keeping their terminals, after both completion and inactivity reach 3 minutes; working or blocked Agents are not forcibly stopped. Later Agent activity does not reopen a user-completed task. Explicit `PATCH {"done":false}` reopens it but does not revive its earlier ask. Automatic rework and recommendation sends recheck completion/reopening after slow session/device lookups, before dispatch; ordinary user messages to an Agent retain their existing behavior.
- **Don't handle and Later (web, #4808)**: the Needs you row offers both actions beside the decision choices. Later hides only this browser session's copy of the current review. Don't handle persists a dismissal of the current review through `POST /api/v1/todos/{id}/decision-dismiss {review_at}`; it never completes the task, chooses an option or sends a message. The returned `dismissal_id` is the Undo receipt: `POST /api/v1/todos/{id}/decision-undo-dismiss {review_at, dismissal_id}` restores only that dismissal. `GET /api/v1/todos[].decision_review` carries `review_at` and an optional `dismissal_id`; a newer review naturally appears again. A dismissed decision cannot be accepted by a stale page or taken by its deadline. Both writes require a full device role and the exact current review; stale rounds/receipts return 409. Old `needs_user` reviews without an `ask` remain visible with their original `reason` or `note` and these actions, not invented options or a fabricated acceptance timestamp. iOS and Android are unchanged in this web-only client fix.
- **The push**: a review's `needs_user` with a `recommend` (`task_review`) is pushed to the owner's devices once (not when it can wait: "Decisions that can wait" below), besides its Lark card and whether or not the bot is on: a `decide` notification (`notify.request` kind `decide`, `docs/protocol/protocol.md` "Bus") to the devices that take "needs you" pushes (quiet hours make it silent, like a card's), opening the conversation the task came from. Its APNs payload:

  ```jsonc
  {"aps": {"alert": {"title": "Conclusion: <task>", "subtitle": "Persona", "body": "🤔 Needs your decision: <reason>\nRecommended: <option>"},
           "sound": "default", "thread-id": "<origin conversation>", "category": "TODO_DECIDE", "interruption-level": "time-sensitive"},
   "machine_id": "<the assistant's machine>", "session_id": "<origin conversation>",
   "todo": {"id": "<to-do id>", "asked_at": "<RFC 3339, the round>", "recommend": "<option>", "manager": "<manager id>"}}
  ```

  `todo.manager` is the manager whose to-do it is (`assistant` for the assistant the hub starts), as the merged list stamps each item's `manager`; OK names it in `X-Persona-Manager`, so it reaches that manager whichever one is the default. All rounds of one to-do share an `apns-collapse-id`, so a later round's push takes the earlier one's place. Through the push relay `category` and `todo` are sealed with the rest (`docs/operations/push-relay.md` "Encryption"). On the WebSocket (`ws_notify`) it is a `notify` of kind `assistant` with the same `todo`, so a client that does not know decisions shows a plain notification. The app's OK action on `TODO_DECIDE` calls the accept route with `todo.asked_at`. No push for a decision without a recommendation (nothing for OK to take), for a task from a health conversation (the lock screen says nothing of those) or a muted conversation; a deployed to-do's "Please verify" and conclusions that only tell are not pushed either.
- **The supervisor** is told what went out. With a Lark card, as before (don't ask again), plus that a push with OK went too. With the bot off it still asks the owner as before (the hub taking a push says neither that a device got it nor that its app shows OK), and is told that OK on the push may take the recommendation first.
- **Clients**: the web shows the ask on the to-do's row, its page, the main chat's task card and the task panel, with the one button that takes it (`docs/web/web.md`, "Waiting for you"); a stopped to-do with an open ask sorts with Awaiting review. The iOS / Mac / Watch part (the to-do row and detail, the `TODO_DECIDE` action) is not built yet; Android shows the ask in the Needs you tray and on the task's page (`docs/android/android.md`, "Closeout, decisions and tasks nobody works on").
- Not done here: the push is not withdrawn when the decision is taken elsewhere (an OK on it then answers 409, "already handled"); the watch's answer-only credential can neither read `/api/v1/todos` nor call the accept route.

## Decisions the owner can answer

(#3804, `assistant/decision.go`.) A supervised task reviewed `needs_user` used to reach the owner as a title and "waiting for your decision", often for a task they had not started themselves. Now only a decision reaches them, it stands on its own, and it never rots.

- **A decision or nothing**: `task_review` with `needs_user` is refused unless it carries `why_owner` (`irreversible`, `visible_to_others`, `priority`, `acceptance` or `only_owner_knows`: why only the owner can decide), `reason` (one sentence: what is to be decided), `recommend`, `options` (2 to 4 of `{label, leads_to}`, the recommended one first; the hub moves it first if the review did not) and `cost_of_waiting` (one sentence). The refusal names everything missing and says what to do when nothing needs the owner: decide it and send the Agent on, send the work back, or close the task. A task that only waits for something is not a decision. A third `rework` is refused the same way unless it carries these fields, in which case it becomes the decision. The ledger's review keeps the fields (`supervision.reviews[]`), with the decision's `deadline` and `reversible` as the review gave them (absent when it gave none, and on reviews from before they were kept), so they can still be read once the decision is made.
- **Self-contained**: the hub, not the model, adds where the task came from and where it stands, read when the decision is asked. `from`: the origin conversation (`main` for the main chat, else its `title` when it has a name of its own), the to-do's creation time, and the owner's message that led to the work: the one the task's brief froze at dispatch (`request`, with its time; `docs/assistant/unified-entry.md` "Briefs"), else, for a task whose brief does not know, the first message the owner typed to the task (the first `routed` chat-activity entry with neither `from` nor `relay`, from before the task's first review). A to-do with no such message is `by_assistant` (with `started_by` when its brief says who: `assistant`, `leader`, `routine`, `hub`) and reads "Started by the assistant on <date>", never a guess. `stands`: the latest Agent's closeout when it wrote one (what it did, else what is missing, what it waits for, what it verified), else its work line. Both are on the to-do's `ask`, in the decision push and on the Lark card, next to each option with what it leads to and the cost of waiting.
- **A default and a date**: a decision whose `why_owner` is not `irreversible` or `visible_to_others` gets a 24-hour deadline with `reversible: true` unless the review sets its own, and "Decision deadlines" below then takes the recommendation. `irreversible` and `visible_to_others` are never taken by default (a review that says `reversible: true` for one is refused); after the recheck below they are raised to the owner again once a day (the decision push, and the card when there was one).
- **Old decisions are checked first**: a decision that has waited 24 hours goes back to its supervisor once as supervision signal `recheck`, with the decision as it was asked: confirm the facts still hold and re-issue it, or close it. The daily raise to the owner waits an hour for that. Kept on the ask (`recheck_at`, `raised_at`), so a restart does not repeat it.
- **The backlog**: an open task in `needs_user` with nothing the owner can answer (no ask, or one that recommends nothing) goes back to its supervisor once as signal `undecidable`: restate it as a decision, or close it. Kept on the review (`restate_at`). It waits ten minutes after the review or after an answer, so an ask being written or an answer on its way to the Agent is not mistaken for one.
- **"I can't answer this"**: besides its options every decision takes three fixed answers through the accept route (`{"response"}`), and none is ever a default: `decide_yourself` ("You decide"), `not_what_i_asked` ("This isn't what I asked for") and `explain_first` ("Tell me the background first"). Nothing is taken; the task's supervisor gets signal `owner_cannot_answer` once, with the answer and the decision, because the answer says the supervisor was not aligned with the owner.
  - `decide_yourself`: the task stops waiting for the owner and the supervisor decides, telling the Agent and stating its assumption. Asking the same question again is refused. When `why_owner` was `irreversible` or `visible_to_others` the step is not the supervisor's to take: the task stays `needs_user` and the only review accepted is the same decision restated as a plain approval with exactly two options.
  - `not_what_i_asked`: the task stops waiting for the owner and its Agent gets no automatic follow-up (continue, wake, CI follow-up; `workGuard`) until the supervisor reviews the task again (re-scoped with `rework`, `cancelled`, or the link to the owner's request explained in a new decision) or sends its Agent on.
  - `explain_first`: the decision stays as it is, no longer taken by default, and the supervisor re-issues it with a short background.
  - Counted: each is a work event `owner_cannot_answer` and `GET /api/v1/agents/work/stats` sums them per supervisor conversation (`docs/assistant/agent-work.md`, "Evaluation").
- **Choosing an option**: `POST /api/v1/todos/{id}/accept {"asked_at", "option"}` with the recommended label is the plain OK; another option goes to the task's Agent as the owner's choice with what it leads to, is recorded in the to-do's decisions and ends the decision. The Lark card has a button per option and one per fixed answer. The `decide` push's `todo` also carries `options` (the labels, the recommended first) and `responses`, so an app can offer them from the notification; its body lists the background, the options and the cost of waiting.
- **Answered in the chat** (#6470, `assistant/task_decided.go`): the owner often answers in their own words in the main chat instead of on the card. The main conversation, or the task's supervisor, records that answer with the assistant tool `task_decided` (`todo_id`, `option`: one of the waiting decision's labels, `said`: the owner's words, `told_agent`). Without `told_agent` the option is taken exactly as the accept route takes it (sent to the task's Agent, then recorded). With `told_agent: true` (the answer already went to the Agent with `agent_send`) nothing is sent again. Either way the decision ends as a card answer ends it: the ask is answered and leaves Needs you, its deadline default and daily raise stop, the supervision leaves `needs_user`, the to-do's decisions get a `manual` row with the conversation as its source and the owner's words as its reason, and an `owner_decided` event is written. An option that is none of the decision's, a conversation that is neither the main one nor the supervisor, and a decision no longer waiting are refused. Relaying the answer with `agent_send` alone used to leave the decision waiting.
- **A decision is not replaced by "Please verify"**: while a decision waits, a turn of the task's Agent that says "deployed" (or a held deploy landing) no longer starts a "Please verify" round in its place; and a review that arrives while such a round is still being written keeps its decision, the round giving way. Before, either order left a `needs_user` task with no `ask`, passed by the supervising assistant as if it were a deployed task.
- **iOS** (`DecisionRow`, `docs/apple/ios.md` "Closeout, orphaned tasks and answerable decisions (#3612, #3618, #3804)"): the same row as the web's in the Needs You tray and on the task board, answered through the accept route with `option` or `response`; an option of an `irreversible` or `visible_to_others` decision takes two taps. The `TODO_DECIDE` push's OK and its `options` / `responses` are not actions in the app yet.
- Not done here: offering the options from the decision push on Android (its notification opens the conversation) and on iOS. A task that only waits is parked: "Parked tasks" below.

## Decisions that can wait

(#4930, `assistant/decision_wait.go`; `docs/design/proposals/main-chat-availability.md` section 4b.) A decision nobody needs today used to ring the owner's phone the moment it was raised. A supervisor may now say that it can wait, and it arrives with the next briefing instead.

**The default, in one sentence**: a decision is pushed the moment it is raised, unless its supervisor marked it as able to wait and a daily briefing will bring it to the owner in time. Without a daily routine with `facts` nothing changes. With one, turning `facts` off on the routine (or the routine off) brings back "every decision is pushed"; there is no switch of its own.

- **The field**: `task_review` with `needs_user` takes an optional `can_wait: true`, set by the supervisor when nothing is due within 12 hours and waiting costs little. `cost_of_waiting` stays the sentence the owner reads; `can_wait` is a boolean beside it (as `user_check` and `reversible` are) because the hub only has to know push now or not, and a sentence cannot be tested. Absent or `false`: pushed as before. On any other verdict it is refused.
- **Held**: a decision that can wait gets no `decide` push and no Lark card when it is raised. It is the to-do's `ask` at once, so Needs you in the apps and the board show it, with its options and fixed answers as any decision; its `ask` says `for_briefing: true` while nothing was pushed for it. The ask is kept with `for_briefing` and `no_card` in `assistant.acceptance`; a hold that cannot be written is not kept in memory only, the decision is pushed at once.
- **Always pushed**: `can_wait` is ignored, and `task_review`'s answer says why, when `why_owner` is `irreversible` or `visible_to_others`, when the review's own deadline says `reversible: false`, when the deadline is less than 12 hours away, and when no briefing comes in time. In time means: the next run of an enabled daily routine with `facts` (the routines "Questions that can wait" count on, `docs/extensions/bots.md`) is within 24 hours and at least 12 hours before the decision's deadline. The deadline is counted from when the decision is raised, as for any decision, so with the default of 24 hours a decision is held when a briefing is due within 12 hours; a review that can wait longer gives a longer `deadline`.
- **In the briefing**: a run of a routine with `facts` lists it under "To verify" with its recommendation and **Take the recommendation**, where every open decision already is (`docs/extensions/bots.md`, "Morning and evening briefings"). The hold ends (`for_briefing` cleared, for the round the run listed) once that briefing reached the owner: the run ended normally and its finished push with the counts was sent (the run's `brief` item lists every row), or its Lark card went out with the decision's row on it. A run that was only sent, failed, or whose card had no room for the row does not end it. A decision a briefing brought to the owner stays card-less: the briefing and the to-do are where it is answered.
- **Never lost**: a held decision is pushed after all as soon as one of three things is true: no such routine is on any more, 24 hours passed since it was raised, or its deadline is 11 hours away (an hour after the latest briefing it could count on, so the owner has at least 11 hours to answer before a default is taken). Checked once a minute with the deadlines. The hold ends when the hub took the push; a push it did not take is tried again a minute later. The decision's Lark card is then due as when a decision is raised: posted on the next tick of the card retry (within 10 minutes), and tried again for 45 minutes from the push. One the owner hid in the apps (Don't handle) is not pushed.
- **A leader's or the background supervisor's held decision** is not sent to the main conversation when it is raised (`escalated`, `docs/assistant/unified-entry.md` "Leader conversations", "Background supervisor"): nothing went to the owner, and the main conversation is not woken for what can wait. It is sent when the decision is pushed after all; one a briefing brought to the owner is not sent at all. The held decision keeps who raised it (`raised_by` in `assistant.accept`, cleared with the hold), because a background supervisor's task names the main conversation in its ledger; one held by a manager from before that is sent when its task is a leader's.
- **Unchanged**: the 24-hour default of a reversible decision, a deadline the review gives, the `recheck` after 24 hours, `undecidable` and `owner_cannot_answer`. The owner can answer a held decision at any time from Needs you.
- **The supervisor** is told that nothing went out and not to ask the owner itself; when `can_wait` was ignored it is told why and the answer goes on as for any decision.
- Not done here: the briefing lists it among "To verify", where decisions already are, not in a block of its own; the Android app marks a held decision on its card and on its To-dos row (#5802, `docs/android/android.md` "Rule suggestions, held decisions, recommended setup and purpose descriptions") and the Apple apps mark it "Comes with your next briefing" on its row and card (#5803, `docs/apple/ios.md` "Suggested standing rule and held decisions"); the web marks it on the decision's card in Needs you and on the to-do's ask line (#5803, `docs/web/web.md` "Decisions held for the briefing"); nothing counts how many decisions were held; and there is no switch of its own in Settings (above). A hub rolled back to a build from before #4930 drops `for_briefing` on its next write of the asks, and such a decision is then neither pushed nor carded by either build: it is still in Needs you and in the briefing.

## Parked tasks

(#3804, `assistant/parked.go`.) `needs_user` used to park tasks nobody was deciding anything about (waiting for an experiment's scope, for someone else, for a later date), so they sat in the owner's Needs you for days with nothing to answer. A `needs_user` that is no decision is now refused, and a task that waits on purpose says so with a verdict of its own.

- **The verdict**: `task_review` with `parked` is refused unless it carries `reason` (one sentence: what the task waits for) and `waiting_on` (`owner_priority`: the owner has to say whether to do it or what comes first; `someone_else`; `external_event`; `date`). `until` is a duration (`3d`, `36h`, `2d12h`, `90m`) or an RFC 3339 time, 1 minute to 30 days ahead, 24 hours when left out. The refusal names everything missing at once. Only the task's supervisor parks it, as for the other verdicts; a done task, an unsupervised one and a task leader Agent's worker are refused.
- **What parked means**: the to-do stays open with `supervision.state: "parked"` and `supervision.parked: {reason, until, waiting_on, count}`. It is not the owner's to answer: no `ask`, no push, no conclusion card (a decision that was waiting ends), and it is never filed under Waiting on you for being parked. While it is parked its supervisor gets no `stalled`, `idle`, `unjudged`, `orphaned`, `overdue` or `undecidable` signal for it, and the manager sends its Agent nothing on its own (continue, wake, CI follow-up; `workGuard`), since any turn of its Agent ends the parking.
- **At `until`**: one supervision signal `parked_due` with what it waited for: decide, park it again with a new reason, or close it. The time is read off the ledger on every look, so a restart before the supervision message went out loses nothing; once a message carried it (sent, or queued), that is kept on the review (`due_at`) and a restarted manager does not tell it again. The task stays parked until its supervisor acts.
- **Leaving**: one of its Agents starting a turn (the owner or the supervisor sent it something) ends the parking: the state goes back to in progress (or `rework` when rounds were used), `parked` is gone, a `parked_due` still waiting is dropped, and the task is supervised as before. Any other review ends it too. A closed to-do is not parked.
- **Not a place to forget things**: `count` is how many times in a row the task was parked with no Agent turn in between (1 when first parked). Three re-parks are taken; the fourth is refused with the count, and the supervisor is told to close the task or state the real decision for the owner (`needs_user`). An Agent turn starts the count again.
- **The owner hears of one kind only**: a task parked with `waiting_on: owner_priority` is listed in the daily digest's briefs (`docs/assistant/unified-entry.md`, "Briefs") as parked, waiting for their priority call, with its reason. No other parked task is mentioned to them.
- **Kept on the review**: the ledger's `reviews[]` entry of a `parked` review carries `reason`, `until`, `waiting_on`, `parks` (the count) and `due_at`; `supervision.parked` is read off the latest review while the state is `parked`, so there is no new column. The `review` feed item of a parked review has `verdict: "parked"`, the reason as its `note` when the review gave none, `until` and `waiting_on`.
- **Clients**: the web shows "Parked until <time> · <reason>" on the task's In progress row, its To-dos row and its page, and lists it In progress however long it has been still (`docs/web/web.md`). The To-dos page's sections (`docs/assistant/todo-status-sop.md`) are unchanged: a parked task is filed by its other facts. iOS and Android do not know the state yet and show the task as supervised and in progress.

## Decision deadlines

(#3127, `assistant/decision_deadline.go`.) A decision that waits for the owner can carry a recommended default and a deadline, so work does not stop just because nobody answered. Without a deadline nothing changes.

- **Who sets it**: `task_review` with `needs_user` (`deadline`, `reversible`, with its `recommend`) and `ask_user` (`deadline`, `reversible`, and a `recommend` on every question naming one of its options). `deadline` is a duration (`4h`) or an RFC 3339 time, 1 minute to 30 days ahead; a deadline without `reversible`, or without a recommendation, is refused. `reversible: false` is for what cannot be undone: deleting, sending anything to other people, spending money and production changes.
- **Where it is kept**: a task's on its decision in the acceptance book (`acceptAsk.deadline`, `reversible`, `due_at`, `by_default`); a question's in its arguments (as a time) and, once it became a to-do, on its record (`assistant.ask_todos`). The card waits no longer than the deadline. The Lark card and the decision push add a line with the deadline and what it does; on the phone card the recommended option's description says so.
- **At the deadline** (`acceptLoop` looks every minute):
  - **Reversible**: the recommendation is taken the way the owner's OK takes it. A task's goes to its Agent (the message says it was taken by default and can still change) and the task stops waiting for the user; a question still waiting gets the recommended options as the tool's answer, and one that became a to-do earlier has them sent to the asking conversation as a new message and closes. Either way a decision is recorded on the to-do: the question, the option, the reason "taken by default: no answer by MM-DD HH:MM", with `source = "agent"` because it is not the owner's own call.
  - **Not reversible**: nothing is taken. The owner is reminded once (the decision push again, and the Lark card again when there was one; a question's to-do gets a push), and it keeps waiting; the owner can still answer at any time.
- An answer from the owner before the deadline wins as before; a deadline that passes while the hub is down is handled on the next sweep.

## Chat thread

(#5279, step 2: the binding itself) A to-do can be bound to a chat thread, a topic in a group chat or a conversation, so that the thread and the to-do are known to belong together. The binding itself writes nothing to any channel. What the user says in the thread comes back to the to-do ("Replies in the thread" below), and what happens to the to-do is told in the thread ("Posting into the thread" below). `todo.*` events come in a later step.

- **The binding**: `thread` on the to-do, `{channel, chat_id, thread_id, title}` (the first three name the thread, the title is a label). `channel` is a channel id as `internal/channel` names them (`channel.Feishu` = `"feishu"`); it is trimmed and lower-cased before it is kept, so `Feishu` and `feishu` are one channel. For `feishu`, `chat_id` is the chat's id (`oc_…`) and `thread_id` is the `thread_id` the message events carry (`omt_…`), not the thread's root message id (`om_…`). The server does not check them against the channel (it cannot know a thread exists), so the caller must pass the real ones. At most one thread per to-do and one to-do per thread: binding a thread another to-do holds is refused (409, from memory first, finally by the unique index, so a second assistant on the same database cannot slip past it). Binding again replaces the thread; the old one is free for another to-do. A done to-do can be bound or unbound too (it may be reopened, and the user's tidying should not depend on its state).
- **API**: `PUT` / `DELETE /api/v1/todos/{id}/thread` (full role only), "API overview" above. Both move the to-do's `updated_at` and broadcast `{"type":"todos"}`, unless nothing changed (unbinding a to-do that has no thread, or binding exactly what it already has: nothing is written); `GET /api/v1/todos` returns `thread` with each to-do that has one. Editing a to-do leaves its thread alone.
- **Reverse lookup** for the next step (a reply in a thread finds its to-do): in memory, every `Todo` carries `Thread` and `sameThread(a, b)` (`assistant/todo_thread.go`) compares two bindings; from the store, `DB.TodoOfThread(channel, chat_id, thread_id)` (`internal/db/todo_thread.go`).
- **From the Agent**: an Agent on an open to-do has `todo_bind_thread {channel, chat_id, thread_id, title?, todo_id?}` (`mcp/todo/`, with the decision tools; the node resolves its caller the same way, `callerTools`). It binds the to-do the Agent works on and no other: `todo_id`, if given, must be that to-do's own id. A to-do that already has another thread keeps it (changing it is the user's call, the tool says to ask them); the same thread again only updates its title. Outside an open to-do it says there is none.
- Web (`views/Todos.tsx` `ThreadSection`, `lib/todo-thread.ts`): the to-do's page has a **Topic** section under the notes: one line "Lark topic · <title, or the thread id shortened>" (any other channel: "Topic (<channel>)") and **Unbind**, which asks first and then `DELETE`s the thread; the list row of a bound to-do has a small chat mark. No link to the topic is drawn: the binding holds no message id, and the repo has no verified Lark link that opens a topic by `thread_id`. Binding is not on the web: it would need the bot's recent topics, which the hub has no route for, so an unbound to-do says that a topic started in a `/topics` group opens and binds a new to-do, and that an Agent can bind it (the note does not name the tool). The web is always a full-role device, so Unbind is always there. A hub with no thread route (a route-level 404 on the unbind, as `isLegacySpacesRouteError` reads it) loses the section without a word.

### Replies in the thread

(#5279, step 3.) A message from a group chat (the bot event's `chat_type` is anything but `p2p`) never takes the bot's private-chat road: no commands (a text starting with `/` is a word like any other), no answering the question card or the "Please verify" card, never the chat's current target. It goes by its topic alone (`assistant/feishu_thread.go`). The hub hands the assistant only the owner's messages in a topic of a group chat the owner opted in (`docs/extensions/bots.md` ("Topic group chats")); the assistant's own rule here is the second line of defense.

**Using it in Lark**: (1) in the Open Platform console give the bot `im:message.group_at_msg:readonly` (every message then has to @ the bot) or `im:message.group_msg` (all messages in the group, needs the admin's review), and add the bot to a group chat with you; (2) send `/topics` in that group, the bot answers that it is on; (3) start a topic in the group for a to-do and bind the to-do to it (the to-do's `thread`: `chat_id` of the group, `thread_id` of the topic, "The binding" above); (4) what you write in the topic is a decision of the to-do and goes to its Agent, and the answer, the progress card and the Agent's questions and permission requests come back into the same topic, where the buttons (Stop included) work for you alone. `/topics off` turns the group off.

- **Only the owner**: the message must come from a user whose open_id is the paired owner's, else it is dropped without a word (the hub checks it too, "docs/extensions/bots.md" ("Topic group chats"); the words go to an Agent that acts on them, so this is not left to one line of defense).
- **Lookup**: the to-do whose `thread` is `{feishu, chat_id, thread_id}` of the message, in memory (`sameThread`). A message outside a topic (no `thread_id`) is left alone.
- **No open to-do** (the topic is bound to nothing, or to a to-do that is done): one short hint in the topic (`assistant-feishu.thread_unbound` / `thread_done`), at most once per topic in 10 minutes; nothing is recorded or sent, unless the message asks for a to-do (["Opening a to-do from a topic"](#opening-a-to-do-from-a-topic) below). A done to-do is not reopened by a reply.
- **Open to-do**: the words are written as a decision, `source = "thread"`, `source_message = "feishu-<message_id>"`, question "Reply in the Lark topic" (like a reply to the "Please verify" card, which records "Review feedback"), choice the text as said (trimmed, clipped as every decision is). The same message again writes nothing and is not sent on again (the unique index on `(todo_id, source_message, question)`; the bot also takes each message id once). Without the database nothing is recorded and the words still go on.
- **Who gets it**, settled before anything is written: the Agent on the to-do that most needs it (`pickTaskAgent`, among the ones running: a closed Agent, offline or interrupted, is not counted), else the conversation that opened it (`origin`, when it still exists; for a question's to-do, which has none, the conversation that asked, from its record: "Questions nobody answered"), else the main conversation; one the bot's switches do not allow (`agents` for an Agent, `main` for a conversation) is left out. It is sent as the bot's own send (`botSendIn`), so the run follows it like any message of the bot; when a send fails (the machine is gone, the node refuses) the next one is tried. With no one left, or all of them failing, the words are still recorded and the topic is told "noted on the to-do, but not passed to anyone" (just "couldn't send it" when nothing was recorded). The text is one line, "To-do "X": the user's new decision in the topic" (the title escaped like a decision's text), then what was said (`prompts/todo/thread_reply.md`); the line says it was recorded as a decision only when it was (not for a message of only a picture, with no database, or when the write failed). A Persona conversation also gets the note that it was said in a topic (`bot/message.md`). A quoted message and a merged forward are not read in (what others said there is not the owner's words); a merged forward gets "can't read this kind of message". Handoff context shows these decisions as "said by the user in the Lark topic".
- **The answer stays in the topic**: the run keeps the chat and thread in its channel values (`ext.chat`, `ext.thread`, kept with the run), and its progress card, answer cards and notes are sent with `chat_id` and `in_thread: true` (`feishu.post` / `feishu.text`, #5903), and so are the question, plan, permission and terminal-dialog cards of the conversation the run follows (`postInteractionCard`: the card is a reply to the run's message, in the topic; with a private run on the same conversation it goes to the owner's DM instead and the topic is told so in a line, and it goes to the DM when the topic refuses it outright). It makes no agent message (`feishu.cot_create` only knows the owner's private chat), and its cards are not bound as reply targets of the private chat. A topic's run and a private chat's run on the same conversation are not folded into one answer. A private chat's run keeps neither field and behaves as ever.
- **Not posted back**: a decision with `source = "thread"` is never posted into the thread (`postable`): it is already there, and the bot's own post must not come back as a reply. The posts below ask `postable`; and a bot's own message is not the owner's (`sender_type` is not `user`), so both the hub and `threadMessage` drop it before anything is recorded.

### Posting into the thread

(#5279, step 4.) A to-do bound to a Lark topic tells the topic, in one short line with a link back to the to-do (`/todos?id=…` on the hub's `public_url`; none when the hub has no address), when:

- **a decision is noted**: from the app, a card answer, an Agent (`todo_decision_add`) or the outcome on completion. Not one the user said in the thread, and not the words the user wrote in the private chat as the answer to a "Please verify" card (`postable`): what is said in the private chat stays in it.
- **an Agent working on it finishes a turn or needs the user**: the same two events the phone's pushes are made of (`notifyFinished`, after its push decision; `tell`, for a card that is not muted), so what is not pushed (a turn the user saw, a muted conversation, a turn asked in the bot and answered there) is not posted either. A card the topic already knows about gets no line: it went into this topic (its run was asked there: same chat and same thread), or a line there says it went to the DM (a private run of the conversation wins, `interactionPlace`). Otherwise the line says where the card is: in the DM, it only says so ("Agent X needs you, the card is in your private chat"; what an approval asks is not for a group); in another topic, only that the Agent needs the user; with no card at all (the cards switch is off, or the chat does not drive that Agent), the line is the notice and carries what is asked, except for a permission (a command or a path is not for a group): then it only says the Agent needs the user. An Agent with no name is "an agent".
- **the to-do is accepted** on its "Please verify" card (or from the Accept button of a briefing, when the ask has no card), **done** (by the user, or by the hub's judge, with its reason), or **closed because its Agent never started** (with the error). Accepted and done together are one line, the done one.

The line is "New decision: …", "3 new decisions: …", "An agent finished a turn: …", "Agent X needs you: …", "The to-do is done", joined with the others of the same minute (`assistant-feishu.thread_post_*`, in the bot's language). Decisions are quoted as "question → choice", at most three, the rest counted.

- **At most one line a minute per to-do.** The first thing of a quiet to-do waits 3 seconds (`threadPostSettle`), so what comes right behind it (the rows of one outcome, a decision and the closing) is one line; what happens after a line goes out waits for the minute (`threadPostEvery`) to be over and is then one line, "N new decisions: …". The clock and the timer are the poster's own (`threadPoster.now` / `after`), which the tests replace. A restart forgets what waits: it is a notice, not a record. A post that fails is lost, not tried again. An outcome decision that arrives more than the 3 seconds after the closing (the model is slow) is a line of its own, after the minute.
- **Every line has its own key** (`uuid` of `feishu.text`, cut to 50 characters; `feishu.post` takes it too, for a reply as well as a send into the chat, cut to 46; only letters, digits, `:`, `_` and `-` are taken, any other key is ignored as if none was given). Without it the hub keys a reply by its parent and words, so two lines that read the same under one anchor (two finished turns) would be one to Feishu, and the second silently dropped. Calls that pass no `uuid` keep the key they had.
- **Only into a chat the bot may send into.** Before a line goes out the assistant reads `feishu.status` and posts only when the thread's `chat_id` is in `chats`: the hub's own rule for `feishu.post` / `feishu.text` (the owner's private chat and the group chats the owner opted in, `docs/extensions/bots.md` ("Topic group chats")). Otherwise nothing is sent and the todo's id is logged. This closes the gap that `todo_bind_thread` lets an Agent write any `chat_id` into a binding: what an Agent binds is never a place the assistant writes to unless the owner opted that chat in. (The hub refuses the send anyway; this is the check before it.)
- **Where it goes**: `feishu.text` with `chat_id` and `in_thread: true`, as a reply to the latest message the owner said in that topic. The binding keeps only the `thread_id`, and Feishu replies into a thread by a message in it, so the assistant remembers that message (`bots.feishu.state`, `topics`, per chat and thread, 30 days, at most 200) each time a message of the topic reaches it, bound or not. With none known (nobody has written in the topic since the assistant has had this state) nothing is sent and the todo's id is logged; the first message the owner writes there fixes it. If the anchor was withdrawn or deleted the line is not turned into a message in the group: the assistant's call carries `no_detour` (the hub's option on `feishu.post` / `feishu.text`: a reply to a gone parent fails with `feishubot.MessageGone`), and it forgets that anchor, the line is lost, and the owner's next message in the topic is the new one.
- **Nothing for a to-do with no thread**, none for one unbound while the line waited. Not sent: the log says why.
- **Private chat as before**: the reports and pushes (`reports`, `feishuAgentDone`, the cards) go out as ever; a bound to-do's topic is told in addition. Whether a bound to-do should be told in the topic only is left for later.

### Telling the extensions

(#5279, step 5.) The extensions are told of the to-dos too, through two events (`todo.changed`, `todo.decision`; [extensions.md](../extensions/extensions.md) "To-do events"): the ones that subscribed and were granted `todos.read` (the read scope that already lets them call `GET /api/v1/todos`), so a connector extension can post into a thread it owns as the user. Nothing needs a binding: they go for every to-do. `assistant/todo_events.go`.

- **`todo.decision`** is sent from `insertDecision`, the one place every decision is written through, so every source is told (the thread's own too, with `source: "thread"`).
- **`todo.changed`** is not hung on the writers. Whenever the to-dos change (`todosChanged`, what tells the apps) a timer of one second starts; at its end the to-dos are compared with what the extensions were last told of (title, done or failed to start, bound thread), and a to-do created, deleted or different is told once. A new way to change a to-do cannot forget it, and several changes inside the second are one event. The baseline is taken when the to-dos are loaded, so nothing is told of the ones found there.

### Opening a to-do from a topic

(#5279, step 5.) In a registered group chat, a new topic opens a to-do by itself and hands it to the main conversation: the same as a bot that auto-starts a session on a new topic, but the session is the to-do (`assistant/feishu_thread_open.go`). The hub's gate and registration decide which groups get this far; the assistant opens only for the owner's own messages (see "Replies in the thread").

- **Shared path**: the to-do, the binding and the hand-over are `openTodoIn`; a request from another chat ("Where it came from" below) comes in through it too, with the first message posted by the bot.
- **When**: the message starts its topic (`isTopicRoot`: it has a `thread_id`, and `root_id` is empty or its own `message_id`), or it is "/ai" (or the full-width "／ai", any case) followed by a space or the end, in a topic bound to nothing. The command is taken off, and what is left is the first words. In a topic whose to-do is open "/ai" is a word like any other (a reply, a decision); in one whose to-do is done it is answered "reopen it in the app" every time (the 10-minute limit of the hint does not apply to a command), and no second to-do is made. A reply that is not "/ai" in a topic bound to nothing gets the hint, which now says to send "/ai" and a line. Checked on a real topic group with the message API (not the event push; the two carry the same fields): the first message has an empty `root_id` and `parent_id` and a `thread_id`, a reply has both set.
- **What is made**: a to-do titled after the first words (as `task_plan`'s are, the model renames it later), the first words as its `notes` (not a decision: no decision is written), `origin` the main conversation, which also supervises it (`superviseTodo`), bound to the topic, with its task card in the main conversation's feed. Only a text or a rich-text message has words (`openingWords`): the bot's @ at the start is taken off (in a group where the bot only gets what @s it every message starts with one), an @ further in is the person's name when the message's mentions give it, and the placeholders of other types (`[语音消息]`, a shared group or card, a location, an unknown type) are not words. A message with no words (a picture, a merged forward, a voice message, a rich text of only pictures, or only "/ai") makes nothing and is answered "say it in a line of text".
- **Whom it goes to is settled first**: the main conversation must be allowed by the bot's `main` switch and exist; with no one to take it nothing is made and the topic is told why. The binding is made right after the to-do; if another to-do holds the topic by then (`ErrThreadTaken`) the to-do just made is deleted (`removeTodo`, the DELETE route's own code) and the topic is told.
- **The reply**: one line in the topic, as a reply with `chat_id` and `in_thread` — "To-do "X" opened and handed to the main conversation", with the to-do's web link when the hub has an http(s) address (as the bot's cards' links) — then the hand-over: the first words, quoted line by line (so that a many-line message cannot pass for the instructions around it), and the to-do's id (`prompts/todo/thread_open.md`), sent as the bot's own send (`botSendIn`) so the run answers into the topic. A hand-over that fails leaves the to-do (bound, so a later reply goes to the main conversation) and says so in the topic.
- **Running an Agent on it**: the hand-over tells the main conversation to give `task_plan` the to-do's id as the task's `todo_id`. That reuses the to-do rather than making one: it must be one the plan's conversation opened or supervises, not done, with no live Agent on it (an Agent let go or dismissed does not count, and since #6427 neither does one whose session is listed stopped or archived, or whose computer the hub no longer knows; an unreachable computer's Agent still counts) and not held by another plan that has started and not yet linked its Agent. When the task starts, the stopped Agents still linked are let go (`released_at` only, so they stay in the to-do's history) before the new one links. It is checked when the plan is made (an error says why, nothing is made) and again when it starts (the task gets the reason as its `error`). The to-do keeps its title and notes, and no second task card is added. A reused to-do has no `plan_id`, so a failed start cannot be retried from the plan card (the to-do is closed with the error as for any failed start; reopen it in the app).
- **After that** a reply in the topic goes the way those of a bound topic go: the running Agent, else the main conversation (the origin).
- **Risks**: a registered group used as a notebook gets a to-do per topic; and a group another bot works in is answered twice (`docs/extensions/bots.md`).

### Where it came from

(#6146) A to-do opened for a request made in another chat (`openFromElsewhere`, `docs/extensions/bots.md` ("Asking from any group")) records that chat and message as its `source`, and tells the outcome there once it is done or accepted. `GET /api/v1/todos` returns `source`; nothing writes it but the opening.

- **One way in, whoever received the request.** `openFromElsewhere(ctx, Source{Channel, ChatID, MessageID, Text, Quote})` (`assistant/feishu_elsewhere.go`) posts the topic's first message in the home topic group, then runs the same path as a topic the owner started (`openTodoIn`: to-do, binding, main conversation) and records the source. The Lark bot's gate calls it first. **With no home topic group** it does not turn the request away (Lark is one channel, not the shape of Persona): the first message goes into the owner's private chat with the bot, the to-do is made by the same `openTodoIn` but bound to no topic, and the source gets an `anchor`, the id of that first message (`openInOwnerChat`). The hand-over to the main conversation says so (`NoTopic` in `todo/thread_open.md`: the answer goes to the private chat, and what the owner says there later is not recorded as a decision). The text of a message the request replied to is someone else's: it goes into the notes under a label that says so, and to the main conversation as an escaped context block of its own titled as written by someone else, never in the quotation of the user's words. Another channel (say an extension that sees the owner's own chats) calls it the same way, and tells the outcome back itself: it is added to `sourceChannels` and `sendSourceReport` (`assistant/todo_source.go`); a request from a channel that is not there is refused before anything is posted.
- **When it is planned.** When the to-do becomes done (the user, the judge or the supervisor), when its Agent never started, or when the user accepts it on its "Please verify" card or from a briefing's Accept button, whichever comes first. A done to-do waits for its outcome (`todo_outcome.go` reads the Agents' last replies and asks a model): the report is planned the moment the recording is through, or after `sourceReportWait` (3 minutes) with what there is; a start that failed waits a moment (`threadPostSettle`) only. Only a to-do that is done (not reopened since) and was done within the last 7 days is reported. Reopening and closing again makes no second report.
- **What is told: one fixed-shape line, and the owner sees it first.** The original chat is not the owner's own: nothing of the to-do's inside leaves it. The line is the first line of the latest outcome note (the `#o` row `todo_outcome.go` writes, or the receipt's text when no model wrote it), without the links after it, and cleaned (`cleanReport`): no web address or markdown link, no backtick code, no path (words joined by `/`), no markup (`<...>`, an `<at ...>` among it) and no `@`-mention; at most 600 characters; with no outcome note, or nothing (or only punctuation) left of it, only "Done."; for a start that failed only "Couldn't get this done." (three languages). Not told: decisions, the Agents' replies, the judge's reason, the error of a start, the words of the topic. The text is fixed when it is planned: the topic gets a line, "Will be posted under the original message in 10 minutes: <text> (send /noreply to cancel)" (a to-do with an `anchor` has no topic: the same line goes into the private chat as a reply under the anchor, ending "reply to this with /noreply to cancel"), and the report goes out when the 10 minutes (`sourceReportDelay`) are over. The text and the time are kept with the todo (`source.report_text`, `report_due_at`), so a restart in between keeps both. If the topic cannot be shown the line (the todo was unbound from it, or nothing in it is known to reply under) nothing is planned. A to-do unbound from its topic by the time the report is due tells nothing (there is no place left to say `/noreply`); one with an `anchor` is not affected, its notice is in the private chat. The claim is made in the store: it checks that the planned time kept there has come and returns the planned text kept there, which is what is sent, so an assistant whose own copy of the plan is stale (another one planned it afresh) neither tells early nor tells an old text.
- **Once, and retried only if it may pass.** `source.reported_at` is written before the send (a conditional update, so two assistants on one store cannot both win) and the send carries a key made of the to-do and the message, so Feishu drops a repeat. A look at every to-do with a report to make runs when the todos are loaded and every 10 minutes (`sweepSourceReports`): it plans what is not planned, tells what is due, and retries a try that failed for a reason that may pass (no answer from Feishu, a rate limit, a server error): the claim is given back, and the hub allows a source two replies, so a report has two tries in all (`source.attempts`). A report that can never go (the hub refuses the chat, the original was withdrawn or deleted, Feishu says no) or has used its tries keeps its claim, is not tried again, and the topic is told "Couldn't post the outcome where it was asked: <why>". One that could not be told because the bot was not ready claims nothing and is found by the next sweep. A to-do reopened between the plan and the time cancels it (the text and the time are dropped, `ClearTodoSourcePlan`); closed again, the text is worked out afresh, the topic is shown a new notice, and the 10 minutes start again, so what goes out is always the last text the topic was shown.
- **Don't report back.** "/noreply" (also the full-width slash, any case, and nothing else in the message besides the bot's own @, which a group that only sends what @s the bot starts every message with) said in the topic sets `source.no_report`; said in the 10 minutes after the notice it cancels the report. Decided by the text alone, never by a model; recorded as a `source = "thread"` decision of the to-do ("Don't report back to where it was asked"); not passed to any Agent; works while the to-do is done and not yet told. After the report went out it says so. On a to-do with no source it says there is nothing to stop. The topic's first message says it. A to-do with an `anchor` has no topic to say it in: the owner replies `/noreply` to the anchor (the bot's first message in the private chat), to the notice, or to any answer under them (the reply's `root_id` or `parent_id` is the anchor); it is recorded as a `source = "manual"` decision ("Reply in the Lark chat") and not passed on. A `/noreply` in the private chat that replies to none of those is an ordinary message.

## Due date, reminder, priority

#1683. A to-do can be due at a moment (`due_at`) or on a day (`due_date`, read in the user's time zone: due by the end of it), have a reminder (`remind_at`) and a priority. The assistant's `remindLoop` (`todo_plan.go`) sleeps until the next reminder (at most a minute, woken when the to-dos change) and pushes each one once when it is due:

- It claims the reminder in the store first (`reminded_at` set only while `remind_at` is still that moment, not yet pushed and the to-do not done), then pushes it like `notify_user`: to every device (opening the main conversation) and to the Feishu bot and the channels with pushes on. A claimed push that is lost is not retried; a reminder is never pushed twice, by a restart or a second manager.
- The push's title is the to-do's, its body the due date (or "was due" once it has passed), the first line of the notes, and when it went out more than two minutes late (the manager was down), the time it was for.
- A done to-do is not reminded; changing `remind_at` re-arms it; a mesh member on standby leaves it to the center, as with scheduled tasks.

## Imported from Reminders

#4009 (`assistant/todo_imports.go`). The iPhone can import the user's Reminders as to-dos, one way. The phone reads the
lists the user picked (Settings › Phone data › Reminders) and sends their incomplete reminders to
`POST /api/v1/todos/import/reminders`; the manager matches each by its `external_id` (`todo_imports`):

- **New**: a reminder never seen becomes a to-do with its title, notes and due date (a moment, or a day for an all-day
  reminder). One without a title is skipped.
- **Changed**: only the fields that changed in Reminders since the last import are written, so a title the user changed
  in Persona stays until the reminder's title changes too. A due date removed in Reminders is removed here.
- **Left alone**: completing or deleting a reminder does nothing to its to-do, and nothing is ever written back to
  Reminders. A to-do deleted in Persona stays deleted: its reminder is skipped from then on.
- One batch at a time per manager; when two managers import the same new reminder, the second removes its copy.

The import runs only while the app does (launch, return to the foreground, a change in the Reminders database while it
is in front), since only the phone can read Reminders; it is not real time. There is no background refresh yet, which
keeps it out of the battery budget (#1633). A batch the hub already took (same hash, same hub) is not sent again
(`apple/Persona/PhoneTools/RemindersImport.swift`). A request takes at most 1000 reminders; the phone sends more in
several requests, in a stable order, and counts the set as sent only once every request was taken.

## Calendar

#2029. The to-dos page switches between the list and a calendar (List | Calendar at its top, kept per device; the calendar's Day | Week | Month too). The calendar shows the to-dos that have a due date, from the same list the page already has: `GET /api/v1/todos` returns them all, so switching needs no request and works offline from the cache.

- **Where a to-do goes**: due at a moment (`due_at`) on the time axis of the day and the week, the block's top edge at that moment. A due moment is not a span, so every block is the same height (about 50 minutes, a tap target). Due on a day (`due_date`, a day in the user's time zone) in the All Day row above the axis, on that day on every device. Blocks that would overlap sit side by side; on an iPhone's week, whose columns are a few characters wide, they become one block that says how many and opens their day (Android keeps them side by side there too, narrower, so each can still be dragged; #4200).
- **The month**: each day shows up to three lines (all-day first, then by time), or two and "+N" (phone) / "N more" (iPad, Mac). Tapping a day opens it in the day view; on Android a sheet lists that day's to-dos first (state, when, flag and bell; a tap on one opens it, as the month did before the day and week), with Show Day to open the day view.
- **Looks as in the list**: the bar and the dot are the state's color (needs you, working, done unread, not started); overdue is red, before the state; done is faded and struck through (Show Done, in the calendar's options, hides them, per device); a flag for high priority and a bell while a reminder is still to be pushed, as on the row. A reminder is not drawn on its own: it is not something to do, and would show the to-do twice. The moment is a red line on today.
- **Without a due date**: not on the calendar; a bar under it says how many and goes back to the list.
- **Moving around**: Today, previous / next, and on iOS and Android a sideways swipe; the day view has the week's strip (a dot for each open to-do, a few) to pick a day; a day of the week, or of the month, opens that day.
- **Where a week starts**: on the system's or browser's first day of the week, the same for the day's strip, the week and the month. Apple: the first weekday the user chose (Language & Region), else Monday in Simplified Chinese or on the Chinese mainland (Apple's data still says Sunday there; current CLDR and the browsers say Monday), else the region's (`TodoCalendar.userCalendar`). Web: `Intl.Locale` week info for the browser's language (`zh-CN` Monday, `en-US` Sunday); a browser without it goes by the language's region (`weekStartDay`). Android: the region of the app's language (the web's CLDR table; a language without a region goes by its usual one, `zh` → CN, Monday; `weekStart` in `core:domain`).
- **Making one**: tapping the empty axis offers a new to-do due there (snapped to the half hour; the All Day row: that day), only its title to type (`TodoQuickAddSheet`; the reminder, priority and notes are set on its page; at the accessibility text sizes the date is a wheel under its label and the sheet opens full height, as in "Change Due Date…"). The page's "+" in the calendar makes one due on the day shown. `POST /api/v1/todos` takes `due_at` / `due_date` with the title.
- **Moving one** (#2045; the web, iOS / iPadOS and Android): drag a to-do on the axis of the day or the week to another time (its top edge snaps to the quarter hour) or another day's column, onto a day's All Day row (due that day, all day), or in the month onto another day (the same time there; an all-day one stays all day). Every to-do on the calendar can be moved, done ones too. While it is dragged, it fades where it was and where it would land shows with the time; letting go saves it at once (`PATCH /api/v1/todos/{id}` with `due_at` or `due_date`, either replacing the other), dropping it where it was sends nothing, and a failed save puts it back and says why. A mouse drags after a few pixels of movement, so a click still opens the to-do; a touch drags after a press held still, so a swipe still scrolls and turns pages.
  - Web: a touch picks it up after 350 ms; Escape puts it back. The drop rules are pure in `web/src/lib/todo-calendar.ts` (`dropOnAxis`, `dropOnDay`, `dropPatch`).
  - iOS / iPadOS: a press held still 0.35 s picks it up on the day, the week and the month; on an iPad a trackpad or mouse drags after a few points of movement. While it is carried the time shows in the hours' column, the page doesn't turn, and near the top or bottom edge of the axis, or of a month taller than the screen, it scrolls; a phone's week block that stands for several still opens their day. ## Project

#2581. A to-do can belong to one knowledge-base project (`todos.project`, its slug; `todo_project.go`), usually a long-term one standing for an area of the user's work. The knowledge base already keeps these areas with a summary and a timeline; the to-do only points at one.

- **Setting it**: the apps through `POST` / `PATCH /api/v1/todos` (`project`), the assistant through `todo_create` / `todo_update` and each `task_plan` task's `project`. A slug, a name or an alias is accepted (`kb.Engine.FindProject`; a merged project's name leads to the one it went into) and stored as the slug; no live project of that name, or the knowledge base off or not open, is refused. The assistant's CLAUDE.md tells it to set one when the area is clear, reusing an existing project (long-term first) and never making a near-duplicate.
- **Outcomes**: a finished task in a project writes its conclusion to that project's timeline only ("Record conclusions on completion"); the directory-inferred projects get it when it has none, or when its project was deleted or ignored since.
- **The web To-dos page** groups open to-dos under their project's name (from `GET /api/v1/kb/projects`; the slug while the list is not loaded) before the groups by repository, which only to-dos without a project still fall into; those with neither go last under **Unsorted**. The detail picks the project from a menu (long-term projects first). An area's group never folds for being quiet and shows no "Done" when no agent is at work: its to-dos are the user's open ones. The iPhone and iPad (#7077) show it too: a **Project** row in the detail with the due date, reminder and priority (the same choices and order as the web's picker), and **Group By › Project** on the To-dos list (a section per project, the one with the most pressing to-do first, then **Unsorted**, then Done folded, as the other groupings). The Mac and Android ignore the field for now. Checked by `scripts/test/web_todo_project_e2e.py` (mock hub, light and dark, wide and phone width).

## The assistant's todo tools

#1683. The assistant has the user's to-dos as MCP tools (`todo_tools.go`, descriptions in `prompts/mcp/todo/`), so it can note what the user asks it to, or a batch of deadlines from a mail, without a hub token:

| Tool | What it does | Confirmed on the phone |
| --- | --- | --- |
| `todo_list` | Open to-dos and failed starts by default, earliest due first (none last), filtered by state, due before / after, overdue, with or without agents, project, words | — |
| `todo_get` | One in full: notes, agents, the task it is, decisions in force | — |
| `todo_create` | `title`, `notes`, `due` (a day, a moment in the user's time zone or RFC 3339, `2h` / `3d`), `remind` (a moment, not past), `priority`, `project`; an open to-do with the same title and due date is returned instead of made twice | No |
| `todo_update` | Title, notes, due, remind, priority, project; `""` clears | No |
| `todo_complete` / `todo_reopen` | Mark done / open again | Only for a task, or a to-do agents work on (completing closes its agents) |
| `todo_delete` | Delete for good | Always |

A to-do it makes is the user's own (no `origin`): work for an agent still goes through `task_plan`. In a health conversation, anything that writes asks first (`confirmOutbound`, `health.md`). The generated CLAUDE.md tells the assistant to use `todo_create` when the user says to note a to-do or to remind them of something.

## Design trade-offs and reasons

1. **Not another Lark Tasks or Reminders**: Persona to-dos drive and track Agent workflows, focusing on which Agents share one task and their progress, not complex subtasks, deadlines, priority trees, calendar reminders or multi-party collaboration. The Reminders import (#4009) keeps to that: one way, title, notes and due date only, so a to-do started in Reminders can be handed to an Agent without retyping it; lists, subtasks, sharing and completion stay in Reminders.
2. **No stored state**: overall state derives entirely from linked Agents' live runtime states (questioning, working, finished unread, etc.). Agent state changes frequently; derivation avoids dual-write consistency problems and large synchronization overhead.
3. **One active to-do**: `UNIQUE (machine_id, session_id) WHERE released_at IS NULL` ensures each Agent serves only one current to-do at a time. Assigning other work automatically marks the previous task "Previously involved", keeping context and execution goal clear.
4. **Automatic completion only for chat-dispatched tasks, judged by model**: these have explicit requirements (dispatch prompt) and deliverables (Agent's final reply), so requiring individual user completion taps is a burden; manual to-dos often represent the user's own plans, whose completion hub cannot know. Stopped is not finished, so do not close by state alone; judgment model decides, leaving open when uncertain. Wrong auto-close (user thinks finished) costs much more than missed close (one extra tap), hence reversible, reasoned, and not reclosed by the same work after reopening.

## Known limitations

1. **Direct renames inside herdr**: renaming workspace in herdr terminal rather than hub API acts as a new project; previously linked Agents remain, but later Agents in that workspace will not auto-link.
2. **Marker overwrite across multi-hub groups**: a computer's persistent node serves only one long-lived connection at a time. If independent hubs in different linked-hub groups connect alternately to one node, later hub's expected markers overwrite earlier hub's.
3. **Empty-workspace rename does not migrate**: when renaming through hub with no active sessions, hub cannot resolve old workspace name; `todo_spaces` does not automatically migrate, like pin/mute.
4. **`/clear` recreates session**: Agent `/clear` creates a new session uuid underneath; new session does not auto-link to old to-do, and original session row stays listed.
5. **Assistant disconnected**: to-do APIs and create/send with `todo_id` return 503; workspace renames through hub do not migrate and answered cards are not recorded as decisions ("Who owns what").
