# Internationalization (i18n)

Apple (iOS / macOS / Watch / extensions), Android, the web app, and hub share this policy. Implementations may differ, but the language list, fallback rules, terminology, and protocol must agree. This document takes precedence in a conflict; update it before changing the policy.

Public documentation, code comments, issues, and PRs are written in English. User-visible strings belong in localization resources, with `en`, `zh-Hans`, and `ja` supported consistently. Additional languages must be extensible through resources, not hardcoded UI branches.

## Supported languages

| Code | Name (always shown this way in the selector, regardless of UI language) | Notes |
| --- | --- | --- |
| `zh-Hans` | 简体中文 | Existing Chinese UI wording is retained; Apple uses English development keys (#5090), without changing Chinese display |
| `en` | English | Fallback language |
| `ja` | 日本語 | Japanese resources |

These three languages ship today. Clients use their canonical codes in settings, resource names, and requests to the hub, without regional suffixes. Web, Android, and hub discover supported languages from resources; see "Adding a language" below.

## Choosing a language

The "Language" setting (web: **Settings › General › Appearance › Language**; Android: **Settings › Appearance › Language**; Apple: **Settings › Appearance › Language**) has four options: **Match system** (default), 简体中文, English, and 日本語.
An explicit selection wins. When matching the system, resolve only the system's **first preferred language** (do not look for a second match):

| First preferred system language | Result |
| --- | --- |
| Any Chinese variant: `zh`, `zh-Hans`, `zh-CN`, `zh-SG`, `zh-Hant`, `zh-TW`, `zh-HK`, `zh-MO`… | `zh-Hans` |
| Any Japanese variant: `ja`, `ja-JP`… | `ja` |
| Unsupported languages (currently including `fr`, `ko`, `de`), English, or unavailable preference | `en` |

Match the language subtag (the first segment, case-insensitive, treating `_` as `-`), so Traditional Chinese also resolves to Simplified Chinese. Each platform must implement and unit-test this resolver. **Do not rely on the system's automatic matching**:
iOS Bundle matching and Android resource qualifiers may fall back to the development language (Chinese), or use their own selection rules when a language is missing. That does not match the table above.

- When a translation is missing in the target language, fall back to `en`, then `zh-Hans`, then display the key (development builds only; tests should catch this).
- Language changes take effect immediately, without restarting. If a platform cannot do this, at least explain it in Settings and apply the change on the next launch; do not silently leave the UI unchanged.
- Never translate "Persona" or user-defined avatar names.

## Dates, numbers, and sorting

Always use platform formatting APIs (`Intl.*`, `Date.FormatStyle` / `DateFormatter`, `java.text` / `DateTimeFormatter`). Do not assemble date labels such as 「月」「日」「周」 (month, day, week) by hand, or hardcode `zh_CN`.
Formatting locale: use the system locale when its language matches the current UI language (preserving regional conventions, such as date order in `en-GB`); otherwise use the UI language code (`zh-Hans`, `en`, or `ja`).
Use `Intl.RelativeTimeFormat` / `RelativeDateTimeFormatter` for relative time (「3 分钟前」, "3 minutes ago"). Use platform plural rules (English distinguishes one / other; Chinese and Japanese have only other).

## Copy style

- **Chinese**: keep the existing conventions (spaces between Chinese and English or numbers; use 「」 for quotation marks).
- **English**: conversational and concise, with platform-appropriate capitalization. Use Title Case for iOS / macOS navigation titles and buttons (Apple HIG), and sentence case throughout Android and the web app (Material).
  Do not translate Chinese word for word: use Unread for 「完成未看」 (completed but unseen), not Completed not viewed. Buttons use verbs (Approve, Send); an empty state explains the next step in one sentence.
- **Japanese**: use the polite です・ます style for sentences, and noun phrases for buttons and labels (「承認」「送信」「設定を開く」: approve, send, open settings). Use full-width punctuation 「、」「。」 and 「」 for quotation marks.
  **Do not insert spaces** between Japanese and English or numbers (consistent with Apple / Microsoft Japanese interfaces). Retain long-vowel marks in katakana according to Microsoft conventions (コンピューター、サーバー: computer, server).
- All three languages must fit. English is on average 1.5–2 times longer than Chinese; Japanese is slightly longer than Chinese. The single-line button rule (`CLAUDE.md`) applies to all three. Shorten copy or use an icon if it does not fit; do not wrap or truncate it.
- Always name placeholders (`{count}`, `{name}`), allowing each language to set its own word order. Do not concatenate fragments (`"已发送给" + name`, "Sent to " + name, must become a complete sentence with a placeholder).

## Command line

What a command prints for people (`personad`, `persona-hub`, `persona-node`, `persona-manager`) is in the **terminal's language**, not the user language: a hub is often set up or repaired over SSH by someone whose apps are in another language (#5520).
`i18n.Terminal()` reads `PERSONA_LANG` (a catalog code or BCP 47 tag, for when the locale cannot be changed), then the POSIX locale's messages category in its own order (`LC_ALL`, `LC_MESSAGES`, `LANG`): the first one set wins, its language part is resolved as above (`zh_TW.Big5` is zh-Hans), and `C`, `POSIX`, an unknown language or nothing set is English.
A command that calls the running hub sends that language as `Accept-Language`, so the hub's own text (errors, permission lines, statuses) comes back in it; a command that has to recognize a hub error checks its `code`, never its text (`hub peer center` and `confirm_required`).
Machine-readable output (JSON such as `extension show`, `--get` values, `RESULT` lines) is not translated. Catalog namespaces are per command family (`extmgr-cli`, `hub-cli`, `hub-doctor`, `hub-setup`); tests pin the language with `PERSONA_LANG` rather than relying on the machine's locale.
A report that a command prints and a page also shows is built once as data and worded where it is shown: `hub doctor` collects items (`ok` / `problem` / `info`, an item, its detail) and next steps, the command prints them in the terminal's language and the admin page's **Run checks** (`POST /api/v1/admin/doctor`) gets the same items in the page's language. Never parse a command's printed text back into data.
`hub setup` speaks the installer's language when it has one (`--lang`, else `PERSONA_INSTALL_LANG`, which `install.sh` sets from the language it ran in), else the terminal's; its `--json` lines word `detail` and `next` the same way and keep `step` and `ok` as machine fields.

## Adding a language

Web, Android, and the hub discover supported languages from resources. To add Korean (`ko`), for example, add translations without changing a switch, enum, settings page, or checker:

- **Web**: copy the English directory under `web/src/i18n/locales/` to a new `ko/` directory, translate its namespace JSON files, and set `_meta.json` to `{"name":"한국어","matches":["ko"]}`. Translate the separate `admin-*` namespaces too. The shared Vite plugin generates the client and admin modules; the picker and preload script discover them automatically.
- **Hub**: copy the English directory under `server/internal/i18n/locales/` to `ko/`, translate the JSON files, and add the same `_meta.json`. The directory is embedded in the binary. `Langs`, `Resolve`, `Valid`, and the language name supplied to prompts update automatically. Cardinal plural categories use the existing `golang.org/x/text` CLDR rules.
- **Android**: add a language file under `android/i18n/` named `ko.properties` with the metadata below, plus a `values-ko/strings.xml` resource in every module with interface text. Gradle generates `AppLanguage`, the in-app choices, `locales_config.xml`, and APK locale filters. Existing Chinese stays in `values-zh/` so Traditional Chinese systems still use Simplified Chinese; it is not narrowed to the regional `values-zh-rCN/` qualifier.

```properties
name=한국어
matches=ko
resources=values-ko
plurals=other
```

`name` is the language's own name, `matches` is a comma-separated list of lowercase language subtags, `resources` is its Android resource directory, and `plurals` lists its CLDR cardinal categories (including `other`). Each subtag belongs to exactly one language. Currently `zh` maps to `zh-Hans` and `ja` to `ja`; adding Korean makes `ko` map to `ko`. Only the first preferred system language counts. An unsupported language falls back to English rather than searching later preferences.

Run the web catalog and preload tests, `python3 scripts/app/android_i18n_check.py`, and `go test ./internal/i18n` after adding resources, then build and inspect screenshots. The checks automatically cover new languages and reject missing keys, placeholders, or metadata. Web and hub look up a missing entry in English, then Chinese, using each fallback language's own plural rules; fallback does not mean a translation is complete.

The protocol fields are unchanged. A new language uses its own BCP 47 code. An older hub that does not recognize it retains its existing fallback; clients that omit locale retain their old behavior. Ship client and hub resources together. Apple extends its String Catalog using the same code. Korean is only an example here, not a shipped translation.

## Deployment errors across requests

Deployment jobs keep canonical source-language errors in Postgres and manager reports, so a language change does not freeze the job in its starting language. `i18n.DeploymentText` matches only the deployment catalog templates (including known node capability reasons), then formats them for the current HTTP request or WebSocket connection. Machine snapshots, live machine events and resumed events translate copies; persisted records, RPC retry codes, versions and unknown node/SSH details stay unchanged. This compatibility bridge also reads records saved before localization; it is not a general translator for transcripts or user content. Changing `client_hello.locale` refreshes the full client's current machine status immediately.

Unknown-machine HTTP errors and the machine settings validation errors use `i18n.Err` and the request's `Accept-Language`. Undeclared routes still use the router's standard response and are not claimed as localized.

## Protocol: telling hub the language

Hub needs two language choices: the language of **this request / connection** (synchronous errors and status copy), and the language of **this user** (asynchronous output: push notifications, assistant replies, injected messages, bot replies).
Clients send only the resolved code (`zh-Hans` / `en` / `ja`), not "Match system". When the user changes the language, or the system language changes while matching the system, immediately resend it in all three places below.

| Where | Field | Purpose |
| --- | --- | --- |
| Every HTTP request | Header `Accept-Language: <code>` | User-visible text in this response (`error`, status explanations, server-rendered web pages). The browser's own `Accept-Language` (`en-US,en;q=0.9`) is also accepted; resolve the first entry using the fallback rules above |
| WebSocket | `client_hello.locale` | Copy such as `notify` and `error` on this connection; also updates the user language (below). Browser WebSockets cannot carry custom request headers, so this field is required |
| Device registration | `locale` in `POST /api/v1/devices` | Notifications pushed to this device use this language; when absent, use the user language |

Current senders: web and Android send the first two (`web/src/lib/api.ts`, `lib/store.ts`; Android `ClientLanguage`). Neither registers push devices, so neither sends a device `locale`. Apple sends all three, using this launch's interface language (`LanguageStore.launched`): `Accept-Language` from `APIClient` and the WebSocket handshake, `client_hello.locale` from `LiveConnection`, and `locale` in `APIClient.DeviceBody` ([ios.md](../apple/ios.md), "Interface language").

For each hub broadcast, machine status and extension events are localized once per receiving language, and connections using that language share the resulting bytes. The cache lasts only for that broadcast and its event type, so later events and locale changes get fresh results. For events retained in the resume log, the hub keeps the canonical payload with its sequence number; resumed events are localized for the reconnecting client.

**User language**: hub stores it in Postgres `settings` (`user_locale`). Assistant replies, injected messages, task notifications, Lark / WeChat bot replies, and push notifications to devices without their own `locale` all use it. If no client has ever reported a language, it is hub.json's `initial_locale`: the language the installer ran in, written by a new install's `personad hub setup` ([config.md](../operations/config.md), #5519). It is not saved as `user_locale`, so the first device to report a language still sets it. A hub without `initial_locale` (one set up before it, by hand, or in Docker) uses `zh-Hans`, preserving behavior for old clients and existing users.
It changes only when **a device's own interface language changes**. The hub remembers the `locale` each device last reported in `client_hello` (`hub.device_locales`, the 64 most recently changed devices) and counts only clients with the `full` role (Watch, link, and linked-hub credentials do not count):

- The first device to report a language sets the user language when none is saved yet.
- A device reporting a different language than it did before (the user picked another language in that app, or the system language changed under "Match system") sets the user language to the new one, whether on a new connection or by sending `client_hello` again on the same one.
- A device reporting for the first time, or reporting the same language again, is only remembered. Another device connecting in its own language, or the user switching devices, leaves the user language alone: an English Mac and a Chinese iPhone no longer flip it at every reconnect.

A device is its device credential; a connection on the main token is identified by its hello's `device_id`, and one with neither can only set the first language. A hub upgraded from a version that took the most recent report keeps the language it had saved until a device changes its own.

A hub supporting this protocol includes `locale` in `hello.features`, and also includes a `locale` field in `hello` (the current user language). Old hubs ignore these fields; clients still display their own localized copy.
The existing `locale` in extension UI context keeps its region-bearing BCP 47 format, such as `zh-Hans-CN` ([extensions.md](../extensions/extensions.md), "Context"). Its language portion should come from the UI language. Android sends the UI language plus the phone's region (`ClientLanguage.localeTag()`, the same language as its `Accept-Language`). Web still sends the browser's `navigator.language`, and Apple the Bundle-matched language plus region (`ExtensionUIModel.appLocale`); both still follow the system language rather than the UI language.
[protocol.md](protocol.md) is authoritative for field details.

## Follow-up work (not in this round)

- **Extension contribution titles**: an extension's name, description, settings form and secrets come in the request's language from the package's `l10n/<language>.json` and the index entry's `l10n`, picked by the hub (#897, `docs/extensions/extensions.md` "Translations: `l10n/`"). Contribution titles (pages, navigation entries, shortcuts, themes) and built-in extensions still have one language.
- Knowledge base content (chat summaries, people / group / project pages) keeps its original language; do not rewrite it when the UI language changes.
- **Refusal notices** (`Item.model_refusal`): the hub adds localized explanation and recovery guidance in every supported language, including `zh-Hans`, while preserving Claude Code's original model names, category, scope, explanation and raw record. Unknown refusal subtypes receive a neutral heading, without inventing a fallback.
- **Chinese written by node in chats** (`server/internal/transcript`): node does not know the user language. Before sending items / sessions to the app, hub rewrites recognized text according to the connection or request language
  (`hub/transcript_text.go`: task notification titles are rewritten by `task` kind / status; `已中断` (interrupted), `/loop 到点` (/loop due), Codex events, agent teams labels,
  `activity`, each background workflow agent's `latest_tool.summary` and each subagent's `last_tool.summary` (the same activity text), commands moved to the background on timeout, `来自` (from) in queued messages, and the main chat's CLI fallback reasons `runtime_fallback` (source text is `proto.Fallback*`) are recognized from node's literal output). Still Chinese: `上下文已压缩` (context compacted), `已从压缩的上下文继续` (resumed from compacted context), `压缩上下文` (compact context)
  (the app uses these to recognize compaction dividers and /compact echoes), `API 错误：…（正在重试 / 重试 N 次后放弃）` (API error: …; retrying / giving up after N retries, parsed by the app's API error card),
  and `…（已截断…）` (…truncated…, recognized by the app to show "View full text"). Before translating these, node must add structured fields to items, clients must render from those fields, and hub can then replace the text.
  Items read by the assistant and channels are not rewritten (`assistant/done.go` tests for `已中断`, interrupted), so these lines forwarded by Lark / WeChat bots also remain Chinese.
- The "type" in assistant chat titles (`功能` / `修复`, feature / fix…) consists of fixed Chinese terms parsed by the assistant (`assistant/titles.go`). The topic follows the user language; the type remains Chinese.
- **Hub text still parsed by clients as literal Chinese** (requires structured fields and field-based rendering on every client before translation): the model configuration status `未验证` (unverified, compared literally on iOS and Android),
  session titles `MMDD | 类型 | 主题` (type | topic) and `旧主对话 · 至 M月D日` (old main chat · through month M, day D; assembled / parsed by iOS and web), and injected messages themselves (the app displays only hub's localized `injected.line`).
- Text written into chats or sent to an Agent or model either follows the UI language or remains Chinese, depending on each implementation's choice. Web slash commands (`/继续`, /continue, etc.) and `用户拒绝了` (the user denied it) are sent in the UI language;
  the first line of a task reference, `任务「…」` (task "…"), `（整篇）` (entire document) inside `<persona-context>`, and instructions to stop `/loop` remain Chinese because they are read back or matched.
- Persisted text (run history, Inbox sorting reasons, default device-token names, audit records) keeps the language used when written; it is not rewritten on a language change.
- The WeChat extension gets its language from `initialize`'s `hub.locale` at startup. A language change does not take effect until its next restart.
- The `site/` website, privacy policy, and terms of service.
- Command-line output not moved to the catalogs yet ("Command line" above; `hardcoded-terminal-baseline.json` lists what is left: node doctor and preflight, Persona Link, the manager's commands, `personad ask` / `notify`). Logs stay as they are.
